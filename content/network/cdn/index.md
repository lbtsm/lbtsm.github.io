## Summary

在网络传输中,有一个东西,无论协议怎么优化都突破不了的,那就是**光速。**，例如:

```
一个请求从北京发到纽约，其直线距离约 11000 km
光纤里的光速约 20 万 km/s(比真空中慢约 1/3)

单程理论最快:  11000 / 200000 ≈ 55 ms
一个来回(RTT):至少 110 ms
```

这还是只是理想值。实际光缆不走直线(要绕路、要经过登陆点),中间还有几十跳路由器要转发和排队,真实 RTT 可能更长。而这个现象也推论出:只要用户和服务器之间隔着半个地球,你的协议优化得再好,也快不过物理定律。

那怎么解决这个问题呢,既然路途远,那就让让数据跑那么远呗,把内容搬到离用户近一点的地方就可以了。

这就是 **CDN(Content Delivery Network,内容分发网络)** 的全部思想。它不是一个更快的协议,而是属于**部署策略**:在全球各地部署成百上千个节点,把内容复制过去,**让用户就近取货**。

> 用现实类比:**这就是从"全国只有一个总仓库,所有订单都从北京发货"改成"每个省都有前置仓,你下单后从最近的仓库发"。** 京东次日达和亚马逊的物流网络,解决的是同一类问题。

## CDN 只做的三件事

加速只是最显眼的那件,另外两件同样重要。

### 降低延迟:把距离缩短

用户到边缘节点通常只有 10~30ms,而不是 200ms。**光这一项就能让首屏时间下降一个量级。**

而且收益是**复利**的:延迟低不只是"每个包快一点",还意味着**握手快、慢启动爬得快、每个往返都省时间**。一个需要 5 个 RTT 才能完成的页面加载,RTT 从 200ms 降到 20ms,总时间从 1 秒降到 100ms。

### 削减源站压力与带宽成本

**这一点常被低估,但它往往是企业上 CDN 的首要动机。**

一个热门文件被一百万人下载:

```
没有 CDN:  源站要发一百万次     → 带宽账单爆炸,服务器可能被压垮
有 CDN:    源站只发几百次(每个边缘节点回源一次)
           剩下的都由边缘节点就近提供
```

**源站的负载从"用户数量级"降到了"节点数量级"**,通常能降 90%~99%。而且 CDN 的带宽单价远低于云主机的出网带宽——**很多公司算完账发现,上 CDN 是省钱的,加速反而是附赠的**。

### 抗攻击与安全

因为所有流量先到 CDN,**源站 IP 可以完全隐藏**。DDoS 攻击打到的是 CDN 的全球分布式网络,而不是你那台服务器——**攻击流量被分散到几百个节点上稀释掉了**。

现代 CDN 还顺带提供 WAF(Web 应用防火墙)、Bot 管理、TLS 卸载。对小团队来说,套一层 CDN 是性价比最高的安全措施之一。

## 怎么把用户导到最近的节点:两种调度方式

CDN 的第一个技术问题是:**用户在浏览器里输入 `www.example.com`,怎么让他连到离他最近的那个边缘节点?**

有两条主流路线,原理完全不同。

### DNS 调度:靠"给不同的人不同的答案"

```
① 你把 www.example.com 配一条 CNAME,指向 CDN 的域名
      www.example.com.  CNAME  example.cdn-provider.net.

② 用户查询时,CDN 的权威 DNS 服务器看查询来源在哪
      北京的用户  → 返回北京边缘节点的 IP
      纽约的用户  → 返回美东边缘节点的 IP

③ 用户直接连那个 IP
```

**关键在于第 ②步:CDN 的 DNS 服务器会根据"你从哪来"返回不同的 A 记录。**

**它是怎么判断你在哪的?** 早期只能看你的本地 DNS 服务器的 IP——而这就是它最大的缺陷:

> 如果你在上海,却把 DNS 配成了 `8.8.8.8`(Google 在美国),CDN 看到的是"这个查询来自美国",于是**给你返回美国的节点**。你就跨洋取数据了,反而更慢。

补丁是 **EDNS Client Subnet(ECS)**:递归解析器在查询时**带上用户 IP 的网段前缀**,让 CDN 知道真实用户在哪。但这又**泄露了用户位置隐私**,所以并非所有解析器都启用(Cloudflare 的 1.1.1.1 就默认不发 ECS,理由正是隐私)。

**局限**:

- **受 TTL 限制**,节点故障后切换不及时(所以 CDN 的 TTL 通常设得很短,几十秒)。
- 只能按"网段"粗粒度调度,**不能感知实时链路质量**。

### Anycast:靠"让路由自己选"

**所有边缘节点公布同一个 IP 地址**,靠 BGP 路由协议把用户的包自动送到"网络上最近"的那个节点。

```
DNS 调度:   不同用户拿到【不同 IP】     → 靠 DNS 分流
Anycast:    所有用户拿到【同一个 IP】   → 靠路由分流
```

**对比:**

| | DNS 调度 | Anycast |
|---|---|---|
| 切换速度 | 受 TTL 限制(几十秒~几分钟) | **路由收敛,秒级** |
| 精度 | 看 DNS 服务器位置(可能错) | **看实际网络路径**,更准 |
| 节点故障 | 要等 DNS 更新 | **BGP 自动绕开,近乎无感** |
| 抗 DDoS | 一般 | **极强**(攻击流量被全球节点自然分摊) |
| 部署门槛 | 低,买服务就行 | **高**,需要自己的 IP 段和 BGP 能力 |

**Cloudflare 是 Anycast 的典型代表**,它的全网就一套 IP,靠路由把你导到最近的数据中心。传统 CDN(Akamai 等)更多用 DNS 调度,现在很多是**两者混用**。

> **一个必须知道的细节:Anycast 对 TCP 是有风险的。** 路由可能在连接中途变化,把后续的包送到另一个节点——那个节点没有这条连接的状态,连接就断了。所以 Anycast 更适合 UDP(DNS)和短连接;用于 TCP 时需要网络层面保证路由稳定。
>
> **而这一点恰好是 QUIC 的一个额外优势**:[08 篇](./08-HTTP3与QUIC.md) 讲的连接 ID 让连接不绑定 IP 路径,**Anycast 路由抖动对 QUIC 的影响远小于 TCP**。

## 回源:边缘节点没有的东西怎么办

用户请求到了边缘节点,但**节点上不一定有这份内容**。

```
用户 ──▶ 边缘节点
           │
           ├─ 缓存命中(HIT)   → 直接返回,几十毫秒搞定 ✅
           │
           └─ 缓存未命中(MISS)→ 【回源(origin pull)】
                                    │
                        ┌───────────▼───────────┐
                        │  上级节点 / 区域中心    │  ← 多级缓存
                        └───────────┬───────────┘
                                    │ 还是没有
                        ┌───────────▼───────────┐
                        │      你的源站          │
                        └───────────────────────┘
```

### 多级缓存:保护源站的关键

大型 CDN 不是"边缘 → 源站"两层,而是**边缘 → 区域中心 → 源站**的多级结构。

**为什么要中间这一层?** 假设全球有 500 个边缘节点,一个新文件第一次被访问时:

```
两级结构:  500 个边缘节点各自回源一次 → 源站被打 500 次
三级结构:  500 个边缘 → 20 个区域中心 → 源站只被打 20 次
```

**这个"收敛"效果在热点内容发布时是救命的**。视频网站发布新剧集、电商大促上新品,如果没有多级缓存,发布瞬间的回源风暴能直接打垮源站。

### 缓存击穿与合并回源

还有一个更尖锐的问题:**同一个边缘节点上,一万个用户同时请求一个刚过期的文件,会发生什么?**

朴素实现下:**一万个请求同时发现缓存没了,一万个回源请求同时打向源站**——这叫**缓存击穿(cache stampede)**,基本在有缓存的设计情况都要考虑这个情况,源站瞬间崩溃。

CDN 的解法是**合并回源(request coalescing / collapsed forwarding)**:

```
同一个资源的并发 MISS 请求:
  第 1 个 → 真正回源
  第 2~10000 个 → 【挂起等待】,不发起新的回源
  源站响应回来 → 一次性唤醒所有等待者
```

**源站只看到 1 个请求。**

> **这个模式你在 Go 里见过**:`golang.org/x/sync/singleflight` 做的正是同一件事——**把并发的相同请求合并成一次实际调用**。做报价缓存、做 RPC 结果缓存时,这是防止缓存击穿的标准工具:
>
> ```go
> var g singleflight.Group
> // 一万个 goroutine 并发调用,底层只会真正执行一次 fetchPrice
> v, err, _ := g.Do("ETH/USDC", func() (any, error) {
>     return fetchPrice("ETH/USDC")
> })
> ```

## 缓存键与命中率:CDN 调优的核心

**CDN 的效果好不好,几乎全看缓存命中率。** 而命中率的关键,在于**缓存键(cache key)**怎么定。

### 缓存键决定了"什么算同一份内容"

边缘节点用缓存键在自己的存储里查找。默认的键通常是:

```
缓存键 = 协议 + 主机名 + 路径 + 查询字符串
        https://example.com/img/logo.png?v=2
```

**问题出在查询字符串上。** 如果 URL 里带了对内容毫无影响的参数:

```
/img/logo.png?utm_source=weibo      → 缓存条目 1
/img/logo.png?utm_source=wechat     → 缓存条目 2
/img/logo.png?from=app&t=1692000001 → 缓存条目 3
```

同一张图被存成了成千上万份,会导致命中率暴跌,回源量暴涨。

**解法:配置 CDN 忽略无关的查询参数**(或者只保留白名单里的参数参与缓存键)。这是 CDN 调优里**收益最大、最容易被忽略**的一项。

### Vary:另一个命中率杀手

`Vary` 响应头告诉缓存"这个响应会随某些请求头变化":

```
Vary: Accept-Encoding      ← 合理,gzip 和非 gzip 要分开存
Vary: User-Agent           ← ⚠️ 灾难!UA 有成千上万种,等于禁用缓存
Vary: Cookie               ← ⚠️ 同样灾难,每个用户一份
```

**`Vary: User-Agent` 会让缓存条目数量爆炸**,基本等于关掉 CDN。需要按设备返回不同内容时,更好的做法是**用不同的 URL**,或者让 CDN 按"设备类型"(而非完整 UA)分组。

### 静态与动态:分开处理

```
静态资源(图片、CSS、JS、字体、视频)
  → 内容不变,可以长期缓存
  → Cache-Control: max-age=31536000, immutable
  → 靠【文件名带哈希】来更新:app.a1b2c3.js

动态内容(API 响应、个性化页面)
  → 每个用户不同,不能缓存
  → Cache-Control: no-store 或 private
  → 但可以用【动态加速】
```

**"文件名带哈希 + 永久缓存"是现代前端的标准做法**,值得理解它为什么优雅:

- 内容没变 → 文件名没变 → **永久命中缓存,零请求**
- 内容变了 → 文件名变了(新哈希)→ **相当于一个全新的 URL,必然回源**

**它把"缓存失效"这个难题,转化成了"改名字"**

### 刷新与预热:两个必备操作

- **刷新(Purge)**:内容更新后,主动通知 CDN 删除旧缓存。**注意生效需要时间**(要通知全球所有节点),而且频繁刷新会降低命中率。
- **预热(Prefetch)**:大流量活动前,**主动把内容推到各边缘节点**,避免开始瞬间的回源风暴。

**大促、新版本发布前做预热,是运维的标准动作。**

## CDN 不只送静态文件

现代 CDN 早已超出"缓存静态资源"的范畴。

### 动态加速:内容不能缓存,路径可以优化

API 响应每个用户都不同,缓存不了。但 CDN 仍能加速,**靠的是优化传输路径**:

- **就近接入 + TLS 卸载**:用户和边缘节点完成 TCP + TLS 握手(**只需 20ms 而不是 200ms**),边缘节点再和源站通信。**握手的往返被大幅缩短,这是动态加速最主要的收益来源。**
- **长连接复用**:边缘节点到源站维持热连接池,省掉握手和慢启动。
- **优化的骨干链路**:CDN 厂商的专线通常比公网路由更优,绕开拥塞节点。

**理解这一点很重要:即使 0% 缓存命中,CDN 对跨境 API 仍然有明显加速效果。** 很多人以为"我的接口都是动态的,用不上 CDN",这是个误解。

### 边缘计算

```
用户 ──▶ 边缘节点【执行你的代码】──▶ 直接返回
                    │
                    └─ 需要时才回源
```

把代码跑在边缘节点上,可以用作:A/B 测试分流、请求改写、鉴权、简单 API、地理位置个性化。

**核心价值是"在离用户 20ms 的地方做决策",而不是绕到 200ms 外的源站。** 这是"把计算搬到数据附近"这个思想在网络层的体现。

## 从 Go 的视角看

### 服务端:给 CDN 发正确的缓存指令

CDN 的行为由**你的响应头**驱动,写对它们是源站的责任:

```go
func staticHandler(w http.ResponseWriter, r *http.Request) {
    // 文件名已带哈希 → 永久缓存,immutable 让浏览器连"重新验证"都不做
    w.Header().Set("Cache-Control", "public, max-age=31536000, immutable")
    w.Header().Set("Vary", "Accept-Encoding") // 只按压缩方式区分,别乱加
    http.ServeFile(w, r, path)
}

func apiHandler(w http.ResponseWriter, r *http.Request) {
    // 用户相关数据:CDN 绝不能缓存
    w.Header().Set("Cache-Control", "private, no-store")
    json.NewEncoder(w).Encode(data)
}

func publicDataHandler(w http.ResponseWriter, r *http.Request) {
    // 公共数据(如全网 gas price):可以短时缓存
    // s-maxage 只对【共享缓存/CDN】生效,max-age 对浏览器生效
    w.Header().Set("Cache-Control", "public, max-age=10, s-maxage=60")
}
```

**`s-maxage` 是个很实用但常被忽略的指令**:它让你能**分别控制浏览器和 CDN 的缓存时长**。上面这个配置的含义是:浏览器缓存 10 秒(用户刷新能较快看到新数据),CDN 缓存 60 秒(源站压力降到 1/60)。

**一个必须避免的事故:给带 `Set-Cookie` 或用户数据的响应设了 `public`。** 后果是 **CDN 把 A 用户的数据缓存下来,发给了 B 用户**——真实发生过的严重数据泄露。**凡是响应内容与用户身份相关,一律 `private, no-store`。**

### 拿到真实客户端 IP

**用了 CDN 之后,`r.RemoteAddr` 是 CDN 节点的 IP,不是用户的。** 限流、风控、地理判断全会失效。

```go
func realIP(r *http.Request) string {
    // CDN 厂商的专用头(最可信,如果你用的是这家)
    if ip := r.Header.Get("CF-Connecting-IP"); ip != "" {
        return ip
    }
    // 通用:X-Forwarded-For 是逗号分隔的链,最左边是原始客户端
    if xff := r.Header.Get("X-Forwarded-For"); xff != "" {
        return strings.TrimSpace(strings.Split(xff, ",")[0])
    }
    host, _, _ := net.SplitHostPort(r.RemoteAddr)
    return host
}
```

**⚠️ 安全提醒:`X-Forwarded-For` 是可以被客户端伪造的。** 攻击者可以随便填一个 IP 来绕过你的限流或 IP 封禁。

**正确做法有两条:**
1. **只信任来自已知 CDN 节点的请求里的这个头**(校验 `r.RemoteAddr` 是否在 CDN 的 IP 段内)。
2. **优先用 CDN 的专用头**(如 Cloudflare 的 `CF-Connecting-IP`),因为 CDN 会覆盖它,客户端伪造无效。

**如果你基于 IP 做限流或封禁,这一步做错等于没做。**

### 源站保护

CDN 隐藏了源站 IP,但**如果攻击者通过其他途径找到了源站真实 IP**(历史 DNS 记录、SSL 证书透明度日志、邮件头等),就能绕过 CDN 直接打你。

所以要在源站做一层防护:

```go
// 只接受来自 CDN 的请求 —— 用中间件实现([Go工程/05] 讲的模式)
func onlyFromCDN(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        host, _, _ := net.SplitHostPort(r.RemoteAddr)
        if !cdnIPRanges.Contains(net.ParseIP(host)) {
            http.Error(w, "forbidden", http.StatusForbidden)
            return
        }
        next.ServeHTTP(w, r)
    })
}
```

更彻底的做法是用 **mTLS**:CDN 用客户端证书连源站,**源站只接受持有该证书的连接**。Cloudflare 的 "Authenticated Origin Pulls" 就是这个。**这比 IP 白名单更可靠**,因为 IP 段会变而证书不会。
