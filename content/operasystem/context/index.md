## Summary

上一篇里,经理为了让每桌客人都能快点吃上第一口,让厨师在几张单子之间轮流做。当时顺口提了一句"换锅要花工夫",没有细说。

饭馆里有个厨师长,干了二十年,对这件事体会最深。他说过一句话:**新来的厨师以为换一道菜,就是把手上的进度记一下、把下一道的小票拿过来;其实那只是看得见的一小半,真正耽误工夫的,是换完以后好一阵子手都不顺。**

这一篇跟着厨师长,把一次换菜的工夫一项项拆开算。算清楚之后,很多看起来反直觉的现象就都说得通了:为什么厨师请多了出菜反而更慢,为什么学徒能多到几十万个,为什么灶台全都在开着火、出菜量却上不去。

---

## 看得见的工夫:记进度、看小票、走流程

厨师正在做红烧肉,经理过来说:先去做那份草莓蛋糕。

厨师要做的第一件事,是把红烧肉做到哪了记下来:"已经炒了糖色,肉还没下锅,火开在中档。"然后拿起蛋糕的小票,看上次做到哪了:"奶油打发到一半,还没加糖。"这样以后回来做红烧肉,才不会把糖色再炒一遍。

计算机里,这就是保存和恢复**上下文**。所谓上下文,就是一个线程接着往下跑所需要的全部状态,最主要的是 CPU 里的那些**寄存器**,也就是 CPU 手边几十个存放"正在处理的数"的小格子:下一条要执行哪条指令(程序计数器)、栈顶在哪(栈指针)、正在计算的各种中间值。切换时,把当前线程的这些值存到内存里它的记录中,再把下一个线程上次存下的值装回寄存器。

如果换的是厨师,也就是两个线程之间换,还要多走一道流程:经理要登记、更新排班表、决定下一个是谁。这就是之前说的"进内核":从程序自己的运行模式切换进内核的特权模式,内核更新它的调度记录,再切回来。

这些看得见的工夫加起来,一次线程切换大约 **1~3 微秒**。听起来很少,但这只是账单的一小部分。

## 看不见的大头:手边的料全是上一道菜的

### 料台上摆的是红烧肉的料

厨师走到蛋糕那边,准备开工,伸手一摸,料台上摆的全是红烧肉的东西:酱油、冰糖、八角、葱段。蛋糕要的奶油、草莓、低筋面粉,一样都不在手边。

于是他得一样样去拿:先看灶台边的小架子上有没有,没有就去厨房角落的冷藏柜,再没有就得穿过整个后厨,去大冰箱里翻。每样东西都要跑一趟。等料台上终于摆满了蛋糕的料,手感和节奏也慢慢找回来,已经过去了好一阵子。

更要命的是,**料台上的东西没法"存起来带走"**。小票可以写下来揣进兜里,但料台就那么大,换了蛋糕的料,红烧肉的料就被挪走了。等会儿回去做红烧肉,又得一样样拿回来。

计算机里的"料台",就是 CPU 的**缓存**。CPU 直接从内存里取数据太慢,所以在芯片上放了几层又小又快的存储,把最近用到的数据留在手边。一个线程跑了一会儿,它常用的数据就都在缓存里了;换成另一个线程,缓存里装的还是上一个线程的数据,新线程要的东西大多不在,只能一样样从更慢的地方取。

### 料放在不同地方,差距有多大

如果把 CPU 从各层取一个数据的时间,按"从手里拿一样东西用 1 秒"来换算,差距是这样的:

| 计算机里 | 实际耗时 | 饭馆里 | 换算成饭馆时间 |
|---|---|---|---|
| 寄存器 | 约 0.3 纳秒 | 手里正拿着 | 1 秒 |
| L1 缓存 | 约 1 纳秒 | 料台上 | 3 秒 |
| L2 缓存 | 约 4 纳秒 | 灶台边的小架子 | 13 秒 |
| L3 缓存 | 约 15 纳秒 | 厨房角落的冷藏柜 | 50 秒 |
| 内存 | 约 80~100 纳秒 | 后厨的大冰箱 | 5 分钟左右 |

从料台上拿只要 3 秒,去大冰箱要 5 分钟,差了一百倍。

算一笔极端的账:一个线程要用的数据有 256KB,正好装满一个 L2 缓存。CPU 从内存搬数据到缓存,每次搬 64 字节,叫一个**缓存行**。换回来以后,要把这 256KB 全部重新搬进来:

```
256KB ÷ 64 字节 = 4096 次去大冰箱
4096 × 80 纳秒 ≈ 328 微秒
```

比那 1~3 微秒的"记进度、看小票"贵了一百多倍。实际情况可能没这么夸张,数据是边用边取的,L3 里也可能还留着一部分,但**间接成本远大于直接成本**这个结论是站得住的。工程上常说的量级是:**一次线程切换,算上缓存的影响,总成本大约几微秒到几十微秒**,相当于白白少执行了几千到几万条指令。

除了料台,还有一样东西也会"凉掉":厨师做一道菜做顺了,手上有节奏,下一步要干什么不用想。CPU 里也有类似的东西,叫**分支预测器**,它记着程序过去在每个"如果……就……"的地方往哪边走,提前猜着往下执行。换了线程,它记的是别人的习惯,要猜错好一阵才能重新猜准。

## 跨店换菜:储物柜的编号全不对了

前面说的是同一个厨房里换菜。如果经理让厨师去另一家分店做菜,也就是进程之间的切换,还有一笔额外的账。

每家分店的储物柜都从 1 号开始编,同一个编号在两家店指的是完全不同的柜子。每家店都有一本厚厚的对照表,写着"几号柜实际在仓库哪个位置"。厨师在一家店干久了,会把最常用的几个记在脑子里:"3 号柜在冰箱左边,17 号柜在灶台底下",不用每次都去翻对照表。

一换到另一家分店,脑子里记的这些全部作废。"3 号柜"在这里是另一个位置了,每找一样东西都得重新翻对照表,翻一次还得一层层查目录,特别慢。

计算机里,那本对照表叫**页表**,负责把程序看到的虚拟地址翻译成真实的物理内存地址;厨师脑子里记住的那几条,是 CPU 里专门缓存翻译结果的一个小硬件,叫 **TLB**。同一个进程里的线程共用一套地址,切换时 TLB 继续有效;换到另一个进程,地址的含义全变了,TLB 里的记录就用不上了。在 x86-64 上,TLB 没记住时,要查四层页表,最多要多访问四次内存。

**这就是进程切换比线程切换贵的主要原因**,不是多保存了几个结构体,而是脑子里的地址记忆全废了。

现代 CPU 有一个缓解办法,叫 **PCID**:厨师在脑子里给每条记忆标上"这是哪家店的",换店时不用全部忘掉,只是暂时不用别家店的记录,回到原来那家店还能接着用。这让进程切换便宜了不少,但仍然比线程切换贵。

## 三种换法放在一起比

把学徒换人(协程切换)、同一个厨房里换菜(线程切换)、跨店换菜(进程切换)放在一起:

| | 学徒换人(协程) | 同厨房换菜(线程) | 跨店换菜(进程) |
|---|---|---|---|
| 要不要经理走流程(进内核) | 不用 | 要 | 要 |
| 要记多少进度(保存寄存器) | 几个 | 全部 | 全部 |
| 换不换储物柜对照表(页表) | 不换 | 不换 | 换 |
| 脑子里的地址记忆(TLB) | 留着 | 留着 | 作废(PCID 可缓解) |
| 料台上的料(CPU 缓存) | 大多还能用 | 部分要重新拿 | 大量要重新拿 |
| 大致成本 | 约 100~200 纳秒 | 约几微秒 | 约几微秒到几十微秒 |

两件事最该记住。协程快,是因为它把前三行全跳过了,而且多个学徒在同一个灶台上轮流干活,用的料往往有不少是重合的,料台不会全凉。进程比线程贵,主要贵在 TLB 那一行。

## 什么时候会换菜

换菜有两种起因,区分开来很有用。

**自己让出来的**:手上这道菜要等炖锅、等烤箱、等别的厨师用完油炸锅,厨师主动去做别的。计算机里叫**自愿切换**:线程在等磁盘、等网络、等锁、主动 sleep。

**被叫走的**:菜还没做完,经理过来说你的时间到了,或者来了一张更急的单子,厨师只能放下手上的去做别的。计算机里叫**非自愿切换**:时间片用完,或者被更该运行的线程抢占。

在 Linux 上,这两种切换能分别数出来:

```bash
pidstat -w -p <进程号> 1
# cswch/s   每秒自愿切换次数
# nvcswch/s 每秒非自愿切换次数
```

| 现象 | 说明 | 怎么办 |
|---|---|---|
| 自愿切换多 | 经常在等 IO 或等锁 | 网络服务这样很正常;远超预期时查锁争抢 |
| 非自愿切换多 | 想上灶的线程比灶台多,大家在抢 CPU | 减少并发,或者加机器 |
| 两者都多 | 系统过载 | 先减并发,再判断要不要扩容 |

其中最有用的一条判断是:**非自愿切换很多,CPU 却没有用满,几乎一定是线程开多了,减少并发反而会更快。** :厨师们在不停地被叫走、换菜、重新拿料,时间都花在了换来换去上,而不是炒菜上。

## 少换锅的五个办法

厨师长总结了五条让厨房少折腾的办法,在计算机里一一对应。

**一、人别请太多。** 灶台就八口,请二十个厨师抢着用,只会互相打断。纯计算的任务,并发数接近 CPU 核数就够了;要等网络、等磁盘的任务大部分时间不占灶台,可以多开。用一个固定大小的工作池把并发数管住,比来一个任务开一个线程要稳。

**二、攒一批再做。** 十桌都点了炒青菜,一锅炒十份,比换十次锅、每次炒一份快得多。换锅的成本是固定的,一次换锅干的活越多,摊到每份上的成本就越少。计算机里这个思路随处可见:写文件时先攒在缓冲区里,攒够一批再交给内核;TCP 的 Nagle 算法攒够一个满包再发;数据库批量插入、日志批量刷盘。**用批量摊薄固定开销**,是性能优化里最通用的手法之一。

**三、少抢公用的工具。** 厨房只有一口油炸锅,好几个厨师都要用,抢不到的只能停下来去做别的,等锅空了再回来,每抢一次就多换一次菜。计算机里,拿不到锁的线程会被挂起,锁释放时再被唤醒,一来一回就是两次切换。所以要么多备几口锅(把一把大锁拆成按 key 分片的多把小锁),要么让每个厨师用自己的料、最后再汇总(每个线程处理自己那份数据,不共享),要么用不需要等待的原子操作。

**四、固定灶台。** 一道菜一直在同一口灶上做,锅一直是热的,料一直在手边。对延迟特别敏感的程序,可以把关键线程钉在固定的 CPU 核上(`taskset -c 2,3 ./程序`),避免被挪来挪去导致缓存重新加载。代价是经理没法再灵活调配,所以只在测出确实是迁移造成的问题时才这么做。

**五、用学徒代替厨师。** 学徒换人不经过经理,只记几个关键进度,这就是协程。Go 的 goroutine 走的就是这条路。

## 学徒也不是免费的

协程便宜,但不是零成本,有两个容易忽略的地方。

**大扫除时每个小凳子都要查一遍。** 饭馆每晚大扫除,清洁工要检查每个学徒的小凳子下面有没有还在用的东西,确认没用的才能扔。学徒越多,大扫除越慢。Go 的垃圾回收也是这样:每个 goroutine 的栈里都可能引用着堆上的对象,垃圾回收时要把所有 goroutine 的栈都扫一遍。十万个 goroutine 就是十万个栈要扫。所以 goroutine 泄漏(开了却永远不结束)是双重伤害:既占内存,又拖慢每一轮垃圾回收。

**只切一根葱的活,别专门派个学徒。** 派一个学徒去做事,有安排、交接、回报的成本,大约一两百纳秒。如果这件事本身只要几纳秒,比如把两个数加起来,那安排的成本比干活本身还高。一百万个数求和,开一百万个 goroutine 各加一个,会比一个循环直接加完慢得多;正确的做法是按核数把数据切成几大块,每个 goroutine 处理一块。一个粗略的判断标准是:**单个任务耗时不到 1 微秒的,就别为它单独开 goroutine**,要么直接做,要么攒成批再分。

## 把饭馆翻译回计算机

**上下文里到底有什么。** 以 x86-64 为例,线程切换时要保存的有:16 个通用寄存器、程序计数器、栈指针、标志寄存器,以及浮点和向量寄存器。最后这部分可能很大,支持 AVX-512 的 CPU 上,向量寄存器加起来超过 2KB。Linux 用 `XSAVES` 这类指令只保存真正被改动过的部分来减少开销。早年 Linux 还用过一种"用到浮点运算时才恢复"的惰性方案,2018 年因为 LazyFP 安全漏洞被取消了,现在每次切换都会处理。

**为什么要进内核。** 线程由内核调度,切换必须发生在内核里:时钟中断或系统调用让 CPU 进入内核态,内核的调度函数(Linux 里叫 `schedule()`,真正换寄存器和栈的是 `context_switch()`)选出下一个线程,换好寄存器和内核栈,如果是不同进程还要换页表(x86 上是写 `CR3` 寄存器),再返回用户态。

**一个和安全有关的额外开销。** 2018 年的 Meltdown 漏洞之后,Linux 加了一项防护叫 KPTI:用户态和内核态用两套页表,于是每次进出内核都要换一次页表。这让系统调用和切换都变贵了一些,PCID 在这里同样起到了缓解作用。

**常用命令**

```bash
vmstat 1                                          # cs 列:整机每秒切换次数
pidstat -w -p <进程号> 1                          # 某进程的自愿、非自愿切换
perf stat -e context-switches,cpu-migrations ./程序  # 精确统计切换次数和跨核迁移次数
```

## 总结

```
经理让厨师从红烧肉换去做蛋糕
  │
  ├─ 看得见的:记下进度、看下一张小票、经理登记
  │    = 保存恢复寄存器、进出内核,约 1~3 微秒
  │
  ├─ 看不见的大头:料台上全是上一道菜的料,得一样样重新去拿
  │    = CPU 缓存失效,从内存重新加载,比直接成本高一到两个数量级
  │    手感也要重新找 = 分支预测器要重新学
  │
  └─ 跨店换菜:脑子里记的储物柜位置全作废
       = 换页表,TLB 失效;PCID 可以缓解
  ▼
三种换法:学徒换人(协程)< 同厨房换菜(线程)< 跨店换菜(进程)
  ▼
少换锅的五个办法
    人别太多(控制并发)、攒一批再做(批处理)、少抢公用工具(减少锁争抢)、
    固定灶台(绑核)、用学徒(协程)
  ▼
学徒也不是免费的
    大扫除要查每个小凳子(GC 扫描每个 goroutine 的栈)
    只切一根葱的活别专门派人(小于 1 微秒的任务别单独并发)
```

最该记住的几句话:

- **上下文切换的大头不是保存寄存器,而是切换之后缓存失效带来的损失。** 料台上的东西没法存起来带走。
- **进程切换比线程切换贵,主要贵在 TLB 失效。**
- **非自愿切换很多而 CPU 没有用满,说明并发开多了,减少并发反而更快。**
- **批处理是摊薄固定开销最通用的办法。**
- **协程切换便宜,但不是免费的**:太小的任务不值得单独开,泄漏的协程会拖慢垃圾回收。

## 动手练习

以下需要一台 Linux 机器。

1. **看整机的切换次数。** 运行 `vmstat 1`,看 `cs` 列;然后在另一个终端执行一个编译任务或者压测,观察 `cs` 怎么变化。
2. **看一个服务是在等还是在抢。** 对一个正在运行的服务执行 `pidstat -w -p <进程号> 1`,比较 `cswch/s` 和 `nvcswch/s`。
3. **制造一次"开太多"。** 用 `stress-ng --cpu 64 --timeout 20s`(没有就 `apt install stress-ng`)在一台核数少得多的机器上开 64 个计算任务,同时用 `vmstat 1` 和 `pidstat -w 1` 观察非自愿切换飙升。再改成 `--cpu <核数>` 对比。
4. **数一数切换和迁移。** `perf stat -e context-switches,cpu-migrations sleep 5` 和 `perf stat -e context-switches,cpu-migrations stress-ng --cpu 64 --timeout 5s`,对比两者的数字。
5. **查一下你的 CPU 缓存有多大。** `lscpu | grep -i cache`(macOS 用 `sysctl -a | grep cachesize`),对照第 2 节的表,看看料台、小架子、冷藏柜各有多大。
