## Summary

饭馆生意越来越好,你在同一栋楼里开了好几个厨房:川菜厨房、粤菜厨房、面点厨房,还有一个专门做外卖的厨房。每个厨房就是一个进程,各做各的菜。

厨房多了,原来每个厨房墙角那台小冰箱就不够用了。你在楼下改出一间大冷藏室,里面是一排排货架,每个货架分成很多格子,所有厨房的食材都存在这里。郊区还租了一个大冷库,放平时用不上的大宗货。

对应到计算机里:

| 饭馆里 | 计算机里 |
|---|---|
| 楼下的冷藏室,一排排货架上的格子 | 物理内存 |
| 郊区的大冷库 | 磁盘 |
| 每个厨房 | 每个进程 |
| 厨房里的厨师 | 线程 |

问题来了:这么多厨房共用一间冷藏室,谁的食材放在哪个格子里,该怎么管呢?

---

## 没有管理的冷藏室:直接用格子号

最简单的办法是不管:冷藏室的格子从 1 编到 10000,每个厨房自己挑空格子放东西,菜谱里直接写"酱油在 352 号格子"。

早期的计算机就是这么做的:程序直接使用物理内存的真实地址。很快,三个麻烦接连出现。

### 麻烦一:拿错了别人的东西

粤菜厨房的帮工手忙脚乱,菜谱上写的是"去 352 号格子拿蚝油",他看成了 353 号,一伸手拿走了川菜厨房刚备好的一盆毛血旺的料,还顺手把蚝油倒进去了。

川菜厨房的菜就这么被毁了,而且没有任何机制能拦住他:冷藏室里每个格子谁都能伸手。

计算机里,这就是一个程序的数组越界写到了另一个程序的内存上。一个程序的小 bug,可以把别的程序的数据改坏;一个恶意程序,可以随便读走别的程序内存里的密码和密钥。

### 麻烦二:菜谱上写死的格子号

面点厨房的菜谱是去年写的,上面写着"面粉放在 1200~1250 号格子"。今年开了外卖厨房,恰好占了 1220 号。面点厨房一开工,两边就抢起格子来。

想解决,要么每次开工前把菜谱上所有的格子号改一遍,要么所有厨房事先开会,把格子分好、谁也不许越界。厨房一多,这两个办法都不现实。

计算机里,程序编译好之后,里面的指令写死了要访问哪些地址。如果用的是物理地址,程序在编译时就得决定自己占哪一块内存,可运行时那一块是不是空的,谁也说不准。

### 麻烦三:空格子不少,就是凑不出连续的一大片

冷藏室用久了,空格子东一个西一个。今天来了一条三米长的金枪鱼,需要连续 20 个格子才能放下。冷藏室里空格子加起来有 50 个,但没有一处是连着 20 个的,鱼放不进去。

更麻烦的是,接了一个婚宴大单,食材加起来比整个冷藏室还大,根本没法接。

计算机里,前一种情况叫**外部碎片**:空闲内存总量够,但不连续,大程序分配不到一整块。后一种是程序需要的内存超过了物理内存,直接没法运行。

## 经理的办法:每个厨房一套自己的编号

经理(操作系统内核)想了一个办法,三个麻烦一次解决。

**第一步:每个厨房都有一套自己的储物柜编号,都从 1 号编起。** 川菜厨房的菜谱写"酱油放 7 号柜",粤菜厨房的菜谱也写"蚝油放 7 号柜",两个 7 号柜互不相干。每个厨房都觉得自己有一整排从 1 号开始、连续的、很长很长的柜子,整栋楼只有自己一家在用。

**第二步:经理给每个厨房都做一张对照表**,写明"这个厨房的几号柜,实际是冷藏室里的哪个格子":

```
川菜厨房的对照表              粤菜厨房的对照表
  7 号柜 → 冷藏室 352 号格       7 号柜 → 冷藏室 4810 号格
  8 号柜 → 冷藏室  19 号格       8 号柜 → 冷藏室 2203 号格
  9 号柜 → (还没分配)            9 号柜 → 冷藏室  357 号格
```

**第三步:冷藏室门口站一个管理员。** 厨师来取东西,只报自己厨房的柜号,"川菜厨房,要 7 号柜"。管理员翻川菜厨房的对照表,查到是 352 号格,替他去拿。厨师从头到尾不知道、也不需要知道真实的格子在哪。

计算机里的对应是这样的:

- 每个厨房自己的柜号,叫**虚拟地址**。每个进程看到的是一整套专属于它的、从 0 开始的地址,叫这个进程的**虚拟地址空间**。
- 经理做的对照表,叫**页表**,由操作系统内核为每个进程维护一份。
- 门口按表翻译的管理员,是 CPU 里的一个硬件部件,叫 **MMU**(内存管理单元)。程序每访问一次内存,MMU 都要把虚拟地址翻译成物理地址。

再看前面三个麻烦:

**麻烦一没了。** 粤菜厨房的帮工报错了柜号,管理员也只会在粤菜厨房自己的对照表里找,怎么也查不到川菜厨房的格子。想越界都越不过去,这就是进程之间的**隔离**。

**麻烦二没了。** 每个厨房的菜谱都可以放心地写"7 号柜",至于 7 号柜实际在哪个格子,开工时由经理安排。程序编译时可以假设自己从固定的地址开始,运行时再由操作系统映射到实际有空的物理内存上。

**麻烦三也没了。** 金枪鱼要 20 个连续的柜子,厨房看到的是连续的 101~120 号柜,但对照表可以把它们分别指向冷藏室里零散的 20 个空格子。在厨房眼里是连续的,实际怎么放无所谓。至于比冷藏室还大的大单,后面会讲到。

这一招的本质是**在中间加了一层翻译**。计算机科学里有句流传很广的话:"计算机科学中的任何问题,都可以通过增加一个间接层来解决。

### 按一整格登记,不按一瓶酱油登记

对照表还有一个细节。如果每瓶酱油、每根葱都要在表上单独登记一行,这张表会比冷藏室里的东西还多。

所以经理的规矩是:**按整格登记。** 一个格子固定大小,对照表只记"几号柜对应几号格",至于酱油在这一格里的左边还是右边,柜子里和格子里的相对位置是一样的,不用翻译。

计算机里,这个固定大小的格子叫**页**,通常是 4KB。一个虚拟地址被拆成两段:前一段是"第几页"(页号),要查页表翻译;后一段是"页里的第几个字节"(页内偏移),原样保留。

```
虚拟地址 = [ 虚拟页号 | 页内偏移 ]
               │          │
          查页表翻译    原样保留
               ▼          ▼
物理地址 = [ 物理页号 | 页内偏移 ]

一页 4KB = 2^12 字节,所以页内偏移占地址的最低 12 位
```

## 一个厨房的柜子是怎么分区的

每个厨房的柜子虽然是虚拟的,摆放也有固定的规矩。从 1 号往后数,大致是这样:

```
编号最大的一头
  ┌──────────────────────────────┐
  │ 经理办公室的柜子                │  每个厨房的表上都有这一段,但厨师打不开
  ├──────────────────────────────┤
  │ 厨师手边的临时台面(往小号长)     │  正在做的菜用的东西,做完就清
  │            ↓                 │
  │                              │
  │      一大片还没用的编号         │
  │                              │
  │            ↑                 │
  │ 越堆越多的备料区(往大号长)       │  做菜过程中随时要新放的东西
  ├──────────────────────────────┤
  │ 常备调料区                     │  开业时就备好的,一直都在
  ├──────────────────────────────┤
  │ 菜谱区(只许看,不许改)           │
  ├──────────────────────────────┤
  │ 最前面一小段:故意不发           │  谁要"0 号柜",立刻报警
  └──────────────────────────────┘
编号最小的一头
```

几个讲究:

**备料区和临时台面从两头往中间长。** 备料区从小号往大号用,临时台面从大号往小号用,中间留一大片空着。两边谁需要多少就长多少,不用事先决定各分多少,只有真撞到一起了才算不够用。

**最前面一小段故意不发。** 如果某个厨师拿着一张写着"0 号柜"的单子来取东西,说明单子肯定写错了(没填柜号)。管理员不会随便给他一个格子,而是当场报警,让这个错误立刻暴露出来,而不是拿了一堆不知道是什么的东西回去做菜。

**经理办公室在每个厨房的表上都有一段。** 厨师有时要找经理办事,经理的东西在每个厨房的编号表里都有登记,找经理时就不用换一张表。但这一段对厨师是锁着的,厨师自己伸手去拿,管理员会直接拦下。

把名字换回计算机:菜谱区叫**代码段**,常备调料区是**数据段**(全局变量),备料区是**堆**(程序运行中动态申请的内存),临时台面是**栈**(函数调用和局部变量),中间那一片叫**内存映射区**和空洞,最前面不映射的那一段让**空指针**一访问就崩溃。

## 账上先记一笔,真用的时候才给格子

### 按需分配

新开的外卖厨房报上来:"我们要 10 万个柜子。"

冷藏室一共才 1 万个格子。但经理很清楚,厨房报的数总是往大了报,真正同时在用的往往只有一小部分。所以他的做法是:**在对照表上把 10 万个柜号都登记上,但一个格子都不分。** 每个柜号后面都写着"还没分配"。

等外卖厨房真的往 35 号柜里放了第一包东西,管理员发现 35 号柜还没有对应的格子,就去找经理。经理这时才从冷藏室挑一个空格子,填进对照表,东西放进去。没用到的柜号,永远不占冷藏室的地方。

计算机里这叫**按需分配**:程序申请一大块内存,操作系统只是在虚拟地址空间里划出这段范围,不分配任何物理内存;程序第一次读写其中某一页时,才真正分配一个物理页。中间"管理员发现没分配、去找经理"这一步,叫**缺页**。

### 报了多少和实际占了多少

这就解释了一个经常吓到人的现象。你用 `top` 看一个进程,会看到两个内存数字:

```
VIRT(也叫 VSZ):这个厨房在对照表上登记了多少柜号     → 报了多少
RES (也叫 RSS):这些柜号里有多少真的对应了冷藏室的格子 → 实际占了多少
```

VIRT 常常大得吓人,几十 GB、几百 GB 都有,但它只是"登记过的编号",几乎不代表什么;**真正占物理内存的是 RES/RSS,看内存用了多少要看这个。** 

### 超额批准

既然登记柜号不占格子,经理干脆放开了批:所有厨房登记的柜号加起来,可以远远超过冷藏室的格子数。他赌的是大家不会同时把登记的柜子都用满。

大多数时候这个赌都赢了。万一输了,所有厨房同时把柜子用满,冷藏室真的一个空格子都没有了,经理也有后招:先把一些最近没人碰的东西挪去郊区冷库腾地方,实在腾不出来,就只能关掉一个厨房,把它的格子收回来。这两个后招就是**换页**和 **OOM Killer**。

计算机里这叫**超额分配**(overcommit),Linux 默认就是这么做的。

## 几个厨房共用一个格子

既然每个厨房都有自己的对照表,那么完全可以让两张表上的柜号,指向冷藏室里的**同一个格子**。这带来几个很实用的好处。

**共用一本手册。** 所有厨房都要查同一本《基础调味手册》。没必要每个厨房都在冷藏室放一本,放一本就够了,各厨房对照表上的"手册柜"都指向这一个格子,并且标明"只许看,不许改"。计算机里,几百个进程都用到同一个系统库(比如 C 标准库 libc),物理内存里只需要放一份代码,各进程的页表都指向它。这叫**共享库**。

**开分店时先不搬东西。**新开一家分店是先把现有的原样复制一家。如果真把冷藏室里那个厨房的几千格东西都复制一份,太慢了。经理的做法是先让新厨房的对照表也指向同样的格子,都标成"只许看";谁要改哪一格,才单独给他复制一格。这叫**写时复制**。

**把冷库里的一整箱货直接登记成柜号。** 有些菜要用郊区冷库里一大箱干货。经理可以直接在厨房的对照表上登记一段柜号,对应这一整箱货:厨师取哪一包,管理员才去冷库运哪一包回来;用不到的那些就一直留在冷库。计算机里这叫 **mmap**(内存映射文件):把一个文件映射到虚拟地址空间里,之后读这段内存就等于读文件,访问到哪一页才从磁盘读哪一页,多个进程映射同一个文件还能共用同一份物理页。

## 把饭馆翻译回计算机

故事讲完,把底层细节补上。

**两个进程打印出同一个地址。** 写两个最简单的程序,各自打印一个全局变量的地址,同时运行,打出来的地址往往一模一样。它们明明是两个进程、各有各的变量,却住在"同一个地址"上。原因就是:打印出来的是虚拟地址,同一个虚拟地址在两个进程的页表里指向不同的物理页。

**真实的地址空间有多大。** 64 位的 x86-64 CPU 目前通常只用 48 位虚拟地址(较新的 CPU 支持 57 位,需要内核开启),也就是 2^48 = 256TB。Linux 把它一分为二:低的一半(`0x0000_0000_0000_0000` 到 `0x0000_7FFF_FFFF_FFFF`,128TB)给进程自己用,高的一半(从 `0xFFFF_8000_0000_0000` 开始)是内核空间,中间一大段是 CPU 规定不能用的地址。一个进程的虚拟地址空间比任何一台机器的物理内存都大得多,这正是按需分配能成立的前提:虚拟地址很便宜,可以大方地分。

**内核空间为什么在每个进程里都有。** 这样进程调用系统调用、进入内核时,不用切换页表。2018 年 Meltdown 漏洞曝光后,为了防止用户程序借 CPU 的漏洞偷看内核内存,Linux 引入了 KPTI,把内核页表和用户页表拆开,系统调用的开销因此变大了一些。这是一次安全和性能之间的真实交换。

**翻译必须由硬件做。** 程序每执行几条指令就要访问一次内存,每次都要翻译。如果每次都要停下来让内核用软件查表,程序会慢几百倍。所以翻译交给 CPU 里的 MMU 硬件,内核只负责维护页表。

**亲眼看看一个进程的地址空间。** Linux 上 `cat /proc/<进程号>/maps` 会列出这个进程所有已登记的虚拟地址段,每行是一段地址范围、权限(`r` 读、`w` 写、`x` 执行、`p` 私有、`s` 共享)和用途。你会看到程序文件本身的几段(代码段是 `r-xp`,不可写)、`[heap]`、各个共享库、`[stack]`。`ps -o pid,vsz,rss,comm -p <进程号>` 可以同时看到 VSZ 和 RSS,单位是 KB。

**超额分配的开关。** `/proc/sys/vm/overcommit_memory` 有三个值:`0` 是默认的启发式超额分配(明显离谱的申请会被拒绝,其余都批);`1` 是无条件批准;`2` 是严格模式,总登记量不能超过"swap + 物理内存 × 一个比例"。

## 总结

```
所有厨房共用一间冷藏室,直接报格子号
  │ 麻烦:拿错别人的东西;菜谱上的格子号写死;空格子凑不出连续一大片
  ▼
经理的办法:每个厨房一套从 1 号编起的柜号 + 一张对照表 + 门口的管理员
  │ = 虚拟地址 + 页表 + MMU
  │ 按整格登记(页,4KB),格子里的相对位置不翻译
  ▼
每个厨房的柜子有固定分区
  │ 菜谱区 / 常备调料 / 备料区往上长 / 临时台面往下长 / 0 号柜故意不发
  │ = 代码段 / 数据段 / 堆 / 栈 / 空指针保护
  ▼
账上先登记,真用时才给格子
  │ = 按需分配;VIRT 是登记了多少,RSS 是实际占了多少
  │ 经理超额批准,赌大家不会同时用满(overcommit)
  ▼
几张对照表指向同一个格子
    = 共享库、写时复制、mmap
```

最该记住的几句话:

- **每个进程看到的都是自己专属的虚拟地址,由 MMU 按页表翻译成物理地址。** 这一层翻译带来了隔离、固定的地址布局和不怕碎片。
- **翻译按页进行,页通常是 4KB**:页号查表翻译,页内偏移原样保留。
- **申请内存只是登记地址,真正访问时才分配物理页。** 所以看内存占用要看 RSS,不要看 VIRT。
- **多个进程的虚拟页可以指向同一个物理页**,共享库、写时复制、mmap 都建立在这一点上。

## 动手练习

`/proc` 相关的需要 Linux 机器。

1. **看两个数字的差距。** 在 Linux 服务器上执行 `ps -eo pid,vsz,rss,comm --sort=-vsz | head`,看看 VSZ 最大的几个进程,它们的 RSS 和 VSZ 差了多少倍。如果有 Go 写的服务,它的 VSZ 通常格外大。
2. **看一个进程的柜子分区。** `cat /proc/self/maps`(`self` 指的就是 `cat` 自己这个进程),从上往下找到:`cat` 程序本身的几段(注意代码段的权限是 `r-xp`)、`[heap]`、`libc` 的几段、`[stack]`。
3. **看共享库只放了一份。** 找两个不同的进程,分别 `grep libc /proc/<进程号>/maps`,两边都映射了同一个 libc 文件。再用 `cat /proc/<进程号>/smaps_rollup` 看 `Rss` 和 `Pss`:Pss 把共享的页按共享进程数平摊,通常比 Rss 小,差出来的部分就是和别人共用的。
4. **看超额分配的设置。** `cat /proc/sys/vm/overcommit_memory` 看当前是哪种模式;`grep -i commit /proc/meminfo` 里的 `Committed_AS` 是全系统登记的总量,`CommitLimit` 是严格模式下的上限,对比一下实际物理内存(`MemTotal`)。
