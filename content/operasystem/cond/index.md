## Summary

互斥锁解决的问题是:一样东西,同一时刻只能一个线程用。但它有两类需求锁管不了:
一是**等某件事发生**,就像传菜员每半分钟跑去问"菜好了没",轮询只会空耗 CPU,要的是"条件满足了再叫醒我"
二是**限制同时做某件事的数量**,资源有 4 份,锁一次只放一个线程,不加限制第五个又没资源。
操作系统为此准备了两个经典工具:信号量和条件变量。

---

## 信号量

### 计数器加两个动作

**信号量**是**一个计数器(还剩几个可用名额),加上"取一个"和"还一个"两个动作**:

```
信号量 = N             一开始有 N 个名额

取(P):如果还有名额,取一个,计数减一;一个都没有,就睡下等
还(V):还回一个,计数加一;如果有人在等,叫醒其中一个
```

就像灶台旁挂 4 块牌子,取一块才能上灶,用完挂回。信号量由 Dijkstra 在 1965 年提出,是最早的并发工具之一;P 和 V 来自荷兰语(Dijkstra 是荷兰人),现在的接口一般叫 `acquire`/`release` 或 `wait`/`post`。P 和 V 本身必须是原子的,否则又回到计数对不上的老问题,操作系统内部用一把锁加一个等待队列实现它们。

名额**不记名**:信号量只关心"还剩几个",不关心"是谁取走的"。这既是它最大的本事,也是它最大的麻烦。

### 初值决定含义

初值为 1 时,信号量就成了一把互斥锁,叫**二元信号量**。区别在于:互斥锁谁加谁解,有"所有者";信号量没有,线程甲 P 掉的名额可以由乙 V 回去。

初值为 0 可以表达先后顺序,要求甲完成某一步后乙才能接着做:

```
信号量 = 0

线程甲:完成第一步 → V
线程乙:P(没有名额,就等着)→ 取到了 → 做第二步
```

乙先到就阻塞在 P 上,甲 V 后乙被唤醒,第二步一定在第一步之后。这里的计数代表**"一件事已经发生了"**,靠的正是"不记名":V 由甲做、P 由乙做,互斥锁做不到。汇总:

```
初值 = N  → 最多 N 个线程同时用(限流)
初值 = 1  → 同一时刻只能一个(互斥)
初值 = 0  → 等某件事发生之后才能继续(同步)
```

### 太灵活,容易用错

- **忘了 V**:名额永久少一个;全忘光了,所有线程永远在等。
- **多 V 了一次**:名额凭空多一个,同时进入的线程超过上限。
- **看不出它在管什么**:P 和 V 可以在代码两头、由不同线程执行,光看一处调用猜不出它在协调什么。

所以现代语言更愿意提供用途单一的工具(互斥锁、等待组、channel):通用工具表达力强,专用工具不容易用错。

### 实现

一个整数加一个等待队列,P 和 V 都在一把内部锁的保护下完成:

```
P(s):                           V(s):
  锁住 s                          锁住 s
  while s.值 == 0:                s.值 += 1
      把自己放进 s.等待队列        如果 s.等待队列不空:
      释放锁并睡眠(原子地)            唤醒其中一个
      醒来后重新锁住 s             解锁 s
  s.值 -= 1
  解锁 s
```

Linux 用户态的 POSIX 信号量(`sem_wait`/`sem_post`)和互斥锁一样基于 futex:没有线程等待时,P 和 V 都只是一条原子指令,不进内核。

## 生产者-消费者

### 有界缓冲区

生产者往容量为 N(比如 6)的缓冲区放数据,消费者从中取:满了生产者等,空了消费者等,同一时刻只能一个线程操作缓冲区(否则可能写进同一个空位)。这是最经典的并发问题,叫**生产者-消费者问题**(也叫有界缓冲区问题)。

### 三个信号量

```
empty = 6     缓冲区还有几个空位(一开始全空)
full  = 0     缓冲区有几个数据(一开始没有)
mutex = 1     缓冲区本身的互斥

生产者:                          消费者:
  P(empty)  ← 没空位就等            P(full)   ← 没数据就等
  P(mutex)                          P(mutex)
    放入数据                          取出数据
  V(mutex)                          V(mutex)
  V(full)   ← 通知消费者有数据了     V(empty)  ← 通知生产者有空位了
```

`empty` 和 `full` 对称:生产者消耗 `empty`、产生 `full`,消费者反过来,两者之和永远是 6。没数据时消费者阻塞在 `P(full)` 上而不是轮询,生产者一 `V(full)` 它就被唤醒。

### 顺序反过来就会卡死

如果生产者先 `P(mutex)` 再 `P(empty)`:

```
缓冲区已满
生产者:拿到 mutex → P(empty),没有空位,阻塞
         (手里还持有 mutex)
消费者:P(full) 成功 → P(mutex),被生产者持有,也阻塞

生产者等消费者腾出空位,消费者等生产者释放 mutex
两边都在等对方,谁也动不了
```

这就是**死锁**:**持有一样东西不放,又去等另一样东西**。顺序必须先 P 资源(`empty` 或 `full`),再 P `mutex`。

## 条件变量

### 计数器表达不了的等待

有些条件没法用计数器表达:消费者等的不是"缓冲区有数据",而是"我的那几项全到齐了",缓冲区里可能已有 5 项,但都不是它的。这时需要**条件变量**:**先睡下,共享状态变化时被叫醒,再检查是不是自己等的情况。** 它总是和一把锁搭配,锁保护要检查的共享状态,通知方改完状态后发通知:

```
等待(条件变量, 锁):
    ① 交出锁,同时睡下            ← 这两步必须是一步
    ② 被叫醒后,重新拿到锁,再返回

叫一个(Signal):    叫醒一个在等的线程
叫所有(Broadcast): 叫醒所有在等的线程
```

POSIX 里是 `pthread_cond_wait(&cond, &mutex)`,调用时必须已持有 `mutex`,内部原子地释放它并睡眠,被唤醒后重新获取再返回。`pthread_cond_signal` 至少唤醒一个,`pthread_cond_broadcast` 唤醒全部。

### 释放锁和睡眠必须是一步

如果先释放锁、再睡眠,两步之间有空档:

```
等待方:检查 → 不满足 → 释放锁
      ─────────── 危险的空档 ───────────
      通知方:改好状态,发出通知     ← 等待方还没睡下,没收到
      ──────────────────────────────────
等待方:睡下等通知                    ← 可能永远等不到了
```

通知发过且不会再发,等待方就一直睡下去。这叫**丢失唤醒**,特别难查:大部分时候正常,只在特定时机卡住。所以条件变量的"等待"把释放锁和睡眠定义成一个不可分割的动作,这也是它必须和锁绑在一起的原因。

### 被叫醒了,也要再检查

```
错误的写法:                    正确的写法:
  如果 条件不满足:               只要 条件不满足:
      等待                           等待
  使用资源                       使用资源
  (醒一次就认定满足了)          (每次醒来都重新确认)
```

即**等待必须放在 `while` 循环里,而不是 `if` 里**,原因有三:

1. **被别人抢先**:从被通知到重新拿到锁,别的线程可能已改了状态(两个消费者同时被叫醒,先到的取走了唯一的数据)。这是最常见的原因。
2. **叫所有时资源只够一个**:Broadcast 叫醒了所有等待者,资源只有一份。
3. **没人叫也可能醒**:等待可能在没有任何通知时返回,叫**虚假唤醒**。POSIX 明确允许,代码必须容忍。

更底层的原因是唤醒语义。**Hoare 语义**下,被唤醒的线程立刻接管锁和 CPU,醒来时条件一定成立。**Mesa 语义**下,唤醒只是把对方放回就绪队列,发出唤醒的线程继续运行,被唤醒者自己排队抢锁,真正跑起来时条件可能已被改掉。**几乎所有实际系统用 Mesa 语义**,因为实现简单、效率高,代价就是等待必须放在 while 里;"被别人抢先"正是它的直接后果。

**等待返回不代表条件成立,只代表"情况可能变了,再看一眼"。**

### 叫一个,还是叫所有

- 等待者等的是同一件事,且每次只够一个线程处理:**叫一个**就够,省得大家白醒。
- 等的是不同条件(一个等 A,一个等 B):只叫一个可能叫错人,A 满足了却叫醒等 B 的,它检查后继续睡,该醒的还在睡。这时必须**叫所有**,各自判断。

叫所有的代价是一群线程同时醒来抢锁,大部分检查完又睡回去,叫**惊群**,但不会出错。**拿不准的时候,叫所有。**

## 关联

以下以 Go 1.26 为准。Go 的思路是提供几个用途单一的工具,而不是让你直接用信号量和条件变量。

**channel 就是有界缓冲区。** `make(chan T, 6)` 就是容量为 6 的缓冲区,满了 `ch <- v` 阻塞,空了 `<-ch` 阻塞。runtime 里的结构 `hchan`:

```go
type hchan struct {
    qcount   uint           // 缓冲区里现有元素数
    dataqsiz uint           // 缓冲区容量
    buf      unsafe.Pointer // 环形缓冲区
    sendx    uint           // 下一个写入位置
    recvx    uint           // 下一个读取位置
    recvq    waitq          // 等待接收的 goroutine
    sendq    waitq          // 缓冲区满、等待发送的 goroutine
    lock     mutex
    // ……
}
```

**channel = 环形缓冲区 + 一把锁 + 两个等待队列**,正是生产者-消费者的标准解法,做成了语言内置。

**带缓冲的 channel 可以当信号量用。** `sem := make(chan struct{}, 10)`,干活前 `sem <- struct{}{}`(P),干完 `<-sem`(V),就是最多 10 个并发。要支持超时取消或一次取多个名额,用 `golang.org/x/sync/semaphore`。限制对下游接口的并发数用的就是这个,数值看下游能扛多少,别拍脑袋。`errgroup` 的 `SetLimit` 内部也是这个原理。

**`sync.WaitGroup` 是一个倒着数的信号量。** 计数减到 0 时叫醒所有 `Wait` 的 goroutine,是"等某件事发生"的专用版。Go 1.25 起可直接写 `wg.Go(func() { ... })`,自动做好 `Add(1)` 和 `Done()`,避免"`Add` 写在 goroutine 里面"这个老错误。

**`sync.Cond` 很少用,但要能看懂。** 它就是的条件变量,`c.Wait()` 必须放在 `for` 循环里。多数场景用 channel 更清楚;只有需要反复"叫所有"、或条件涉及好几个变量时,`sync.Cond` 才有优势。Go 团队讨论过要不要废弃它,原因就是太容易用错。

**channel 的阻塞就是背压。** 下游慢,缓冲区满,上游发送自动阻塞,整条流水线自然降速,就是有界缓冲区满了生产者得等。

**持锁时不要去等别的资源。** 卡死在真实代码里很常见:拿着锁去连接池取连接,池空了就一直等,而别人要还连接又得先拿到这把锁。先取连接,再加锁。

## 总结

```
轮询"条件满足了没"空耗 CPU → 互斥锁表达不了"等某件事"
  ▼
信号量 = 计数器 + P/V
  │ 初值 N:最多 N 个同时用(限流)
  │ 初值 1:一次一个(互斥,但没有所有者)
  │ 初值 0:等某件事发生(同步)
  │ 代价:太灵活,忘还、多还、看不出在管什么
  ▼
生产者-消费者 / 有界缓冲区
  │ empty + full + mutex,两组对称的计数
  │ 顺序反了 = 持有 mutex 等空位 → 卡死(下一篇的死锁)
  ▼
等复杂条件 = 条件变量(配合一把锁)
  │ 释放锁和睡眠必须一步完成,否则丢失唤醒
  │ 醒来也要再检查(while 不是 if,Mesa 语义)
  │ 等的条件各不相同,就叫所有
```

最该记住的几句话:

- **互斥是"别同时动",同步是"等某件事发生",是两类不同的需求。**
- **信号量是一个计数器加取、还两个动作**,初值不同,含义完全不同;名额不记名,所以能表达先后顺序。
- **生产者-消费者 = 空位计数 + 数据计数 + 一把锁**,一定要先等资源、再拿锁。
- **条件变量用来等一个复杂的条件**,"释放锁并睡眠"必须是原子的。
- **等待返回不代表条件成立,一定要在 while 循环里重新检查。**
