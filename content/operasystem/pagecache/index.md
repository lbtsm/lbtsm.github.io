## Summary

一台跑了几个月的服务器,`free -h` 一看:16GB 内存,`free` 只剩 500MB,`buff/cache` 占了 11GB。常见的反应是"内存泄漏了",或者干脆写个定时任务每小时 `echo 3 > /proc/sys/vm/drop_caches`。另一组常见说法是"零拷贝就是一次拷贝都没有""mmap 一定比 read 快"。这几句话都不对:第一句把**可以随时让出来的缓存**当成了被占死的内存;第二句把"CPU 不再亲自复制"说成了"数据不搬动";第三句忽略了 mmap 自己的缺页和映射成本。

错的根源是同一个:没搞清楚**文件数据在内存里到底放在哪、由谁搬、搬几次**。搞清楚了,一串线上现象都能解释:为什么服务第二次启动快得多、为什么备份一跑业务就变慢、为什么写日志的程序每隔一阵卡几百毫秒、为什么容器明明没泄漏却被报内存快满、为什么 Nginx 和 Kafka 发文件几乎不费 CPU。

继续用饭馆来讲。讲文件系统时说过,经理收了货先放进冰箱的"待入库"区,不马上送仓库;从仓库取来的货也在冰箱里留一份,下次就不用再跑。这台冰箱就是本文的主角**页缓存**。内存和 IO 两条线在这里汇合:页缓存是内存里替磁盘服务的区域,零拷贝让数据在发送路上少复制几次。

## 先搞清楚:文件数据在内存里放在哪

先看量级。磁盘再快,和内存也不是一个世界:

```
内存       约 100 纳秒
NVMe SSD   约 100 微秒    比内存慢约 1000 倍
机械硬盘   约 10 毫秒     比内存慢约 10 万倍
```

所以内核的策略很直接:**拿空闲物理内存缓存文件内容**,单位是一页(x86 上通常 4KB,Apple Silicon 的 macOS 是 16KB),这就是页缓存。程序的 `read`、`write`,默认都不直接碰磁盘,而是碰页缓存:

```
          进程 A                     进程 B
   ┌──────────────────┐      ┌──────────────────┐
   │ 用户缓冲区 buf    │      │ mmap 映射的区域   │
   └────────▲─────────┘      └────────▲─────────┘
     read 时 CPU 复制               页表直接指过去,不复制
────────────┼──────────────────────────┼──────────── 用户态 / 内核态
            │       内核                │
   ┌────────┴──────────────────────────┴─────────┐
   │ 页缓存:每个文件(inode)一棵索引树          │
   │   文件偏移 0~4K   → 物理页 #1032  干净       │
   │   文件偏移 4K~8K  → 物理页 #877   脏        │
   │   ……                                         │
   └────────▲───────────────────────┬────────────┘
     缺页/未命中时 DMA 读入      回写时 DMA 写出
   ┌────────┴───────────────────────▼────────────┐
   │                   磁盘                       │
   └──────────────────────────────────────────────┘
```

落到内核数据结构上:每个打开的文件对应一个 inode,inode 里有一个 `address_space`(名字容易误导,它就是"这个文件在内存里的缓存"),里面用一棵 xarray 按"文件里的第几页"索引物理页(新内核以 folio 为单位,可以是多页的大块)。每一页带几个状态位:内容是否有效(uptodate)、是否被改过还没写回(dirty)、是否正在写回(writeback)。所有文件页还挂在 LRU 链表上(分活跃、不活跃两条),内存紧张时从不活跃的那头开始回收。

有两点要先记住,后面每一节都会用到:

- **一个文件在内存里只有一份。** 进程 A `read` 它、进程 B `mmap` 它、`cat` 再读一遍,用的都是同一组物理页。缓存是全系统共享的,不属于哪个进程。
- **页缓存里的东西在磁盘上都有原件**(脏页除外,写回之后也有了)。所以它是"借用"空闲内存,随时可以还。

## 讲页缓存与零拷贝前必须认识的几个词

- **页缓存(page cache)**:内核用空闲内存给文件做的缓存,按页管理。`/proc/meminfo` 里的 `Cached` 主要就是它。
- **Buffers**:块设备本身的缓存(比如文件系统的元数据块),通常只有几十 MB,和页缓存合起来就是 `free` 里的 `buff/cache`。
- **干净页 / 脏页**:内容和磁盘一致的是干净页,回收时直接丢掉;被 `write` 改过、还没写回磁盘的是**脏页**,要先写回才能丢。
- **回写(writeback)**:内核的 flusher 线程(`ps` 里叫 `kworker/...flush-...`)把脏页写回磁盘的过程。
- **预读(readahead)**:内核发现你在顺序读,提前把后面的内容读进页缓存。
- **DMA(直接内存访问)**:磁盘控制器、网卡这类设备自己在内存和设备之间搬数据,CPU 只负责下指令和收"搬完了"的中断,不逐字节复制。
- **内核缓冲区 / socket 缓冲区**:讲五种 IO 模型时说过,每条 TCP 连接在内核里有发送缓冲区,`write` 把数据拷进去就返回。在 Linux 里它由一串 `sk_buff`(skb)组成,每个 skb 既能带自己的数据区,也能挂若干个"指向别的物理页的分片"——零拷贝靠的就是后者。
- **mmap**:把文件映射进进程的地址空间,访问那段内存就是访问页缓存(原理见虚拟内存与地址空间)。
- **直接 IO(`O_DIRECT`)**:打开文件时带上这个标志,读写尽量绕过页缓存,在用户缓冲区和磁盘之间直接 DMA。
- **用户态/内核态切换**:每次系统调用进出内核各一次(详见用户态、内核态与系统调用)。注意它不等于线程上下文切换——进内核不一定换线程。

**一句话:读写文件默认都经过页缓存;"零拷贝"要省的,是页缓存和用户缓冲区之间那几次 CPU 复制。**

## 为什么第二次读同一个文件快很多

### 读路径:先查页缓存

```
read(fd, buf, 1MB)
  │
  ▼
内核按"文件偏移 / 页大小"算出要哪几页,到这个文件的 address_space 里查
  ├─ 页在、内容有效 → 从页缓存 CPU 复制到 buf                   命中,微秒级
  └─ 页不在         → 分配物理页,发起磁盘读(DMA),线程睡眠等待
                      读完唤醒,再复制到 buf                       未命中,慢
```

第一次读一个刚从磁盘冷启动的文件,每一页都要走下面那条路;第二次读,同样的页已经躺在页缓存里了,只剩一次内存复制。本机(macOS,Apple M3,16GB 内存)读一个 1GB 文件的实测:

```
第 1 次读:    307ms    3.50 GB/s     ← 走 SSD
第 2 次读:     63ms   17.15 GB/s     ← 走页缓存,只剩内存复制
```

这里的 SSD 已经是很快的 NVMe 了;换成云盘(普通云硬盘通常只有一两百 MB/s 的吞吐上限),差距会到几十倍。服务第二次启动快、`grep` 同一个日志第二遍秒出、模型文件第二次加载快得多,都是这个原因。而且因为缓存是全系统共享的,**进程 A 读过的文件,进程 B 再读也会命中**,哪怕 A 已经退出。

`mmap` 访问一个不在页缓存里的页时,同样要读磁盘,这就是缺页中断里说的"主缺页";页已在页缓存、只是还没映射进页表,叫"次缺页",只要改一下页表。

### 预读:顺序读为什么远快于随机读

内核在读路径上还会观察访问模式:发现你在顺序读,就**提前把后面的页读进来**。初始窗口是 `/sys/block/<设备>/queue/read_ahead_kb`(多数设备默认 128KB,`blockdev --getra` 显示的是 512 字节扇区数,即 256),确认是顺序读后窗口会逐步加大,并且是异步发起的——你还在处理当前这块,下一块已经在路上了。

- 顺序扫描一个 10GB 文件,预读一直命中,速度接近磁盘带宽上限。
- 在 10GB 文件里随机读 100 万个 4KB,预读全部白费,几乎每次都真读磁盘,还白白多读了预读的那部分。

所以数据库和存储引擎都想办法把随机读写变成顺序读写,LSM-Tree 就是为此而生。程序也可以主动告诉内核访问模式:`posix_fadvise(POSIX_FADV_SEQUENTIAL / RANDOM / WILLNEED)`,对 mmap 区域则用 `madvise`。随机访问为主的程序关掉预读(`FADV_RANDOM`)反而更快,因为不再白读。

### 缓存也会被"冲掉"

页缓存按 LRU 思路回收,这带来一个坑:一次性的大文件扫描(备份、`tar` 打包、`cp` 一个几十 GB 的快照)会把大量只用一次的页塞进缓存,把真正热的数据挤出去,于是备份一跑,业务读延迟就上去。内核的双链表设计(新读入的页先进不活跃链表,第二次被访问才升到活跃链表)就是为了缓解这个问题,新内核的多代 LRU(MGLRU)做得更细,但不能完全避免。

应对办法是让扫描程序"读完就还":读完一段调 `posix_fadvise(fd, off, len, POSIX_FADV_DONTNEED)` 把这段干净页丢掉,或者用 `dd iflag=direct` 这类直接 IO 方式做大拷贝。

## free 的 buff/cache 和 available 怎么看,缓存会不会把内存吃光

### 看 available,不要看 free

```bash
$ free -h
               total    used    free   shared  buff/cache   available
Mem:            16Gi   4.0Gi   500Mi    200Mi        11Gi        11Gi
```

- `free`:完全没被用的内存。内核的态度是**空着就是浪费**,所以它长期很小是正常的。
- `buff/cache`:`/proc/meminfo` 里 `Buffers + Cached + SReclaimable`(最后一项是可回收的内核 slab,比如目录项、inode 缓存)。
- `available`:对应 `MemAvailable`,内核估算的"不动用 swap 的前提下,现在还能分给新程序多少内存",它把 free 加上**能回收的那部分缓存**一起算了。

**判断内存够不够,看 `available`。** 上面这台机器 `free` 只有 500MB,但 `available` 有 11GB,内存很充裕。程序申请内存时,内核先回收干净的页缓存(直接丢,磁盘上有原件),不够再写回脏页后回收,再不够才动 swap、触发 OOM。

### 不是所有 cache 都能还

`buff/cache` 里有两块不能简单丢掉:

- **Shmem**:tmpfs(比如 `/dev/shm`、`/run`、Kubernetes 的内存型 `emptyDir`)和共享内存。它们也算在 `Cached` 里,但磁盘上没有原件,没 swap 就回收不了。`free` 里的 `shared` 列就是它。往 `/dev/shm` 写了 8GB 文件,`buff/cache` 涨 8GB,`available` 也会少 8GB。
- **脏页和正在写回的页**:要等写回完成才能回收,大量脏页时回收会变慢。

所以"缓存会不会把内存吃光"的答案是:普通文件缓存不会,内核会自动让;**tmpfs 和大量脏页会**,要单独盯 `Shmem`、`Dirty`、`Writeback` 三个字段。

### drop_caches 不是清内存的好办法

```bash
sync                                       # 先把脏页写回,否则丢不掉
echo 1 | sudo tee /proc/sys/vm/drop_caches # 1 = 页缓存,2 = 可回收 slab,3 = 两者
```

内核文档说得很清楚:这是"非破坏性操作,不会释放任何脏对象",所以要先 `sync`。它的代价是:接下来所有读都变成冷读,数据库、节点、模型服务的延迟会突然变高,直到缓存重新热起来;在一台 IO 本来就忙的机器上,先 `sync` 那一下本身就可能卡住很久。**它适合做基准测试前的"清场",不适合当定时任务。** 定时 drop_caches 解决的是一个不存在的问题,换来的是一个真实的问题。

## write 返回后数据在哪,脏页什么时候写回

### 写路径:先进页缓存,稍后回写

```
write(fd, buf, 1MB)
  │
  ▼
找到(或新建)对应的页缓存页 → 把 buf CPU 复制进去 → 标记为脏页
  │
  ▼
检查脏页总量(balance_dirty_pages),没超阈值就直接返回      ← 通常几微秒
  │
  ⋮ 之后某个时刻
  ▼
flusher 线程把脏页 DMA 写回磁盘 → 脏标记清除,变成干净页
```

**`write` 返回只代表数据进了页缓存。** 断电时还没写回的脏页就丢了;要确保落盘,得调 `fsync`(或打开时带 `O_SYNC` / `O_DSYNC`),讲文件系统时"写完要 fsync 才算落盘"的结论,根源就在这里。

### 什么时候写回:四个参数

| 参数 | 默认 | 含义 |
|---|---|---|
| `vm.dirty_writeback_centisecs` | 500(5 秒) | flusher 线程每隔这么久醒一次 |
| `vm.dirty_expire_centisecs` | 3000(30 秒) | 脏了超过这么久的页,下次醒来就写回 |
| `vm.dirty_background_ratio` | 10 | 脏页超过"可用内存"的 10%,flusher 开始后台写回,写程序不受影响 |
| `vm.dirty_ratio` | 20 | 脏页超过 20%,**正在写的进程自己被拖住**,等回写腾出空间 |

这里的"可用内存"按内核文档是"空闲页加可回收页",不是总内存,所以实际阈值比按总内存算的小一些。另有 `dirty_background_bytes` / `dirty_bytes` 两个按字节设定的版本,设了字节版,比例版就失效。

### 突然大量回写,为什么会卡住

`dirty_ratio` 是一道闸。写入速度持续超过磁盘写回速度时,脏页一路涨到 20%,写进程在 `balance_dirty_pages` 里被强制睡眠,`write` 从几微秒变成几百毫秒甚至几秒,`ps` 里看到它处于 `D` 状态。现象就是"程序每隔一阵卡一下",和磁盘吞吐的锯齿完全同步。

大内存机器上这个问题更严重:256GB 内存的 20% 是 50GB 脏页,而一块每秒写 200MB 的云盘要四分钟才能写完。一旦撞线,写进程会被拖很久;如果此时谁调了 `fsync` 或 `sync`,也要等这一大坨排在前面的数据。内核的 hung task 检测会在日志里留下 `task xxx blocked for more than 120 seconds`。

调优思路是**让回写早开始、少积压**:用 `dirty_background_bytes` 设成几百 MB、`dirty_bytes` 设成 1~2GB 这样的绝对值,让写回平滑进行,而不是攒一大波一起冲。对数据库这类自己会按节奏 `fsync` 的程序,影响反而小。

`fsync` 本身也有成本:一次要等数据和必要的元数据落到设备,SSD 上通常是毫秒级。每条记录都 `fsync`,每秒只能几百条;攒一批一起写一起 `fsync`(数据库叫 group commit),吞吐能高几十倍,崩溃最多丢这一批,"最多丢多少"可以精确设计。

## 传统 read + write 发一个文件,到底拷贝几次、切换几次

读文件发网络,最朴素的写法是循环 `read` 再 `write`:

```
          用户态           ┌──────────── 用户缓冲区 ────────────┐
                           │   ②▲                       │③      │
  ─────────────────────────┼───┼───────────────────────┼───────┼── 
          内核态           │   │ CPU 复制              ▼ CPU 复制
                       页缓存 ──┘               socket 发送缓冲区
                           ▲①                           │④
                           │DMA                         ▼DMA
                         磁盘                          网卡
```

| 步骤 | 谁来搬 | 发生在 |
|---|---|---|
| ① 磁盘 → 页缓存 | DMA | `read` 未命中时;命中就没有这一步 |
| ② 页缓存 → 用户缓冲区 | **CPU** | `read` |
| ③ 用户缓冲区 → socket 缓冲区 | **CPU** | `write` |
| ④ socket 缓冲区 → 网卡 | DMA | 内核协议栈发送 |

按教科书的数法:**4 次数据搬运,其中 2 次 CPU 复制;2 次系统调用,4 次用户态/内核态切换**。要注意这是"每一块数据"的数法:发 1GB 文件、每次 64KB,就是一万六千多轮 read + write,切换次数要乘上去;缓存命中时步骤 ① 不发生;`write` 遇到发送缓冲区满会阻塞或短写。所以别把"4 次拷贝 4 次切换"背成精确常数,它说的是结构。

浪费在 ② 和 ③:程序一眼不看,数据原样从内核复制出来,又原样复制回内核。好比厨师不开箱,却把整箱酒从冰箱搬到料台,再从料台搬到出货口。发 1GB 文件,CPU 白白复制 2GB,还要把这 2GB 都过一遍 CPU 缓存。

## sendfile 省掉了什么,"零拷贝"到底零的是哪几次

### sendfile:数据不进用户态

```c
ssize_t sendfile(int out_fd, int in_fd, off_t *offset, size_t count);
```

一句话告诉内核"把这个文件的这一段直接送到那个 socket":

```
磁盘 ──DMA──▶ 页缓存 ──CPU 复制──▶ socket 缓冲区 ──DMA──▶ 网卡
                     (只剩这一次)

3 次搬运,1 次 CPU 复制;1 次系统调用,2 次态切换
```

省掉的是 ② ③ 两次跨用户态的复制,以及一半的系统调用。`sendfile(2)` 的几条限制:`in_fd` 必须是支持 mmap 类操作的文件(不能是 socket);Linux 2.6.33 以前 `out_fd` 必须是 socket,之后可以是任意文件;单次最多传 `0x7ffff000` 字节,要循环调用;man page 也建议遇到 `EINVAL` / `ENOSYS` 时退回 `read` + `write`。

### 再省一次:分散-聚集 DMA

如果网卡支持**分散-聚集 DMA**(scatter-gather,能按一组"地址 + 长度"从不连续的内存取数据)和校验和卸载(网卡自己算 TCP 校验和,不用 CPU 先读一遍数据),内核就不必把数据复制进 socket 缓冲区:skb 里只挂几个**指向页缓存物理页的分片引用**,网卡发送时自己去页缓存取。

```
磁盘 ──DMA──▶ 页缓存 ─────────────────────DMA─────────────▶ 网卡
                 ▲
     socket 缓冲区里只有描述:"第 #1032 页,偏移 0,长 4096"

CPU 复制 0 次
```

这才是严格意义上的**零拷贝:零的是 CPU 复制,不是数据搬运。** DMA 搬运省不掉,数据总得从磁盘进内存、再从内存到网卡;是否真的做到 0 次 CPU 复制,还要看内核路径、网卡和驱动能力,现代服务器网卡基本都支持。

好处不止省 CPU 周期:

- **不污染 CPU 缓存。** 复制的数据会流经各级缓存,把常用数据挤掉(上下文切换的成本里也有这个问题),一个大文件能把缓存冲刷好几遍。
- **少占内存带宽。** 每次 CPU 复制都是"读一遍 + 写一遍",多核满负载时内存带宽本身就是瓶颈。
- **少一份内存。** 不需要每个连接一块用户缓冲区。

引用页缓存而不复制,也带来一个副作用:数据真正发出去之前,页缓存里的内容如果被别人改了,发出去的可能是改过的内容。发送"正在被改写的文件"时要心里有数。

### 同一家族的其他几个调用

| 技术 | 从 → 到 | 说明 |
|---|---|---|
| `sendfile` | 文件 → socket(新内核任意 fd) | 最常用;Nginx `sendfile on`、Kafka 都用它 |
| `splice` | 任意 fd ↔ 管道 | 两端至少一端是管道;socket 转 socket 的做法是 socket → 管道 → socket,数据页在内核里传引用 |
| `copy_file_range` | 文件 → 文件 | 在内核里复制;XFS、Btrfs 等支持 reflink 的文件系统上可以只改元数据、共享数据块 |
| `mmap` + `write` | 文件 → 任意 | 省掉页缓存到用户缓冲区那次,`write` 时仍有一次 CPU 复制 |
| `MSG_ZEROCOPY` | 用户缓冲区 → socket | Linux 4.14 起;发送大块**用户内存**时让网卡直接取,发送完成后通过错误队列通知,小包反而更慢 |
| 内核 TLS(kTLS) | 文件 → TLS socket | 加密放进内核或网卡,让 HTTPS 也能 `sendfile`,需要内核、库和配置都支持 |

### 零拷贝帮不上忙的时候

零拷贝的前提是**程序不加工数据**。以下情况数据必须进用户内存:

- **要加工内容**:压缩、解析、修改、用户态 TLS 加密。普通 HTTPS 服务在用户态加密,`sendfile` 用不上(除非上了 kTLS)。
- **数据不来自文件**:动态生成的响应、从数据库查出来的结果。
- **文件很小**:几 KB 的复制本身很快,开销大头是系统调用和协议栈,收益很小。

零拷贝针对的是"大文件原样转发":静态文件服务、文件下载、对象存储、消息队列把消息转给消费者、节点之间同步快照。

## mmap 适合什么,不适合什么

### mmap 省了什么

`mmap` 把文件映射到进程的地址空间,进程的页表直接指向页缓存里的物理页。读写这段内存就是读写页缓存:

- **省掉页缓存到用户缓冲区的复制**,也不用为每次访问调一次 `read`。
- **随机访问很自然**:B+ 树、索引文件、内存数据库可以直接用指针在文件里跳,LMDB、bbolt、MDBX 都是基于 mmap 的存储引擎。
- **多进程共享**:多个进程映射同一个文件,物理上只有一份。

### mmap 的代价

- **缺页成本。** 映射只是登记,第一次访问每一页都触发缺页异常:页在页缓存里是次缺页(改页表,微秒级),不在就是主缺页(读磁盘)。顺序读大文件时,`read` 一次系统调用能拷 1MB,而 mmap 要为每一页(或一批页)进一次内核,加上建页表、TLB 失效的开销,**顺序读大文件时 mmap 不一定比 read 快,常常更慢**。`MAP_POPULATE`、`madvise(MADV_SEQUENTIAL / WILLNEED)` 能缓解。
- **IO 错误变成信号。** `read` 读磁盘出错会返回 `EIO`,mmap 访问时读磁盘出错只能给进程发 `SIGBUS`。
- **文件被截短就崩。** 别的进程把文件截短后,访问超出新长度的那部分页,进程收到 `SIGBUS` 直接崩溃。所以 mmap 只适合"文件的生命周期由自己掌控"的场景。
- **写回时机不可控。** `MAP_SHARED` 映射写的是页缓存里的页,和 `write` 一样由内核择机写回,要落盘得调 `msync`;`MAP_PRIVATE` 映射的写触发写时复制(见缺页中断与换页),根本不会写回文件。
- **发网络仍有一次复制。** `mmap` + `write` 发送时 `write` 还是要把数据复制进 socket 缓冲区,mmap 本身不让发送变成零拷贝。
- **内存统计更绕。** 映射的文件页会算进进程的 RSS,看起来像进程占了很多内存,其实大部分是可以回收的页缓存。

经验上:**纯转发用 `sendfile`,要在文件里随机跳着读、又不想自己管缓存的,才考虑 mmap。** 数据库界对 mmap 争议很大,不少数据库(包括 PostgreSQL、InnoDB)选择不用它,主要就是为了掌握写回顺序和 IO 错误处理。

## 直接 IO(O_DIRECT)为什么数据库爱用

MySQL 的 InnoDB 自己维护一个很大的 Buffer Pool,按自己的规则缓存和淘汰页。如果数据还要经过页缓存,同一份数据会在内存里存两遍(Buffer Pool 一份、页缓存一份),等于白白浪费一半内存;而且内核的回写时机和数据库自己的刷脏策略会互相打架。

这时用**直接 IO**:打开文件带 `O_DIRECT`,读写尽量绕过页缓存,在用户缓冲区和磁盘之间直接 DMA。InnoDB 推荐 `innodb_flush_method = O_DIRECT` 就是为此。它的约束和误区:

- **要对齐。** `open(2)` 写明用户缓冲区地址、文件偏移和长度都要按逻辑块大小(通常 512 字节或 4KB)对齐,否则返回 `EINVAL`。新内核可以用 `statx` 的 `STATX_DIOALIGN` 查确切要求。
- **不等于持久化。** `open(2)` 原话的意思是:`O_DIRECT` 会尽量同步传输,但不提供 `O_SYNC` 那样的保证。文件元数据、磁盘自身的写缓存都还要 `fsync` 来兜,所以 InnoDB 用 `O_DIRECT` 照样要 `fsync`。
- **普通程序用了反而慢。** 没有自己的缓存,每次读都真读磁盘,预读也没了。

也有反过来的选择:PostgreSQL 主要依赖操作系统页缓存,`shared_buffers` 一般只开内存的四分之一左右,剩下留给页缓存。两种路线没有对错,关键是**缓存只在一个地方做**。同一个文件混用直接 IO、缓冲 IO 和 mmap,会带来一致性和性能上的麻烦,别这么干。

## Kafka 为什么快

Kafka 的设计文档把这件事讲得很直白:与其在 JVM 里自己做缓存,不如把一切交给页缓存。

- **只追加,不改写。** 消息只追加到分区日志末尾,是对磁盘最友好的顺序写,进页缓存后由内核成批写回。
- **刚写完的消息还在页缓存里。** 消费者通常紧跟生产者,要读的消息大概率还在页缓存,Kafka 用 Java 的 `FileChannel.transferTo`(底下就是 `sendfile`)把日志段直接发到网卡,数据不进 JVM 堆,也不产生 GC 压力。
- **不自己做缓存。** 文档里算过账:在 JVM 堆里存对象,内存开销通常是数据本身的两倍以上,还要承受 GC;页缓存紧凑、进程重启后还在。所以运维建议是 JVM 堆别开太大,把内存留给页缓存。
- **批量。** 生产者攒批发送、broker 批量写、消费者批量拉,系统调用和网络往返都摊薄了。

顺带一个线上常见的坑:Kafka 开了 TLS 之后,消息要在用户态加密,`sendfile` 就用不上了,broker 的 CPU 会明显上升。

值得借鉴的思路是:**不要重复造操作系统已经做好的东西。** 顺着页缓存的脾气来(顺序写、顺序读、刚写完就读),代码更简单,性能往往更好。

## 线上排查:和页缓存有关的几个现象

| 现象 | 多半是什么 | 怎么确认 |
|---|---|---|
| 告警"内存不足",`free` 很小 | 页缓存占着,并不缺内存 | `free -h` 看 `available`;`grep -E 'MemAvailable\|^Cached\|Shmem' /proc/meminfo` |
| `available` 真的很低,但进程 RSS 加起来不大 | tmpfs / 共享内存占着(`Shmem`),或内核 slab 不可回收部分大 | `/proc/meminfo` 看 `Shmem`、`SUnreclaim`;`df -h -t tmpfs` 看谁在 tmpfs 里放了大文件 |
| 写日志/写文件的程序周期性卡几百毫秒 | 脏页撞上 `dirty_ratio`,写进程被节流 | `grep -E '^(Dirty\|Writeback):' /proc/meminfo` 看是否接近阈值;`vmstat 1` 的 `bo` 列一阵一阵的、`b` 列有阻塞进程;`cat /proc/<pid>/wchan` 显示 `balance_dirty_pages` |
| 备份/拷大文件时业务读延迟变高 | 一次性扫描把热数据挤出页缓存,业务读变成冷读 | `vmstat 1` 的 `bi` 列在备份期间飙升;`sar -B 1` 看 `majflt/s` |
| 重启后服务慢一阵才恢复 | 页缓存冷了,预热期间大量真读磁盘 | `vmstat 1` 的 `bi` 先高后降;`fincore <文件>`(util-linux)看数据文件有多少在缓存里 |
| 容器 `memory usage` 接近 limit,担心 OOM | cgroup 把容器产生的页缓存记在它头上 | cgroup v2 看 `memory.stat` 的 `file`、`file_dirty`、`inactive_file`;Kubernetes 看 `container_memory_working_set_bytes`(用量减去不活跃文件页) |
| 有人加了定时 `drop_caches`,之后每小时抖一次 | 每次清缓存后全体冷读,清之前的 `sync` 也会卡 | `crontab -l`、`grep -r drop_caches /etc/cron*`;对照抖动时间点 |
| 发文件的服务 CPU 高 | 没用上 `sendfile`,走的是用户态读写循环;或开了用户态 TLS | `strace -f -c -p <pid>` 看 `sendfile` 和 `read`/`write` 的调用次数 |

关于容器那一行多说一句:cgroup 内存到 limit 时,内核会先在这个 cgroup 内部回收页缓存,干净页能回收就不会 OOM,所以 `usage` 接近 limit 本身不是危险信号;真正要看的是 working set 接近 limit,或者 `file_dirty` 很大(脏页回收慢)、`shmem` 很大(回收不了)。用 `usage` 做告警阈值,大量读写文件的容器会一直误报。

`strace` 是看"有没有用上零拷贝"的最直接手段:

```bash
strace -f -e trace=sendfile,splice,copy_file_range,read,write -p <进程号>
```

看到 `sendfile` 或 `splice` 就是用上了;只有成串的 `read`、`write` 交替,就还在走传统 read + write 的老路。

## 关联

- **区块链节点的数据库。** 节点的状态库(LevelDB、Pebble 的 SST 文件,或 MDBX 这类 mmap 引擎)读写极其依赖页缓存。同步时按区块高度顺序推进,吃得到预读和批量回写;查询账户状态是按哈希随机读,命中页缓存就是微秒级,不命中就是一次真实的磁盘读。所以同样的节点,**内存给得越多(留给页缓存的越多)跑得越稳**,`available` 长期很低的节点,RPC 延迟会明显抖。节点重启后要预热一段时间,也是页缓存冷了。
- **快照与备份。** 打包节点数据目录、`rsync` 快照到别的机器,是典型的"一次性大扫描":会把节点的热数据冲出页缓存,还会产生大量脏页。要么错开业务高峰,要么用直接 IO / `fadvise(DONTNEED)` 的方式拷,并盯着 `vmstat` 的 `bi` / `bo`。
- **GPU 推理服务。** 几十 GB 的模型权重(safetensors 加载时用的就是 mmap)第一次加载要真读磁盘,第二次快得多,因为还在页缓存里;这部分缓存在容器里记在容器的内存用量上,看监控要区分 working set 和页缓存,别把正常缓存当泄漏去扩 limit。
- **日志写入。** 多个服务同时大量写日志,脏页容易撞上 `dirty_ratio`,表现为业务线程写日志时偶发卡顿;异步写、按大小批量刷盘会好很多。用 mmap 读正在写的日志、或对它做 `copytruncate`,都可能踩到截断问题。
- **巡检口径。** 多台机器的巡检脚本判断内存用 `MemAvailable` 而不是 `MemFree`,另外单独看 `Dirty`、`Shmem`,告警才不会天天"假报警"。

## 总结

```
磁盘比内存慢千倍到十万倍 → 内核拿空闲内存做页缓存(按文件、按页,全系统一份)
  ├─ 读:先查页缓存,命中只剩一次内存复制;顺序读还有预读
  ├─ 写:进页缓存成为脏页就返回,flusher 按 5s/30s/10%/20% 规则回写
  │      撞上 dirty_ratio 写进程被节流;要立刻落盘就 fsync
  ├─ free 小不要紧,看 available;Shmem 和大量脏页才是真占着
  └─ drop_caches 只适合测试前清场
  ▼
读文件发网络,程序不加工数据
  ├─ read + write:4 次搬运,2 次 CPU 复制,4 次态切换(每块数据)
  ├─ sendfile:数据不进用户态,1 次 CPU 复制,2 次态切换
  └─ sendfile + 分散-聚集 DMA:0 次 CPU 复制,只剩 2 次 DMA
  ▼
其他选择
  ├─ mmap:省复制、便于随机访问;代价是缺页、SIGBUS、写回不可控
  ├─ O_DIRECT:自己管缓存的数据库用,要对齐,不保证持久化
  └─ Kafka:顺序写 + 依赖页缓存 + sendfile,不自己造缓存
  ▼
Go:io.Copy(TCPConn, *os.File) 自动 sendfile(Linux、macOS 都是),
    Linux 上文件→文件 copy_file_range,TCP→TCP / socket→文件 splice
```

最该记住的几句话:

- **页缓存是内核拿空闲内存给磁盘做的缓存**,读先查它,写先进它;一个文件在内存里只有一份。
- **`free` 小不代表内存不够,看 `available`**;真正回收不了的是 tmpfs/共享内存和来不及写回的脏页。
- **`write` 返回只代表进了页缓存**;脏页超过 `dirty_ratio`,写进程会被拖住,这是周期性写卡顿的常见根因。
- **零拷贝零的是 CPU 复制,不是数据搬运**:数据不进用户态,在内核里从页缓存直接送到网卡;前提是程序不加工数据。
- **mmap 不是免费的午餐,O_DIRECT 也不是"更接近硬件所以更快"**,它们都是给有特定访问模式、愿意自己承担复杂度的程序准备的。
- **不要重复造操作系统已经做好的东西。** 顺着页缓存的脾气来,往往比自己做一套缓存更快。

### 操作系统线全景

把整个操作系统串起来,饭馆从小到大遇到的每个麻烦,都对应一个操作系统机制:进程与线程、协程与用户态调度、调度算法、上下文切换、虚拟内存、分页与 TLB、缺页与换页、互斥锁、信号量与条件变量、死锁、阻塞与非阻塞 IO、IO 多路复用、Reactor 模式、系统调用、文件系统、页缓存与零拷贝。每个概念都是为解决一个具体麻烦而出现的,碰到陌生的系统机制,先问它要解决哪个麻烦。
