## Summary

"进内核"是操作系统里出现频率最高、也被说得最含糊的一个词。常见的理解有三种,都不对:

- "系统调用就是调用内核里的一个函数",只是比普通函数慢一点。实际上它要让 CPU 换一种身份、换一个栈、经过一道硬件把守的门,门后的代码还要把你传进来的每一个参数当成可疑物品检查一遍。
- "一次系统调用 = 两次上下文切换",所以"系统调用就是要切线程"。实际上绝大多数系统调用从头到尾都是**同一个线程**在跑,换的只是 CPU 的特权级,调度器根本没出场。
- "内核是另一个一直在运行的程序,系统调用是给它发个消息"。实际上内核不是一个单独等着的进程,是你自己的线程穿过那道门,去执行内核的代码。

把这几件事分清楚,很多线上现象就有了解释:`top` 里 `sy` 一栏为什么能占到一半、挂上 `strace` 之后程序为什么慢了上百倍、2018 年打完 Meltdown 补丁为什么一批服务整体慢了几个百分点、`time.Now()` 为什么几十纳秒就能返回、容器里一个正常的调用为什么报 `operation not permitted`、Go 程序为什么一读文件线程数就往上涨。

还是用饭馆来讲。进仓库、开保险柜、拉总闸、改柜锁这些事,厨师不能自己动手,只能走到经理窗口按规矩办。计算机里,厨师是普通程序,经理是内核,那个窗口叫**系统调用**。

## 先搞清楚:用户态和内核态是 CPU 的两种身份,不是两个程序

先把饭馆的比喻修正一下。经理窗口后面,**并没有另一个人坐着等你递单子**。真实的情况是:厨师本人走到窗口前,换上经理的工作服,按经理定好的规章走进去,自己把事办了,出来再脱下工作服回灶台。

计算机里也是这样。CPU 有一个"当前身份"的状态位,同一个线程在这一刻可以是用户态,下一刻进入内核态,再下一刻回到用户态:

```
线程 T 的时间线(同一个线程、同一个 CPU 核)

用户态   ██████████                        ████████████
                   │ syscall 指令          ▲ 返回指令
                   ▼                       │
内核态             ████ 执行内核的 read 代码 ██
                   └──────── 一次模式切换的来回 ───────┘
```

内核的代码和数据被映射在**每一个进程**地址空间的高端那一半(虚拟内存地址空间图里最上面那块),平时用户态碰不得;线程进入内核态之后,执行的就是那里的代码,用的是这个线程自己的内核栈。所以说"进内核"时,**变的是 CPU 的特权级,不是正在运行的那个线程**。

这样就能分清三件常被混为一谈的事:

| | 换了什么 | 谁来做 | 典型成本 |
|---|---|---|---|
| 模式切换(进出内核) | CPU 特权级、栈、部分寄存器 | CPU 硬件 + 内核入口代码 | 几十到几百纳秒 |
| 线程切换 | 正在 CPU 上跑的线程 | 内核调度器 | 几微秒(见上下文切换的成本) |
| 进程切换 | 线程 + 地址空间(页表) | 内核调度器 | 几微秒到几十微秒 |

**系统调用一定有模式切换,但不一定有线程切换。** 下面讲系统调用和上下文切换的区别时会把这条结论拆开。

## 讲系统调用前必须认识的几个词

- **特权级(Ring)**:CPU 给当前执行的代码定的身份等级。x86 设计了 Ring 0 到 Ring 3 四级,主流操作系统只用两级:内核跑在 Ring 0,普通程序跑在 Ring 3。ARM64 上叫异常级别(EL),用户程序在 EL0,内核在 EL1。下文说"用户态 / 内核态"就是这两级。
- **特权指令**:只有内核态能执行的指令,比如关中断(`cli`)、写页表基址寄存器(`CR3`)、读写某些硬件控制寄存器。用户态执行它们,CPU 直接拒绝并报异常。
- **模式切换**:CPU 从用户态进入内核态再回来的过程。它只换身份,不换线程。
- **系统调用号与 ABI**:内核给每个系统调用编了号,程序把编号和参数按约定放进指定寄存器再发起调用。这套"放哪个寄存器、返回值在哪"的约定叫 ABI(应用二进制接口)。x86-64 Linux 上 `read` 是 0 号、`write` 是 1 号、`getpid` 是 39 号;ARM64 Linux 用另一张表,`read` 是 63 号。
- **陷入(trap)、中断、异常**:让 CPU 从用户态跳进内核的三类事件。系统调用是程序**主动**的陷入,中断来自外部设备,异常是当前指令自己出了状况(下文专门对比三者)。
- **内核栈**:每个线程在内核里专用的一小块栈,进入内核态后使用,程序碰不到。
- **libc 封装**:C 程序里写的 `read()` 并不是系统调用本身,而是 C 标准库里的一个包装函数,它负责摆好寄存器、执行陷入指令、把错误码转成 `errno`。**库函数不等于系统调用**:`strlen` 一次都不进内核,`printf` 多半只是写进用户态缓冲区,一个库函数可能对应零次、一次或多次系统调用。
- **vDSO**:内核塞进每个进程地址空间的一小段代码和数据,让取时间这类调用不进内核就能完成(见下文 vDSO 部分)。
- **KPTI(内核页表隔离)**:2018 年为防 Meltdown 漏洞加上的机制,让用户态和内核态各用一套页表,进出内核都要换页表(见下文 Meltdown 与 KPTI 部分)。

**一句话:系统调用是程序按 ABI 摆好编号和参数,执行一条陷入指令,让同一个线程以内核身份去办一件事再回来。**

## 为什么要分用户态和内核态

如果程序能随便做任何事:

| 越权操作 | 后果 |
|---|---|
| 直接读写任意物理内存 | 读走别的进程的密码、密钥 |
| 直接操作磁盘控制器 | 写坏整个文件系统,绕过所有文件权限 |
| 直接修改页表 | 进程之间的内存隔离失效(见虚拟内存与地址空间) |
| 关闭时钟中断 | 内核再也没法把它从 CPU 上换下来,抢占式调度失效 |

DOS 时代就是这样:没有特权级之分,任何一个程序写错一个指针都能把整台机器带崩。

所以需要两种身份:

- **用户态**:只能用自己的内存,碰不了硬件和别人的内存,也执行不了特权指令。
- **内核态**:可以执行任何指令、访问任何内存、直接操作硬件。

这条规矩**由 CPU 硬件强制执行**,不靠程序自觉。页表里每一页都有一个"用户可访问"标志位,内核那一半的页没有这个标志,用户态去读就触发缺页异常,内核一看是越权访问,发 `SIGSEGV` 把进程终止;执行特权指令则触发一般保护异常,同样以终止告终。软件写的检查可以被绕过,硬件在每条指令上做的检查绕不过,这是隔离能成立的根基。

边界的代价是:程序每想办一件涉及硬件或共享资源的事,都得走一趟窗口。所以优化的方向是**减少不必要的往返**,而不是想办法绕开这道门——绕开它就等于放弃了隔离。

## 一次系统调用到底发生了什么

以 x86-64 Linux 上读文件 `read(fd, buf, 4096)` 为例,从用户态一路走到内核再回来:

```
用户态
  │ ① 包装函数(libc 或 Go 运行时)摆寄存器:
  │      rax = 0(read 的编号)
  │      rdi = fd,rsi = buf 地址,rdx = 4096(第 4~6 个参数用 r10、r8、r9)
  │ ② 执行 syscall 指令
  ▼
═══════════════ 特权级边界(CPU 硬件把守)═══════════════
  │ ③ CPU 硬件:把返回地址存进 rcx、标志寄存器存进 r11,
  │      特权级切到 Ring 0,跳到 MSR_LSTAR 寄存器里登记的固定入口
  │      (Linux 里是 entry_SYSCALL_64)。注意:这一步不换栈
  │ ④ 内核入口汇编:swapgs 拿到本 CPU 的私有数据,把用户栈指针存起来,
  │      开了 KPTI 的话先切到内核页表,再换到这个线程的内核栈,
  │      把用户态寄存器全部压栈保存(一个叫 pt_regs 的结构)
  │ ⑤ do_syscall_64:检查编号是否越界,按编号分派到处理函数
  │      (传统上查 sys_call_table 函数指针表;新内核为防分支注入
  │       攻击改成了一个大 switch,作用相同)
  │ ⑥ __x64_sys_read → ksys_read → vfs_read:查 fd 对应的文件、
  │      检查权限、从页缓存或磁盘取数据,用 copy_to_user 拷进 buf
  │ ⑦ 返回值写进 pt_regs 的 rax 位置;出错时返回负的错误码
  │      (比如 -EBADF);恢复寄存器、切回用户页表,执行 sysretq
═══════════════════════════════════════════════════════════
  ▼
用户态:从 syscall 的下一条指令继续。包装函数检查 rax,
       落在 -4095~-1 之间就是错误:取反存进 errno,返回 -1
```

ARM64 上流程一样,换了指令和寄存器:编号放 `x8`,参数放 `x0`~`x5`,执行 `svc #0`,返回值在 `x0`([`syscall(2)`](https://man7.org/linux/man-pages/man2/syscall.2.html) 有各架构的完整对照表)。

第 ③ 步是整个设计的关键:**程序只能决定"办哪件事",决定不了"跳到内核哪里"**。入口地址由内核在启动时写进 CPU 的专用寄存器,用户态改不了。所有系统调用都从这一个入口进,在这里统一保存现场、统一做检查。

### 核对参数是最要紧的一步

参数一个都不能信。程序传来一个地址要求"把数据放这里",内核必须确认它在用户地址空间里、而且可写;不查的话,传一个内核内存地址进来,就能借内核的手改写内核数据。所以 Linux 内核读写用户内存一律通过 `copy_from_user`、`copy_to_user` 这类自带检查的函数,它们还要处理拷贝途中目标页根本不存在、触发缺页的情况。

还有一类更隐蔽的漏洞:内核先检查了一遍用户内存里的数据,用的时候又读了一遍,两次之间另一个线程把内容改了。所以规矩是**从用户空间只读一次,拷进内核再检查、再使用**。不少"普通用户提权成 root"的漏洞,根源都是内核某处漏了这样一次检查。

### 用户栈和内核栈

第 ④ 步换栈,也是因为不能信任用户态:用户栈里可能有伪造内容,栈指针也可能指向无效内存,内核要是接着用它,用户程序就能操纵内核的执行。所以**每个线程其实有两个栈**:用户栈放程序的局部变量,内核栈在进入内核态后使用,由内核管理,程序碰不到。x86-64 Linux 的内核栈只有 16KB,所以内核代码不能写深递归,不能在栈上开大数组。

### errno 是怎么来的

内核没有 `errno` 这个东西,它只是在 `rax` 里返回一个负数。把 `-EAGAIN` 变成"返回 -1、`errno = EAGAIN`"是包装函数做的翻译。Go 的汇编里能直接看到这一步,这也是为什么 Go 的 `syscall` 包返回的是 `(结果, Errno)` 两个值,而不是去读一个全局变量——全局的 `errno` 在一个线程跑着成千上万个 goroutine 的模型里根本没法用。

## 系统调用和上下文切换是一回事吗

不是。把三条路径放在同一条时间线上看:

```
路径 A:线程 T 用户态 → read(数据已在页缓存)→ T 在内核态拷完 → T 回用户态
        只有模式切换,自始至终是 T 在跑

路径 B:线程 T 用户态 → read(数据还在磁盘)→ T 在内核里睡下
        → 调度器换线程 U 上 CPU …… 磁盘读完,T 被唤醒、排队、再上 CPU → 回用户态
        模式切换 + 线程切换(U 若属于别的进程,还要换页表)

路径 C:goroutine G1 → Go 调度器保存 G1 → 同一个线程上恢复 G2
        完全在用户态,既没有模式切换,也没有线程切换
```

所以**进内核 ≠ 换线程**:只有当系统调用需要等待(数据没到、锁被占、管道空了),线程在内核里睡下,调度器才出场,这时才发生调度意义上的线程切换。反过来,**换"执行单元"也不一定要进内核**:协程切换就完全在用户态。

"一次系统调用两次上下文切换"这个说法的来源,是有些教材把模式切换也叫"上下文切换"(进去存一次现场、出来恢复一次)。这在字面上说得通,但和调度意义上的上下文切换不是一个量级:前者几十到几百纳秒,后者几微秒,还会冲掉缓存。Linux 统计的 `voluntary_ctxt_switches`、`pidstat -w` 里的 `cswch/s`,数的都是调度意义上的切换,一次缓存命中的 `read` 不会让它们加一。

还有一个容易漏掉的细节:路径 B 里 T 被唤醒以后**不是立刻运行**,而是进入可运行队列排队。排查延迟时,"在内核里等 IO 的时间"和"唤醒后等 CPU 的时间"要分开看,否则会把 CPU 不够用误判成磁盘慢。

## 中断、异常、系统调用有什么区别

从用户态进内核一共三条路,保存现场、切换身份的过程基本相同,区别在于**谁触发、什么时候触发、处理完回到哪**:

| | 系统调用 | 中断 | 异常 |
|---|---|---|---|
| 谁触发 | 程序主动执行 `syscall` / `svc` | 外部设备:网卡、磁盘、时钟芯片 | 当前指令自己出了状况 |
| 和当前指令的关系 | 同步,程序有意为之 | 异步,和当前程序无关 | 同步,由某条指令引起 |
| 例子 | `read`、`write`、`mmap` | 网卡收到包、时钟每几毫秒一次 | 缺页、除以零、执行特权指令 |
| 处理完回到哪 | 陷入指令的**下一条** | 被打断的那条指令处继续 | 缺页补好后**重新执行**出错的那条;非法访问则终止进程 |

两个值得记住的点:

- **时钟中断是抢占式调度的发动机。** 即使一个程序死循环、从不发起系统调用,时钟中断也会定期把 CPU 交回内核,内核借机决定要不要换线程。这正是前面说"不能让程序关中断"的原因。
- **缺页是"可恢复"的异常。** 访问的页还不在物理内存里(见缺页中断与换页),内核补上这一页,然后让那条访存指令重新执行一遍,程序完全察觉不到。所以 `mmap` 读文件看起来一次系统调用都没有,其实每次缺页都进了内核。

`cat /proc/interrupts` 能看到每个 CPU 上各类中断的累计次数;`top` 里的 `hi`、`si` 两栏就是处理硬中断和软中断花的 CPU 时间,和 `sy`(系统调用等内核态时间)分开统计。

## 一次系统调用多贵,Meltdown 之后为什么更贵了

### 直接成本:数量级

在本机(Apple M3,macOS 26)上用 Go 实测:普通函数调用 1.3 纳秒,`time.Now()` 27 纳秒(不进内核),`getppid` 83 纳秒(进内核但几乎不干活),往 `/dev/null` 写 1 字节 375 纳秒(进内核并走完一趟文件写路径)。和线程上下文切换的成本放在一起,得到一把粗略的尺子:

```
普通函数调用         约 1 纳秒
空系统调用           约几十到一百纳秒        比函数调用慢几十倍
做点事的系统调用     几百纳秒起              门票 + 办事的工夫
线程上下文切换       约几微秒                再贵一个数量级
```

`Getppid` 和 `Write` 差了四倍多,说明**系统调用的成本不只是"进门费"**。`write` 要查 fd 表、拿文件引用、走 VFS 层、做权限和长度检查,Go 这边还要走 `entersyscall` / `exitsyscall`。具体数字随 CPU、内核版本、安全补丁差别很大,上面的数只用来建立量级感,要用就在自己的机器上测。

偶尔调一次无所谓,问题出在循环里:每次循环调一次,一百万次就是零点几秒的纯开销。

### 间接成本:回来以后手不顺

和讲上下文切换时算过的同一笔账,只是规模小一些:

- 内核代码和数据把程序在用的数据挤出 L1/L2 缓存,回到用户态后要重新从内存加载。
- 分支预测器里记的是内核代码的跳转规律,用户代码的记录被冲淡。
- 指令流水线在特权级切换处会被清空重填。

多伦多大学的 FlexSC 论文(OSDI 2010)专门测过:系统调用密集时,用户态代码的每周期指令数(IPC)会因为这些污染明显下降,间接损失可以比直接成本还大。这就是"批量"有效的另一层原因——次数少了,污染也少了。

### Meltdown 与 KPTI

2018 年爆出的 **Meltdown** 漏洞:CPU 为了快,会"猜着"提前执行后面的指令,猜错了再撤销。问题在于,用户态指令在被判定越权、撤销之前,已经把内核内存的内容带进了缓存,程序再通过测量访问时间就能把内容"读"出来。用户页表里本来就映射着内核那一半(开头说过),页表的权限位只挡住了正式的访问,挡不住这种推测执行。

这是硬件缺陷,软件的补救办法是 **KPTI**(内核页表隔离,Linux 4.15 合入):用户态运行时用一套"阉割版"页表,里面几乎没有内核内存,推测执行也就无从偷看;进内核时再切到完整页表(就是前面系统调用流程里第 ④ 步那个切页表),出来再切回去。代价是:

- 每次进出内核多了两次写 `CR3` 寄存器。
- 换页表会让 TLB(地址翻译速查表)失效,回到用户态后地址翻译要重新查表。CPU 的 **PCID** 特性给 TLB 条目打上地址空间标签,切换时不必全部清空,能把损失压下去很多。

Brendan Gregg 在 Netflix 做过一组实测:每 CPU 每秒 1 万次系统调用以下,损失预计在 0.5% 以内;到每秒 5 万次约 2%,调用越频繁损失越大;微基准里的极端情况(大工作集、无 PCID)会更夸张。MySQL 压测在每 CPU 每秒 7.5 万次调用下实测慢了约 5%。**KPTI 让系统调用的固定成本整体上了一个台阶,所以系统调用密集的程序受影响最大。**

AMD 的 CPU 和较新的 Intel CPU 在硬件上修复了 Meltdown,不需要 KPTI。一台机器开没开,看这个文件:

```bash
cat /sys/devices/system/cpu/vulnerabilities/meltdown
# Not affected          ← 硬件不受影响,没开 KPTI
# Mitigation: PTI       ← 开了 KPTI
```

除了 KPTI,Spectre 系列漏洞的缓解措施(retpoline、IBRS 等)也加在了内核入口上,同样让每次进出内核更贵一点。这是安全和性能之间的真实交换。

## 为什么 gettimeofday 不进内核:vDSO

日志每一行都带时间戳、监控每个请求都要记耗时,取当前时间是全世界调用最频繁的操作之一。如果每次都走一趟前面那套完整的系统调用流程,开销很可观。

**vDSO**(virtual Dynamic Shared Object,虚拟动态共享库)的思路是:取时间这件事本身不需要特权,只需要一份"内核知道的时间",那就把这份数据和读取它的代码**直接放进每个进程的地址空间**:

```
进程地址空间里内核放进来的两小段(cat /proc/self/maps 可见)

[vvar]   只读数据页:内核在时钟中断里不断更新
           "上次校准时的墙上时间"、"那一刻的 TSC 计数"、换算系数……
[vdso]   一小段代码:__vdso_clock_gettime 等
           读 [vvar] 里的基准 + 用 rdtsc 指令读 CPU 的时间戳计数器
           → 算出现在几点,全程在用户态
```

`rdtsc`(读时间戳计数器)在用户态是允许执行的,所以整件事不需要跨过特权级边界。就像厨房墙上挂了个钟,经理负责定期校准,厨师抬头就能看,不必去窗口问。内核在 [vvar] 里用一种读写序号(seqlock)保护数据:读的一方先读序号、再读数据、再读一次序号,两次一致才算读到完整的一份,不一致就重读,这样读者完全不用加锁。

根据 [`vdso(7)`](https://man7.org/linux/man-pages/man7/vdso.7.html),x86-64 上 vDSO 提供 `clock_gettime`、`gettimeofday`、`time`、`getcpu` 四个函数;ARM64 上有 `clock_gettime`、`gettimeofday`、`clock_getres` 等。内核在程序启动时通过辅助向量(`AT_SYSINFO_EHDR`)把 vDSO 的地址告诉它,libc 和 Go 运行时据此找到这些函数。

一个线上会踩的坑:vDSO 算时间依赖一个用户态能直接读的时钟源(通常是 TSC)。如果机器的时钟源不支持(比如一些 Xen 虚拟化的云主机时钟源是 `xen`),vDSO 会退回去发真正的系统调用,`time.Now()` 一下子慢好几倍。查当前时钟源:

```bash
cat /sys/devices/system/clocksource/clocksource0/current_clocksource   # 期望 tsc
```

同样的"快车道"思路还出现在两个地方:

- **futex**(互斥锁的底层机制):无竞争时加锁解锁在用户态用一条原子指令完成,真要等待时才进内核睡眠。大多数锁没有竞争,所以大多数加锁不产生系统调用。
- **协程切换**:在用户态换栈换寄存器,不进内核。

**给高频、简单、不需要特权的操作开一条不进内核的路,是操作系统里反复出现的设计。**

## 怎么减少系统调用

一句话:**能一次办完的事别分几次,能不进内核的事就别进。**

### 批量:缓冲是最便宜的优化

逐字节写一百万个字节,就是一百万次 `write`;先在用户态攒一个 4KB 的缓冲区,攒满再一次写出,次数降到 256 次。实测:同样写 1MB,前者 1.1 秒,后者 3 毫秒。这就是 C 的 `stdio`、Go 的 `bufio` 存在的理由。同一个思路还有很多形态:

| 手段 | 一次调用办了几件事 |
|---|---|
| 带缓冲的读写(`bufio`) | 攒满一块再调 `read` / `write` |
| `writev` / `readv` | 一次读写多块不连续的内存,省掉拼接和多次调用;Go 的 `net.Buffers` 底下就是它 |
| `sendmmsg` / `recvmmsg` | 一次收发多个 UDP 包 |
| `epoll_wait` | 一次拿到所有就绪的连接(见 IO 多路复用) |
| `getdents64` 读目录 | 一次读回一批目录项,而不是一项一次 |

批量也有代价,要心里有数:

- **延迟换吞吐。** 数据在缓冲区里攒着,对方就晚一点收到。交互式协议、日志要实时可见的场景,要设一个"攒满或超时就发"的上限。
- **数据还在用户态就不算写出。** 进程崩溃时缓冲区里没 `Flush` 的部分直接丢失;`Flush` 成功也只是交给了内核,断电不丢还要 `fsync`(见文件系统基础)。
- **次数少不等于数据少。** 合并之后数据照样要拷一遍,评估要同时看调用次数、字节数、吞吐和尾延迟,不能只看 `strace` 里的次数降了。

### io_uring:提交和收结果都不必每次进门

批量之后,每一批仍然要一次系统调用并等结果。Linux 5.1 引入的 **io_uring** 更进一步:程序和内核共享两个环形队列,程序把成百上千个 IO 请求写进提交队列,调一次 `io_uring_enter` 通知内核;内核把结果写进完成队列,程序直接从共享内存里读。开启 SQPOLL 模式后,内核用一个线程一直盯着提交队列,提交连一次系统调用都不用。

它的代价在讲五种 IO 模型时提过:接口复杂、出过不少漏洞,Docker 的默认 seccomp 配置直接禁用了 `io_uring_setup` 等三个调用(见下文线上排查部分)。

### mmap:把"读"变成"访问内存"

`mmap` 把文件映射进地址空间,之后读文件就是读内存,不再一次一次调 `read`。但前面讲异常时说过,第一次访问每一页都会触发缺页异常进内核,所以它省的是"调用次数"和"一次拷贝",不是"进内核"本身。随机访问大文件(数据库索引)时它很划算,顺序读一遍的场景不一定比带缓冲的 `read` 快。细节见页缓存与零拷贝。

### 零拷贝

把文件发到网络上,传统做法是 `read` 读进用户内存、`write` 写回内核,两次系统调用、数据多拷两次。`sendfile` 让内核直接从页缓存送到 socket,一次调用,数据不经过用户态,这就是零拷贝。Go 的 `io.Copy` 在"文件到 TCP 连接"的组合下会自动用上它。

## 线上排查:和系统调用有关的几个现象

| 现象 | 多半是什么 | 怎么确认 |
|---|---|---|
| `top` 里 `sy` 很高(比如超过 20%) | 系统调用太频繁,或某个调用在内核里干的活很重 | `perf top` 看热点是否在内核函数;`strace -c -f -p <pid>` 看哪种调用最多 |
| `strace -c` 里 `read`/`write` 几十万次 | 读写没有缓冲,每次只搬几个字节 | `strace -e trace=write -p <pid>` 看到满屏 `write(3, "x", 1)` 这种小写 |
| 小包写网络,吞吐低、`sy` 高 | 每个小消息一次 `write`,没有合并 | 同上;改成 `bufio.Writer` 或 `net.Buffers` 对比 |
| `futex` 调用特别多 | 锁竞争激烈,很多加锁没走成用户态快车道 | `strace -c` 里 `futex` 占比;Go 程序看 mutex profile |
| 挂上 `strace` 后程序慢了几十上百倍 | `strace` 用 ptrace 让被跟踪进程每次调用都停下来通知它 | 正常现象;生产环境改用 `perf trace` |
| 容器里报 `operation not permitted`,宿主机上没问题 | seccomp 过滤器拦下了这个系统调用 | `grep Seccomp /proc/<pid>/status`(2 表示开着过滤);`strace` 看是哪个调用返回 `EPERM` |
| 容器里 `perf` 用不了、io_uring 程序起不来 | Docker 默认 seccomp 禁了 `perf_event_open`、`io_uring_*` | 同上;临时验证可用 `--security-opt seccomp=` 换成放宽的配置 |
| Go 程序线程数几百上千 | 大量 goroutine 同时卡在阻塞系统调用(读文件、cgo) | `grep Threads /proc/<pid>/status`;goroutine dump 里大量 `[syscall]` |
| `time.Now()` 出现在 CPU profile 前列 | 时钟源不是 tsc,vDSO 退回真系统调用 | `cat /sys/devices/system/clocksource/clocksource0/current_clocksource` |
| 升级内核或换机型后整体慢了几个百分点 | KPTI 等漏洞缓解措施,系统调用密集的服务受影响最大 | `cat /sys/devices/system/cpu/vulnerabilities/*` |

几条好用的命令:

```bash
# 按种类统计系统调用次数和耗时,-f 跟踪所有线程;Ctrl+C 结束时打印
strace -c -f -p <pid>

# 开销小得多的替代:基于内核跟踪点,-s 打印每种调用的汇总
perf trace -s -p <pid>

# 全机每秒发生多少次系统调用(数 5 秒)
perf stat -e raw_syscalls:sys_enter -a sleep 5

# 每秒上下文切换:cswch/s 自愿(等待导致)、nvcswch/s 非自愿(被抢占)
pidstat -w -p <pid> 1

# 线程数、累计切换次数、seccomp 状态都在这里
grep -E 'Threads|ctxt_switches|Seccomp' /proc/<pid>/status
```

看 `strace -c` 的输出(`calls` 列是次数,`usecs/call` 是平均每次耗时)时注意两点:阻塞类调用(`epoll_wait`、`futex`、阻塞 `read`)的耗时里包含了睡眠等待,不等于 CPU 真花在内核里的时间;而且 `strace` 本身会改变程序的时序。

`strace` 的开销值得单独说一句。它基于 ptrace:被跟踪的线程每次进出系统调用都要停下来,切到 strace 进程处理完再切回去,每次系统调用变成了好几次线程切换。Brendan Gregg 的实测里,`dd` 在 `strace` 下慢了 442 倍,而且只跟踪一个无关的 `accept` 调用也一样慢——过滤是在被停下来以后才做的。**生产环境里 `strace` 只适合挂几秒钟,长时间观察用 `perf trace`。**

## 关联

- **节点的日志和落盘**:中继、监听服务每处理一笔交易都要打日志、写状态。日志库如果每行直接 `write`,高峰期 `sy` 会先于业务逻辑把 CPU 吃满。主流日志库(zap 等)都带缓冲或批量写,自己写文件时用 `bufio.Writer` 包一层,关键状态再显式 `Sync`。
- **区块链节点的状态数据库**:geth 等节点用 LevelDB / Pebble 存状态,大量读写本地文件,这些都是会占住线程的阻塞系统调用。同步区块时线程数上涨、`iowait` 和 `sy` 同时偏高,往往就出在这里。
- **cgo 密码学库**:节点里常见 C 写的 secp256k1、BLS 签名库。批量验签时让成千上万个 goroutine 同时进 C,每个进入 C 代码的 goroutine 都会占住一个线程,线程数会暴涨,要用有界 worker 池。
- **容器部署**:`CGO_ENABLED=0` 编出的静态二进制能放进 `scratch` 镜像,前提是 Go 自己发系统调用、不依赖 libc。在容器里跑 `perf`、用 io_uring 的组件时,先想到 seccomp,再去怀疑代码。
- **时间戳**:交易处理、超时判断、监控埋点到处是 `time.Now()`。正常情况下它走 vDSO,几十纳秒;云主机时钟源不对时会慢好几倍,这类问题只有知道 vDSO 才查得到。

## 总结

```
用户态 / 内核态:CPU 的两种身份,硬件强制
  │ 内核态专属:访问任意内存、操作硬件、改页表、开关中断
  │ 同一个线程在两种身份间来回,内核不是另一个进程
  ▼
系统调用 = 程序主动进内核的门
  │ 编号和参数进寄存器 → syscall → 硬件切特权级、跳固定入口
  │ → 内核换栈、存寄存器(KPTI 下还要切页表)→ 按编号分派
  │ → 核对参数、copy_from_user/copy_to_user → 返回值进 rax → sysret
  │ 另外两条路:中断(外部、异步)、异常(自身、同步,缺页可重试)
  ▼
系统调用 ≠ 上下文切换
  │ 只有在内核里等待时,调度器才换线程
  ▼
成本:空调用几十到一百纳秒,干活的几百纳秒起
  │ 间接成本:缓存、分支预测、流水线被搅乱
  │ KPTI(2018)让每次进出都切页表,调用越频繁越吃亏
  ▼
减少的办法
  ├─ 批量:bufio、writev、sendmmsg、epoll
  ├─ 共享队列:io_uring
  ├─ 不进内核:vDSO(time.Now)、futex 快路径、协程切换
  └─ 少拷贝:mmap、sendfile(页缓存与零拷贝)
  ▼
Go:Linux 上自己执行 SYSCALL;Syscall 带 entersyscall/exitsyscall,
    卡久了 sysmon 的 retake 把 P 拿走交给新线程 → 文件 IO、cgo 要限并发
```

最该记住的几句话:

- **用户态和内核态是 CPU 的两种身份,不是两个程序。** 系统调用是同一个线程换上内核身份办事,这道墙由硬件在每条指令上把守。
- **系统调用不等于上下文切换。** 一定有模式切换(几十到几百纳秒),只有在内核里需要等待时才会换线程(几微秒)。
- **内核对用户传进来的每个参数都不信任**:只能从唯一入口进、换到内核栈、用 `copy_from_user` 读用户内存。
- **一次系统调用比函数调用贵几十到上百倍,KPTI 之后更贵;优化的方向只有两个:一次多办几件事,能不进内核就不进。**
- **`time.Now()` 快是因为 vDSO;`bufio` 是最便宜的性能优化,记得 `Flush`。**
- **Go 里卡在阻塞系统调用里的 goroutine 会占住一个线程,sysmon 会为别的 goroutine 新开线程。** 网络 IO 走 netpoll 不占线程,文件 IO 和 cgo 要用 worker 池限并发。
