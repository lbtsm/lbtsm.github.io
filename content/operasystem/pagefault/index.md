## Summary

上一篇讲到,对照表每一行的备注栏里,第一个勾是"在不在":这一格的东西现在在不在冷藏室。这个勾经常是空的:经理批柜号时只登记不分格子,有些东西被挪去了郊区冷库,有些还在冷库里没运过来。

厨师报了一个柜号,管理员一查是空的,会怎样?绝大多数时候什么坏事都没发生,厨师照样拿到东西,只是这次等得久了一点。中间发生的事叫**缺页**。正因为"东西不在"能被妥善处理,经理才敢先登记后分配,让冷藏室装下比自己容量还多的东西。

## 缺页:暂停、补上、重做

### 处理流程

```
程序访问虚拟地址,MMU 发现页表项 P 位 = 0
  │
CPU 触发缺页异常,暂停当前指令,进入内核
  │
内核查这个进程的地址空间登记:这次访问合法吗?
  │
  ├─ 没登记过,或往只读页里写   → 发 SIGSEGV,段错误,进程崩溃
  │
  └─ 合法,只是物理页还没就位
        → 分配物理页(或从磁盘读回来),填进页表
        → 让 CPU 重新执行刚才那条指令
        → 这次命中,程序继续
```

关键在最后一步:**不是跳过那条指令,而是原样重做一次。** 所以程序毫无察觉,只是这一次访问慢了一点。

### 同样叫缺页,代价差上万倍

**次要缺页(minor fault):不用读磁盘。** 第一次访问新申请的内存(分一个清零的空闲页);fork 后写共享页(写时复制);要的文件页别的进程已经读进了内存(直接映射过来)。

**主要缺页(major fault):必须读磁盘。** 页被换到了 swap,或者文件内容从没读进内存过。

```
次要缺页                  大约 1~10 微秒
主要缺页(从 SSD 读)      大约 100 微秒
主要缺页(从机械硬盘读)   大约 10 毫秒
```

**非法访问:** 访问 0 号附近的地址、往代码段里写,就是空指针、野指针、写只读内存导致的段错误。

次要缺页非常频繁也完全正常,程序每用一块新内存都会触发。**要警惕的是主要缺页**:程序启动时偶尔有一些正常(代码和文件第一次读进来),持续不断就说明内存不够,页在内存和磁盘之间来回搬。

## 内存满了,先换出谁

要分配新页而物理内存已满,内核就得挑一页换出去。挑得好不好,决定以后要读多少次磁盘。这是**页面置换算法**的问题。

**最优置换(OPT):换出以后最久不会用的那页。** 可以证明缺页最少,但要预知未来,做不出来,只当尺子用来衡量别的算法。

**先进先出(FIFO):换出最早进来的那页。** 最简单,但最早进来的往往是天天在用的(就像开业第一天放进冷藏室的酱油和盐),换出去马上又要读回来。它还有个反常毛病:访问序列 `1 2 3 4 1 2 5 1 2 3 4 5`,3 个页框缺页 9 次,4 个页框反而 10 次。这叫 **Belady 异常**,给更多资源结果更差。

**LRU(最近最少使用):换出最久没被访问的那页。** 之前讲过局部性,用过去猜未来,大多数时候很准。问题是精确 LRU 要在每次内存访问时更新记录,这个开销没法接受。

**Clock(时钟算法,也叫第二次机会):实际在用的近似。** 它借助页表项里的**访问位(A 位)**,这一位由硬件在访问时自动置 1,不用软件记账。把所有物理页排成一个环,指针转着圈扫:

```
A = 1 → 最近用过,清成 0,放它一马,看下一页
A = 0 → 自上次扫过以后没人碰过,换出它
```

常用的页刚被清零很快又被置 1,总能逃过;不常用的转一圈回来就被换出。几乎零成本,效果接近 LRU。Linux 实际更复杂一些(活跃/不活跃两个链表,新内核还有多代 LRU,即 MGLRU),但思路相同:**利用硬件免费给的访问标记做够用的近似,不花大代价精确追踪。**

**换出前看脏位(D 位)。**

- **文件页**没被改过:磁盘上本来就有原样,直接丢弃,要用时再读。
- **匿名页**(堆、栈,磁盘上没有对应文件)或改过的页:必须先写到磁盘才能腾地方。匿名页写去的地方,就是 swap。

## swap

### swap 是什么

**swap**(交换空间)是磁盘上的一个分区或文件。内存紧张时,内核把不常用的匿名页写进去,腾出物理内存;以后再访问这一页,触发主要缺页读回来。没有 swap,内核能回收的就只有文件页。

### 抖动

swap 有用的前提是:被换出的页确实不常用。如果常用的页加起来已经超过物理内存:

```
内存满 → 换出一页 → 它马上又要用 → 读回来 → 又得换出另一页 → ……
```

就像运货车一直在冷藏室和冷库之间来回跑,厨师全在门口等车。这叫**抖动**(thrashing),特征很好认:

```
CPU 利用率   低,都在等磁盘
磁盘读写     打满
swap 读写   持续很高
系统响应     极慢,像死机
```

这时如果调度程序看到 CPU 闲、再加任务,只会抖得更厉害。唯一的解法是**减轻内存压力**:少跑任务、加内存、缩小工作集。

### 该不该开 swap

开 swap 的好处:内存紧张时不至于立刻有进程被杀;长期不用的匿名页可以挪出去,把内存让给文件缓存。

不开的理由:一旦真用上 swap,延迟从纳秒级跳到毫秒级。**对线上服务,"慢到不可用"往往比"直接挂掉"更糟。** 挂了,健康检查失败,负载均衡把它摘掉;慢着却活着,健康检查照样通过,流量继续打进来,请求一起超时,还拖垮上游。

实践中:

- **数据库、缓存、低延迟服务**:关 swap,或把 `vm.swappiness` 设得很低。Redis、Elasticsearch、Kafka 官方文档都这么建议。
- **Kubernetes**:长期要求节点关 swap;1.34 起节点 swap 支持正式稳定(`LimitedSwap` 模式限制每个容器的用量),但开给谁仍要谨慎。
- **桌面、批处理**:开着更好。

`vm.swappiness` 控制内存紧张时内核多倾向于换出匿名页(相对于丢弃文件缓存),取值 0~100(5.8 以后最大 200),越大越积极。服务器常设 1 或 10。

## OOM Killer

之前讲过,内存是可以超额批准的。如果实际使用内存超过内存上限,能换出的都换出了(或者没开 swap),还是腾不出一页,内核只剩最后一招:**挑一个进程杀掉,收回它的内存。**

这就是 **OOM Killer**。它给每个进程打分(`oom_score`),大致是占内存越多分越高,分最高的被杀。可以用 `oom_score_adj` 调整,`-1000` 表示永不杀。

被选中的进程收到 `SIGKILL`,**当场终止,没有任何收尾机会**:清理代码不执行,没落盘的日志丢失,处理中的请求直接断掉。唯一的线索在内核日志里:

```bash
dmesg -T | grep -i -E "out of memory|killed process"
```

容器还有一层:每个容器有自己的 cgroup 内存上限,超过就在容器内部触发 OOM,哪怕整机还有大量空闲内存。Kubernetes 里 Pod 状态 `OOMKilled`、退出码 137(128 + 信号 9),就是这么回事。

## 写时复制

Linux 新开进程是先 `fork()` 再 `exec()`。如果 fork 时真把父进程的内存全复制一份,不但慢,而且多半白费:紧接着的 `exec` 会把它们全部扔掉。所以:

```
fork
  子进程的页表照抄父进程,指向同样的物理页
  双方的这些页统统标成只读
       │
任一方要写某页
  → 写只读页,触发缺页
  → 内核复制这一页给写的一方,标成可写
  → 重做那条写指令
       │
结果:只有真被写过的页才复制,其余一直共用
```

这就是**写时复制**(Copy-on-Write,COW),所以 fork + exec 几乎不用复制内存。

典型的真实场景是 Redis 的 `BGSAVE`:fork 一个子进程把 fork 那一刻的内存快照写到磁盘,父进程继续处理写请求。父进程每改一页就复制一页,持久化期间写入越多,**内存占用越接近翻倍**。给 Redis 规划内存时要为此留余量。

## 缺页撑起的机制

| 机制 | 怎么靠缺页实现 |
|---|---|
| 按需分配 | 申请时只登记不建映射;第一次访问缺页,才分配物理页 |
| 写时复制 | fork 后共享页标只读;写时缺页,才真正复制 |
| mmap 文件 | 映射时不读文件;访问哪页缺页,才读哪页 |
| swap | 换出时清 P 位、记下 swap 位置;再访问时缺页,读回来 |
| 栈自动增长 | 栈往下碰到未映射的页,缺页处理程序认出是栈,自动扩一页 |
| 相同页合并(KSM) | 内容相同的页合成一份、标只读;谁写谁缺页,再分开 |

套路都一样:**先故意把状态设成"一碰就出错",等真有人碰,借缺页把控制权交给内核,内核这时才去做真正的工作。** 能不做就不做,能晚做就晚做。这种思路叫**惰性求值**。

## 常用Linux命令

**看进程的缺页。**

```bash
ps -o pid,min_flt,maj_flt,comm -p <进程号>    # 累计次要、主要缺页
pidstat -r -p <进程号> 1                      # 每秒 minflt/s、majflt/s
```

`minflt/s` 高一般没关系,**`majflt/s` 持续大于 0 才要警惕**。

**看全系统有没有在换页。** `vmstat 1` 看 `si`、`so` 两列(每秒从 swap 换入、换出多少 KB),持续不为 0 说明内存不够了。`free -h` 的 `Swap` 行看用了多少。

**看和改 swappiness。**

```bash
cat /proc/sys/vm/swappiness
sudo sysctl -w vm.swappiness=10     # 临时修改,重启失效
```

**看 OOM 分数。**

```bash
cat /proc/<进程号>/oom_score       # 越高越先被杀
cat /proc/<进程号>/oom_score_adj   # -1000 到 1000
```

**程序刚启动为什么慢。** 代码第一次从磁盘读进来(主要缺页),新内存第一次访问(次要缺页),CPU 缓存和 TLB 也是空的。跑一会儿常用页都到位就快了。这就是"预热",也是压测前几秒数据不能算数的原因。

## 关联

**服务变慢,先花几秒看换页。** `pidstat -r` 的 `majflt/s` 和 `vmstat` 的 `si/so` 不为 0,优化代码没有意义,先解决内存。

**Go 服务在容器里,让失败清晰。** 关 swap(K8s 默认不用 swap),设好 `GOMEMLIMIT`(Go 1.26 不会自动按容器限制设置)。内存吃紧时先是 GC 更积极;真顶不住就是一次清晰的 `OOMKilled`、Pod 重新拉起,而不是在 swap 里慢慢拖死、健康检查还显示正常。

**被 OOM Kill 时没有收尾机会。** defer 不执行,没 flush 的日志丢失,业务停在中间状态。重要流程要有持久化的检查点,重启后能断点续做。

**对象复用省的不只是 GC。** `sync.Pool` 复用缓冲区,还省掉了新内存第一次访问的次要缺页,复用的内存也大概率还在 CPU 缓存里。

**goroutine 的栈不靠缺页长大。** 线程栈靠缺页自动扩;goroutine 栈由 Go 运行时在函数调用前检查空间,不够就分配一块两倍大的新栈,把旧栈整个拷过去,和缺页无关。

**以太坊节点这类内存大户务必配足内存。** 全节点同步时状态缓存很大,一旦开始换页,同步速度会掉好几个数量级。

## 总结

```
访问的页不在内存(缺页)
  │ 内核补上,让那条指令重做,程序无感
  │ 次要缺页:不读磁盘,微秒级,正常
  │ 主要缺页:读磁盘,慢百倍到万倍,持续出现要警惕
  │ 非法访问:段错误
  ▼
内存满了,换出谁(页面置换)
  │ OPT 做不到,只当尺子;FIFO 会换出常用页,有 Belady 异常
  │ LRU 有道理但精确实现太贵;Clock 借硬件访问位近似 LRU
  │ 脏页、匿名页换出前要先写盘
  ▼
swap:匿名页的去处
  │ 工作集超过内存 → 抖动
  │ 延迟敏感服务:慢到不可用比挂掉更糟,通常关 swap
  ▼
实在腾不出:OOM Killer,SIGKILL,没有收尾机会

写时复制:fork 先共享,谁写谁复制
按需分配、COW、mmap、swap、栈增长,全靠缺页:先设成会出错的状态,用时再做
```

最该记住的几句话:

- **缺页不是错误**,内核处理完让那条指令重做一遍,程序毫无察觉。
- **次要缺页正常,主要缺页要警惕**:它意味着在等磁盘,持续出现通常是内存不够了。
- **实际系统用访问位做 LRU 的近似**,因为精确追踪的代价比收益大。
- **线上服务里,慢到不可用往往比直接挂掉更糟**,所以延迟敏感的服务通常关 swap。
- **OOM Killer 用 SIGKILL**,进程没有收尾机会,重要状态必须提前持久化。
- **写时复制让 fork 几乎不用复制内存**,但 fork 之后写入越多,内存涨得越多。

## 动手练习

需要一台可以随便折腾的 Linux 测试机。

1. **看缺页计数。** `ps -eo pid,min_flt,maj_flt,comm --sort=-maj_flt | head`,想想哪些进程主要缺页多、为什么(往往是刚启动或读了很多文件的)。
2. **看启动时的缺页。** `/usr/bin/time -v ls -R /usr > /dev/null`,看 `Major` 和 `Minor` 两行。连跑两次对比:第二次主要缺页明显变少,因为文件已经在缓存里了。
3. **看系统有没有在换页。** `vmstat 1` 观察 `si`、`so`;`free -h` 看 swap 用量;`cat /proc/sys/vm/swappiness`。
4. **观察抖动和 OOM。** 一个终端跑 `vmstat 1`,另一个跑 `stress-ng --vm 1 --vm-bytes 90% --timeout 60s`,看 `si/so` 和 `wa` 怎么变;再把 `--vm-bytes` 调到超过物理内存加 swap,跑完用 `dmesg -T | grep -i killed` 找 OOM 记录。不要在生产机器上做。
5. **验证 Belady 异常。** 用 `1 2 3 4 1 2 5 1 2 3 4 5` 分别按 3 个和 4 个页框模拟 FIFO,数出缺页次数(应为 9 和 10);再用 LRU 模拟一遍,看还会不会出现。
