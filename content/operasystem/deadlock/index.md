## Summary

早高峰,四个方向的车同时抢进一个没有交警的十字路口:

```
         ↓ 北
      ┌─────┬─────┐
      │  A  │  B  │ ← 东
      │  ↓  │  ←  │
      ├─────┼─────┤
 西 → │  →  │  ↑  │
      │  D  │  C  │
      └─────┴─────┘
               ↑ 南

路口分成 A、B、C、D 四格,箭头是每辆车要去的方向:
北边来的车占住 A,要往前开进 D
西边来的车占住 D,要往前开进 C
南边来的车占住 C,要往前开进 B
东边来的车占住 B,要往前开进 A
```

每辆车都占着一格,等着前面那格,而前面那格又被下一辆车占着。谁都不肯倒车,后面还跟着长长的车队,四个方向就永远堵死了。装了红绿灯也一样:绿灯时车头挤进路口,出口却已经堵死,灯变了也走不了。

把车换成进程,把格子换成资源,就是死锁。这一篇先讲死锁是什么、怎么产生,再讲操作系统对付它的四种办法:**预防、避免、检测、解除**,其中银行家算法和资源分配图化简各带一个完整的例子。最后落到写代码:怎么不写出死锁,卡住了怎么查。

## 什么是死锁

**死锁:一组进程中,每个进程都在等待一个只能由这组中其他进程才能引发的事件,结果谁都无法向前推进。** 没有外力介入,它们会永远等下去。

这个定义里有两个要点:

- **是"一组"进程。** 一个进程单独等一个永远不会来的消息,那是程序写错了,不叫死锁。死锁至少要两个参与者,互相把对方卡住。
- **等的事件只能由组内的人引发。** 路口北边的车等 D 格空出来,而能让 D 格空出来的只有西边那辆车,西边那辆又在等南边……外面没有人能帮它们解开。

### 资源的分类

死锁是围绕资源发生的,先把资源分清楚:

**可剥夺资源**:被占用时可以被系统强行收回,收回后不影响进程最终正确运行。典型是 CPU 和内存:进程被调度走、内存页被换出去,以后还能接着跑。**这类资源不会引起死锁**,因为卡住时系统收回来就行。

**不可剥夺资源**:一旦分配出去,只能等进程用完自己释放,强行收回会出错。典型是打印机、磁带机、一把锁、一条数据库记录:打印到一半被抢走,纸上就是两份文档混在一起。**死锁都发生在这类资源上。**

另一个维度是**可重用资源**和**消耗性资源**:打印机、锁用完还在,可以给下一个人用,是可重用资源;消息、信号是消耗性资源,生产者产生一个、消费者拿走一个就没了。两类资源都能引起死锁。

## 死锁产生的原因

### 原因一:竞争不可剥夺资源

系统里的打印机、锁、记录这些不可剥夺资源数量有限,不够所有进程同时用。比如只有一台打印机 R1 和一台磁带机 R2:

```
进程 P1:                 进程 P2:
  申请 R1  ✓ 得到          申请 R2  ✓ 得到
  申请 R2  ← 等 P2 释放    申请 R1  ← 等 P1 释放
```

P1 拿着 R1 等 R2,P2 拿着 R2 等 R1,谁也不会先放手。如果资源足够多(两台打印机、两台磁带机),就不会出现这种争抢。

消耗性资源也一样能死锁。两个进程互相通信,都先等对方的消息再发自己的消息:

```
进程 P1:                 进程 P2:
  receive(P2 的消息)        receive(P1 的消息)
  send(给 P2)              send(给 P1)
```

两边都卡在第一句 receive 上,第二句 send 永远执行不到。

### 原因二:进程推进顺序不当

资源不够只是死锁的土壤,不一定真的会死锁。同样是上面的 P1 和 P2,换个执行顺序就没事:

```
P1 申请 R1 → P1 申请 R2 → P1 用完释放 R1、R2 → P2 申请 R2 → P2 申请 R1   ✓ 没事
P1 申请 R1 → P2 申请 R2 → P1 申请 R2(等)→ P2 申请 R1(等)              ✗ 死锁
```

两个进程交替推进的路线有很多条,其中一部分路线会走进"P1 持有 R1 且 P2 持有 R2"的区域,一旦走进去,往后无论怎么推进都出不来。这片区域叫**危险区**。走哪条路线由调度决定,程序员控制不了,这就是死锁**不一定能复现**的根源:测试跑一万次都没走进危险区,线上某天碰巧走进去了。

所以说,**死锁产生的原因是:资源竞争 + 进程推进顺序不当。** 前者是前提,后者是触发。

## 四个必要条件

1971 年 Coffman 等人总结出,死锁发生必须同时满足四个条件。拿路口对照着看,一个不少:

**① 互斥条件。** 一个资源一次只能被一个进程占用。路口一格只能停一辆车。

**② 占有并等待条件**(也叫请求和保持)。进程已经占有了至少一个资源,又提出新的资源请求,而新资源被别人占着,于是它阻塞等待,但对已占有的资源不放手。车占着当前这格,等前面那格空出来。

**③ 不可剥夺条件。** 进程已获得的资源,在用完之前不能被强行夺走,只能由它自己释放。没人能把别人的车从格子里拖走。

**④ 循环等待条件。** 存在一个进程等待链 {P0, P1, …, Pn},P0 等 P1 占有的资源,P1 等 P2 占有的资源……Pn 等 P0 占有的资源,首尾相接成一个环。北等西、西等南、南等东、东等北。

这四个是**必要条件**,不是充分条件:死锁发生时四个一定都成立;但四个都成立,不一定就死锁(后面讲资源分配图时会看到例子)。反过来,**只要破坏其中任意一个,死锁就一定不会发生**,这是"死锁预防"的理论依据。

## 处理死锁的四种方法

操作系统对付死锁,按出手时机由早到晚分成四种:

| 方法 | 做法 | 出手时机 | 代价 |
|---|---|---|---|
| **预防** | 破坏四个必要条件之一,从根上让死锁不可能发生 | 设计系统时 | 限制最严,资源利用率低 |
| **避免** | 每次分配资源前先算一下,会让系统进入不安全状态就不分 | 每次分配时 | 要事先知道每个进程最多要多少资源 |
| **检测** | 不加限制,定期检查有没有发生死锁 | 事后 | 检查本身有开销 |
| **解除** | 检测到死锁后,撤销进程或剥夺资源 | 发现后 | 被撤销进程的工作白做 |

还有第五种,叫**鸵鸟算法**:把头埋进沙子,假装没这回事。Linux、Windows 对用户程序之间的锁死锁基本就是这么处理的——操作系统不管,出了问题由程序员自己负责。这不是偷懒:死锁很少见,而预防、避免、检测的开销却每时每刻都要付。所以真正需要掌握"预防"的,往往是写程序的你。

## 死锁预防:破坏四个必要条件之一

### 破坏互斥条件

让资源可以同时共享。只读文件、只读数据天然可以共享;打印机可以用 **SPOOLing 技术**:进程不直接占打印机,而是把要打印的内容写到磁盘上的输出井,由一个专门的守护进程逐个打印,对进程来说打印机像是可以同时使用了。

但很多资源本身就要求互斥,一把锁不互斥就失去了意义。所以**这一条一般做不到**,预防死锁主要靠破坏后三个条件。

### 破坏占有并等待条件:静态分配

规定进程在**开始运行前一次性申请它需要的全部资源**,要么全部分给它,要么一个都不给。运行过程中不再申请新资源,也就不存在"占着一个等另一个"。这叫**静态资源分配**,也叫一次性分配。

缺点很明显:

- **资源浪费严重。** 一个进程运行十个小时,只在最后五分钟用打印机,也得从头占着打印机十个小时。
- **可能饥饿。** 一个要很多资源的进程,总有一两个资源被别人占着,永远凑不齐。
- **事先很难知道要用哪些资源。**

工程上的变体是**拿不齐就全放下**:先拿第一把锁,再尝试拿第二把(`trylock`),拿不到就把第一把也放掉,过一会儿重试。这样不会"占着一个干等",但会引出新问题,两个线程同时开始时:

```
1 拿 A、2 拿 B → 都拿不到第二把 → 都释放
1 拿 A、2 拿 B → 都拿不到第二把 → 都释放
1 拿 A、2 拿 B → ……
```

一直在拿、在放,像窄过道里迎面的两个人同时往左让、又同时往右让。这叫**活锁**:都没停下,但谁都没进展。解法是**随机退避**:释放后各等一个随机时间再试,节奏一错开,总有一个先拿齐。

### 破坏不可剥夺条件

规定:**一个已占有资源的进程,申请新资源得不到满足时,必须释放它已占有的全部资源,以后需要时再重新申请。** 相当于它的资源被"剥夺"了。

代价是实现复杂,而且被剥夺的进程前面的工作可能白做,反复申请、释放还会降低系统吞吐。只适合状态容易保存和恢复的资源。

工程上最常见的形式是**超时**:获取锁时设置超时,等太久就放弃并释放已持有的资源。分布式系统里没人能看清全局,也没法统一加锁顺序,只能靠超时兜底。

### 破坏循环等待条件:有序资源分配法

把系统里所有资源**按类型编号**,规定每个进程**只能按编号递增的顺序申请资源**:已经占有了 5 号资源的进程,只能再申请编号大于 5 的资源。

为什么这样环就闭不上?假设真形成了一个环 P0 → P1 → … → Pn → P0,每个进程都占着一个资源、等下一个进程占着的资源。按规则,每个进程等的资源编号都比它占着的大,沿着环走一圈,编号一路严格变大,最后又回到 P0 占着的那个资源——它的编号必须比自己还大,矛盾。所以环不可能存在。

这是**四种预防方法里最实用的一种**,比静态分配的资源利用率高得多。缺点是编号要事先定好,新增资源类型不方便;进程实际用资源的顺序和编号顺序不一致时,只能提前申请大编号资源,造成一定浪费。

写程序时,这就是**规定加锁顺序**。最典型的场景是两个账户互相转账:A 转给 B 先锁 A,B 转给 A 先锁 B,两笔同时执行就是标准的死锁。解法是**不管谁转给谁,一律先锁 ID 小的**:

```
transfer(from, to, 金额):
    first, second = from, to
    if from.id > to.id:
        first, second = to, from      ← 所有线程的加锁顺序一致
    lock(first); lock(second)
    from.余额 -= 金额; to.余额 += 金额
    unlock(second); unlock(first)
```

转账、库存调拨这类同时锁两个对象的操作,都按 ID 或地址排序加锁。工程上预防死锁,九成靠这一条。

## 死锁避免:银行家算法

预防是在设计时就把路堵死,限制太严。**避免**换了个思路:不限制进程怎么申请,但**每次分配资源之前先算一算,这次分出去之后系统还安不安全**,不安全就不分,让进程先等着。

### 安全状态

**安全状态:系统能找到一个进程执行顺序 <P1, P2, …, Pn>(叫安全序列),按这个顺序给每个进程分配它还需要的资源,每个进程都能顺利运行完。** 找不到这样的序列,就是**不安全状态**。

两个关系要记清楚:

- **安全状态一定不会死锁。**
- **不安全状态不一定会死锁**,只是有可能。比如某个进程声明最多要 10 台磁带机,实际只用了 3 台就结束了。但系统没法预知,只能保守地把不安全状态当成危险来避开。

避免的核心就是:**系统永远只在安全状态之间转换。**

### 银行家算法的思路

这个算法由 Dijkstra 提出,名字来自一个比喻:银行家手里有一笔钱,要借给几个客户。每个客户事先说好最多借多少(信用额度),可以分几次借,借够额度、办完事之后一次全还。银行家每次放款前都要确认:放了这笔之后,手里剩下的钱,还能保证按某个顺序让所有客户都借够额度。能保证才放款。

对应到操作系统:钱是资源,客户是进程,信用额度是进程声明的最大需求。

### 数据结构

设系统有 n 个进程、m 类资源:

```
Available[j]        可用资源向量:第 j 类资源现在还剩几个
Max[i][j]           最大需求矩阵:进程 i 最多需要几个第 j 类资源
Allocation[i][j]    分配矩阵:进程 i 已经拿到几个第 j 类资源
Need[i][j]          需求矩阵:进程 i 还需要几个第 j 类资源

Need[i][j] = Max[i][j] - Allocation[i][j]
```

### 安全性算法:判断当前是否安全

```
1. Work = Available            ← Work 表示"假设当前能用来分配的资源"
   Finish[i] = false(所有 i)
2. 找一个进程 i,满足 Finish[i] == false 且 Need[i] ≤ Work
   找不到就跳到第 4 步
3. 假设它拿到资源、运行完、全部归还:
   Work = Work + Allocation[i]
   Finish[i] = true
   回到第 2 步
4. 所有 Finish[i] 都为 true → 安全,刚才的选择顺序就是安全序列
   否则 → 不安全
```

第 3 步加的是 `Allocation[i]` 而不是 `Need[i]`:进程拿到它还需要的那部分资源后,手里就是 `Max[i]`;运行完全部归还,Work 相当于先减 `Need[i]` 再加 `Max[i]`,净增 `Allocation[i]`。

### 资源请求算法:来了一个请求怎么办

进程 i 发出请求向量 `Request[i]`:

```
1. 如果 Request[i] > Need[i]       → 出错,超过了它自己声明的最大需求
2. 如果 Request[i] > Available     → 资源不够,进程 i 等待
3. 试探着分配:
     Available     = Available - Request[i]
     Allocation[i] = Allocation[i] + Request[i]
     Need[i]       = Need[i] - Request[i]
4. 对新状态执行安全性算法:
     安全   → 正式分配
     不安全 → 撤销第 3 步的试探分配,进程 i 等待
```

### 一个完整的例子

系统有 5 个进程 P0~P4,3 类资源 A、B、C,总数分别是 10、5、7。某一时刻的状态:

```
          Allocation     Max        Need       Available
          A  B  C      A  B  C    A  B  C      A  B  C
   P0     0  1  0      7  5  3    7  4  3      3  3  2
   P1     2  0  0      3  2  2    1  2  2
   P2     3  0  2      9  0  2    6  0  0
   P3     2  1  1      2  2  2    0  1  1
   P4     0  0  2      4  3  3    4  3  1
```

Need 由 Max 减 Allocation 得到。Available = 总数减去已分配的总和 = (10,5,7) − (7,2,5) = (3,3,2)。

**问题一:当前状态安全吗?**

从 Work = (3,3,2) 开始,每次找一个 Need ≤ Work 的进程:

```
         Work       Need      满足?   运行完后 Work = Work + Allocation
P1    (3,3,2)    (1,2,2)     ✓       (3,3,2) + (2,0,0) = (5,3,2)
P3    (5,3,2)    (0,1,1)     ✓       (5,3,2) + (2,1,1) = (7,4,3)
P4    (7,4,3)    (4,3,1)     ✓       (7,4,3) + (0,0,2) = (7,4,5)
P2    (7,4,5)    (6,0,0)     ✓       (7,4,5) + (3,0,2) = (10,4,7)
P0   (10,4,7)    (7,4,3)     ✓       (10,4,7) + (0,1,0) = (10,5,7)
```

所有进程都能完成,存在安全序列 **<P1, P3, P4, P2, P0>**,当前状态安全。最后 Work 回到 (10,5,7),正好是资源总数,可以用来验算。安全序列不一定唯一,第一步之后选 P3 或 P4 都可以。

**问题二:P1 请求 (1,0,2),能不能分?**

```
1. Request (1,0,2) ≤ Need[P1] (1,2,2)     ✓
2. Request (1,0,2) ≤ Available (3,3,2)    ✓
3. 试探分配:
     Available       = (3,3,2) − (1,0,2) = (2,3,0)
     Allocation[P1]  = (2,0,0) + (1,0,2) = (3,0,2)
     Need[P1]        = (1,2,2) − (1,0,2) = (0,2,0)
4. 安全性检查,Work 从 (2,3,0) 开始:
     P1  Need (0,2,0) ≤ (2,3,0)  ✓  Work = (2,3,0) + (3,0,2) = (5,3,2)
     P3  Need (0,1,1) ≤ (5,3,2)  ✓  Work = (5,3,2) + (2,1,1) = (7,4,3)
     P4  Need (4,3,1) ≤ (7,4,3)  ✓  Work = (7,4,3) + (0,0,2) = (7,4,5)
     P0  Need (7,4,3) ≤ (7,4,5)  ✓  Work = (7,4,5) + (0,1,0) = (7,5,5)
     P2  Need (6,0,0) ≤ (7,5,5)  ✓  Work = (7,5,5) + (3,0,2) = (10,5,7)
```

找到安全序列 <P1, P3, P4, P0, P2>,**可以分配**。

**问题三:接着 P0 请求 (0,2,0),能不能分?**

此时 Available 是 (2,3,0)。

```
1. Request (0,2,0) ≤ Need[P0] (7,4,3)     ✓
2. Request (0,2,0) ≤ Available (2,3,0)    ✓
3. 试探分配后 Available = (2,1,0),Need[P0] = (7,2,3)
4. 安全性检查,Work = (2,1,0):
     P0  Need (7,2,3)   ✗
     P1  Need (0,2,0)   ✗  B 类要 2 个,只剩 1 个
     P2  Need (6,0,0)   ✗
     P3  Need (0,1,1)   ✗  C 类一个都没有了
     P4  Need (4,3,1)   ✗
```

一个进程都推进不了,分配后系统进入不安全状态,所以**不分配**,撤销试探,P0 等待。注意:此时资源明明够给 P0,系统却拒绝了,这就是避免的代价——为了安全,宁可让资源闲着。

### 为什么实际系统很少用

银行家算法要求每个进程**事先声明最大需求**,而且进程数、资源数要固定。现实中的程序将来要加哪些锁、开多少文件,往往运行前根本不知道;每次分配都跑一遍 O(m × n²) 的安全性检查,开销也不小。所以它是理解"安全状态"的最好工具,但在通用操作系统里基本不用。

## 死锁检测:资源分配图

既不预防也不避免,允许死锁发生,但要能发现它。

### 资源分配图

用一张有向图描述"谁占着什么、谁在等什么":

- **圆圈表示进程**,**方框表示资源类**,方框里的圆点表示这类资源有几个。
- **请求边**:进程 → 资源,表示进程在申请这类资源的一个。
- **分配边**:资源 → 进程,表示这类资源的一个已经分给了这个进程。

开头的 P1、P2 争打印机和磁带机,画出来是:

```
        分配              请求
  R1 ──────────▶ P1 ──────────▶ R2
  ▲                              │
  │ 请求                         │ 分配
  │                              ▼
  └──────────── P2 ◀─────────────┘
```

### 资源分配图的化简

判断有没有死锁,用**化简**:

```
1. 在图中找一个既不阻塞、也不孤立的进程:
   它的每一条请求边,对应的资源都有空闲的,可以立刻满足
2. 假设它拿到资源、运行完、释放全部资源:
   删掉它所有的请求边和分配边,它变成孤立点
3. 释放出来的资源可能让别的进程不再阻塞,回到第 1 步继续
4. 直到找不到可以化简的进程为止
```

**死锁定理:如果资源分配图能被完全化简(所有边都能删掉),系统就没有死锁;不能完全化简,就处于死锁状态,剩下那些删不掉边的进程就是死锁进程。**

化简的思路和银行家算法的安全性检查一模一样:都是"找一个能完成的进程,假设它完成并归还资源,再看下一个"。区别是检测用的是进程**当前的请求**,避免用的是进程**将来最多的需求**。

### 有环一定死锁吗

- **每类资源只有一个**时:图中有环 ⇔ 死锁。检测就退化成在有向图里找环,用深度优先搜索找回边,或者做拓扑排序(排不完说明有环)。
- **每类资源有多个**时:**有环不一定死锁**。

看一个有环但不死锁的例子。R1 和 R2 各有 2 个:

```
R1(2 个):一个分给 P2,一个分给 P3
R2(2 个):一个分给 P1,一个分给 P4
P1 请求 R1,P3 请求 R2

环:P1 → R1 → P3 → R2 → P1
```

图里有环,但 P2 和 P4 不在环上、也不等任何资源。P4 运行完释放 R2,P3 就能拿到 R2;P2 运行完释放 R1,P1 就能拿到 R1。化简能完全进行,没有死锁。这正好说明四个必要条件都成立时,也不一定死锁。

### 什么时候检测

检测有开销,不能时时刻刻做。常见的时机:每次有进程因申请资源被阻塞时检测;定时检测;CPU 利用率异常下降时检测(大量进程卡死时 CPU 会闲下来)。

---

## 死锁解除

检测到死锁后,要把环打开,常用两种办法:

**撤销进程。** 最简单粗暴的是撤销所有死锁进程;温和一点是**一个一个撤销**,每撤销一个就重新检测,直到死锁解除。挑谁先撤销,一般看代价:优先级低的、已经运行时间短的、占用资源多的、还需要资源多的、交互式还是批处理……代价越小越先撤。

**剥夺资源。** 从一个或几个进程手里强行收回资源,分给死锁进程。要解决三个问题:剥夺谁的(代价最小的);被剥夺的进程怎么办(**回滚**到某个安全的检查点重新执行,最简单是从头开始);怎么防止饥饿(同一个进程不能总被选中,把被回滚的次数也算进代价)。

**数据库是这套"检测 + 解除"用得最好的地方。** MySQL 的 InnoDB 在事务等锁时检测等待图里有没有环,发现死锁就回滚其中代价较小的事务,另一个事务继续执行。它敢这么做,是因为事务有回滚机制,撤销一个事务不会留下改了一半的数据。业务里偶尔看到 "Deadlock found when trying to get lock",应用重试这个事务即可。普通程序里的线程没有回滚能力,撤销到一半的线程留下的数据没法收拾,所以很少这么做。

## 哲学家就餐问题

五个哲学家围坐圆桌,每两人之间一根筷子,共五根,每人要用左右两根才能吃饭。

```
            哲学家1
       筷子5       筷子1
  哲学家5                哲学家2
     筷子4            筷子2
       哲学家4  筷子3  哲学家3
```

如果每人都先拿左边、再拿右边,五个人同时拿起左边那根,右边那根都在邻居手里,谁也吃不上。四个条件全满足:筷子不能共用(互斥),拿着左边等右边(占有并等待),不能抢邻居的(不可剥夺),五个人等成一圈(循环等待)。解法也对应着破坏某个条件:

- **改一个人的顺序**:哲学家 5 先拿右边再拿左边,环在他这里断开。这其实就是有序资源分配:给筷子编号,每人都先拿编号小的那根(破坏循环等待)。
- **最多让四个人同时上桌**:用一个初值为 4 的信号量控制。五根筷子、四个人,至少有一人能拿到两根(破坏循环等待)。
- **左右两根都空着才一起拿起**:要么同时拿两根,要么一根都不拿(破坏占有并等待)。

## 死锁、活锁、饥饿

| | 例子 | 进程在干什么 | 有没有进展 |
|---|---|---|---|
| 死锁 | 持 A 等 B,持 B 等 A | 都阻塞不动 | 谁都没有 |
| 活锁 | TryLock 失败后同步重试 | 都在运行 | 谁都没有 |
| 饥饿 | 锁总被新来的抢走,等待中的一直轮不到 | 别人正常干活 | 只有某一个没有 |

死锁要破坏四个条件之一;活锁要加随机性;饥饿靠公平机制,比如等太久就强制排队。

---

## 分布式锁

多个实例共享一份资源,先在一个中心服务(Redis、etcd、ZooKeeper)登记"归我用",用完删除,这就是分布式锁。它比单机难在两点:没有一个地方能看清全局的等待关系;持锁方可能宕机或断网,锁记录还在,别人用不了,还分不清它是真挂了还是网络不通。

对应的做法:

- **锁要有过期时间**,持锁方失联后别人也能拿到。但时长难定:太短,活没干完锁就过期,两个实例同时操作;太长,真出事要等很久。
- **快到期可以续期**,但网络断一阵、续期失败、锁过期、别人接手,网络恢复后它还以为锁归自己。
- **每次加锁发一个递增令牌**(fencing token)。实例 2 拿到 41 号,实例 3 后来拿到 42 号,被保护的资源只认见过的最大编号,"复活"的实例 2 拿着 41 号来写,一律拒绝。

这套说法出自 Martin Kleppmann 的《How to do distributed locking》,核心观点是:**只靠过期时间不够,必须让被保护的资源自己检查令牌。** 更好的办法是尽量不用分布式锁,交给一个服务串行处理,或者把请求排队逐个处理。

## 关联

以下以 Go 1.26 为准。

**Go 只能发现"全体都睡死"的死锁。** 所有 goroutine 都阻塞时,runtime 报 `fatal error: all goroutines are asleep - deadlock!`;只要还有一个在动(HTTP 服务器等新连接、定时任务在 sleep),它就认为程序活着。线上服务基本指望不上这个检测,这就是前面说的"鸵鸟算法"。

**Go 里常见的死锁写法:**

- 无缓冲 channel 自己发、自己收:`ch <- 1` 就卡住,后面的 `<-ch` 永远执行不到。这正是前面"消耗性资源死锁"的样子。
- `for v := range ch` 等着接收,发送方发完却忘了 `close(ch)`,循环永不结束。
- 同一个 goroutine 对 `sync.Mutex` 连续 `Lock` 两次。Go 的锁不可重入,自己等自己。
- 方法 A 持锁调用方法 B,B 又加同一把锁。约定解法是拆出不加锁的内部版本,加 `Locked` 后缀(如 `updateLocked`),表示"调用者必须已持有锁"。

**同时锁两个对象,按 ID 排序。** 支付、库存、跨链桥里同时更新两边余额,都按前面转账的写法来,这是有序资源分配法在代码里的样子。

**持锁时不等外部资源,等待都带超时。** 持着锁去连接池取连接、调 RPC,很容易和别处形成环。可能阻塞的调用都应能被 `context` 超时打断,这是在破坏"不可剥夺"。

**服务卡住时怎么查。** 开 pprof 后访问 `/debug/pprof/goroutine?debug=2`,列出所有 goroutine 的栈,看方括号里的状态和等待时长,比如 `[sync.Mutex.Lock, 5 minutes]`、`[chan receive, 5 minutes]`,等了几分钟的就是嫌疑对象,栈会直接指出卡在哪一行。没开 pprof 时发 `kill -QUIT <pid>`,Go 程序会打出所有栈再退出。Go 1.26 还有实验性的 goroutine 泄漏分析(`GOEXPERIMENT=goroutineleakprofile` 构建,对应 `/debug/pprof/goroutineleak`)。平时监控盯着 `runtime.NumGoroutine()`,只涨不跌通常就是泄漏或死锁。

**能不用分布式锁就不用。** 多个实例给同一个地址分配递增序号(链上交易的 nonce),交给专门的服务串行发号,比抢一把 Redis 锁可靠得多。

## 总结

```
死锁:一组进程互相等待只有组内其他进程才能引发的事件
  │ 只发生在不可剥夺资源上(可重用的锁、打印机,消耗性的消息都可能)
  ▼
原因:资源竞争(前提) + 进程推进顺序不当(触发)
  ▼
四个必要条件,缺一不可:
  互斥 + 占有并等待 + 不可剥夺 + 循环等待
  ▼
四种处理方法:
  │ 预防:破坏条件之一
  │   互斥        → 一般做不到(SPOOLing 是特例)
  │   占有并等待  → 静态分配 / 拿不齐就全放下(小心活锁)
  │   不可剥夺    → 申请不到就释放已有的 / 超时
  │   循环等待    → 有序资源分配(最实用,= 按顺序加锁)
  │ 避免:银行家算法,只在安全状态之间转换
  │   安全一定不死锁,不安全不一定死锁
  │ 检测:资源分配图化简,不能完全化简 = 死锁
  │   单个资源:有环即死锁;多个资源:有环不一定
  │ 解除:撤销进程 / 剥夺资源(数据库靠事务回滚)
  ▼
现实:操作系统多用鸵鸟算法,预防靠程序员按顺序加锁
```

最该记住的几句话:

- **死锁是一组进程各占着资源、又等着别人占着的资源,等成了一个环。**
- **四个条件是必要条件**:都成立才可能死锁,破坏任意一个就一定不会死锁。
- **有序资源分配法是最实用的预防**,写代码时就是:同时锁两个东西,永远按固定顺序。
- **银行家算法的核心是安全状态**:分配前先找安全序列,找不到就不分;安全一定不死锁,不安全不一定死锁。
- **资源分配图能完全化简就没有死锁**;每类资源只有一个时,有环就是死锁。
- **死锁、活锁、饥饿是三种病**:都不动、都在动但没进展、只有一个一直轮不到。
