## Summary

上一篇,经理给每个厨房发了一套从 1 号编起的柜号,又给每个厨房做了一张"柜号 → 冷藏室真实格子"的对照表,冷藏室门口的管理员按表替厨师取东西。

这个办法解决了隔离、编号写死、碎片三个麻烦,但它刚运转起来,就暴露出两个新问题:

- **对照表太厚了。** 每个厨房都登记了十几万个柜号,一张表比冷藏室里的货还占地方。
- **查表太慢了。** 厨师每取一样东西,管理员都要去翻一次表。厨房最忙的时候,一秒钟要取几十次东西,大家都在门口排队等管理员翻表。

这一篇讲的就是这两个问题的解法:第一个靠**多级页表**,第二个靠 **TLB**。

---

## 对照表比冷藏室还大

先算一笔账,看看这张表到底有多厚。

经理是按整格登记的,一格对应计算机里的一页,4KB。一个进程的虚拟地址空间有 256TB(48 位地址),按 4KB 一页切开:

```
虚拟页的数量 = 256TB / 4KB = 2^48 / 2^12 = 2^36 ≈ 687 亿页
每一页在表上占一行,一行 8 字节
整张表      = 2^36 × 8 字节 = 512GB
```

**一个进程光是对照表就要 512GB,而且每个进程都要一份。** 这显然不可能。

每个厨房虽然登记了巨大的柜号范围,但真正用到的只有很少一部分。一个普通程序可能只用了几 MB 到几 GB,256TB 的地址空间里绝大部分从来没碰过。可是一张从头到尾挨个列出所有柜号的表,不管用没用到,每个柜号都得占一行。

就好比一家小面馆只用了 30 个柜子,经理却给它印了一本 687 亿行的对照表,其中 686 亿多行写的都是"未分配"。

---

## 把一本厚表拆成几级目录

经理想到了查字典的办法。一本字典不会把所有字排成一长串让你从头翻,而是先按部首分,部首下面再按笔画分,一级一级缩小范围。没有字的部首,字典里根本不印那一页。

对照表也可以这样拆:**先按大的区段分,区段下面再分小区段,一级一级往下。哪个区段一个柜子都没用,就不给它建下一级目录,上一级目录里在这一行写一个"空"就行。**

```
总目录(第 1 级)
  ├─ 第 0 区:有东西 → 第 0 区的分目录(第 2 级)
  │                     ├─ 第 0 段:有东西 → 再下一级……
  │                     ├─ 第 1 段:空
  │                     └─ ……
  ├─ 第 1 区:空           ← 整个区一个柜子都没用,下面一页目录都不建
  ├─ 第 2 区:空
  └─ ……
```

小面馆只用了 30 个柜子,这 30 个柜子集中在一两个区段里。它的对照表只需要一页总目录、几页分目录、几页最底层的明细,加起来几页纸;其余几百亿个没用的柜号,都被上层目录里的一个"空"字一笔带过。

### x86-64 的四级目录

真实的 x86-64 CPU 用的就是四级目录。一个 48 位的虚拟地址,被切成五段:

```
 47      39 38      30 29      21 20      12 11           0
┌──────────┬──────────┬──────────┬──────────┬──────────────┐
│ 第1级(9)  │ 第2级(9) │ 第3级(9)  │ 第4级(9)  │ 页内偏移(12)  │
└──────────┴──────────┴──────────┴──────────┴──────────────┘
   查总目录   查二级目录  查三级目录  查明细表     不翻译,原样保留
```

每一级用 9 位做索引,所以每张目录有 2^9 = 512 行;每行 8 字节,一张目录正好是 512 × 8 = 4KB,**和一页一样大**。这是有意这样设计的:目录本身也存在内存里,正好占一页,内核可以像管理普通页一样分配和管理它们。

Linux 给这四级起了名字,从上往下依次是 PGD、PUD、PMD、PTE。较新的 CPU 还支持五级页表,虚拟地址扩展到 57 位,原理完全一样,只是多了一层目录。

### 一次翻译的完整过程

CPU 里有一个寄存器叫 `CR3`,存着当前进程总目录的物理地址,相当于管理员手里拿着"现在是哪个厨房的对照表"。

```
CR3:当前厨房的总目录在哪
  │
  ├─ 用第 1 段查总目录 ──────▶ 得到二级目录的位置
  ├─ 用第 2 段查二级目录 ────▶ 得到三级目录的位置
  ├─ 用第 3 段查三级目录 ────▶ 得到明细表的位置
  └─ 用第 4 段查明细表 ──────▶ 得到物理页号
                                    │
                    物理页号 + 页内偏移 = 物理地址
```

这个一级一级往下查的过程叫 **page walk**(页表遍历)。

### 省了多少

一个只用了 8MB 内存的小程序,对照表大概是这样:

```
总目录      1 张  4KB    512 行里只有 1 行不是"空"
二级目录    1 张  4KB
三级目录    1 张  4KB
明细表      4 张  16KB   每张管 512 页 × 4KB = 2MB,8MB 要 4 张
───────────────────────
合计        7 张  28KB
```

从 512GB 降到 28KB,省掉了两千万倍。

这种"数据极其稀疏时,用树代替一张大平表,只为存在的部分建节点"的思路,要牢牢记住,在后面的工作中,比较实用。

## 查一次要翻四本目录:太慢了

多级目录省了纸,却带来了新问题:**以前查一次表翻一页,现在要翻四页。**

对计算机来说,每翻一页目录就是一次内存访问。程序本来只想读一个变量,结果先要访问 4 次内存去查页表,第 5 次才真正读到变量,访问内存的速度直接慢了好几倍。程序每执行几条指令就要访问一次内存,这个代价没法接受。

### 厨师手背上的几行字

厨房里的厨师很快想出了对策。

一个厨师在做一道菜的那段时间里,反复要取的就是那么几样东西:酱油、葱姜、正在腌的那盆肉。第一次取的时候,管理员翻完四本目录,告诉他"7 号柜就是 352 号格"。厨师顺手把这一条写在手背上。下次再要 7 号柜,他看一眼手背,直接去 352 号格拿,不用再排队等管理员翻目录。

手背就那么大,只能写几十行。写满了,就把最久没用到的那一行擦掉,写新的。

计算机里,这块"手背"是 CPU 里一小块专门的高速缓存,叫 **TLB**(Translation Lookaside Buffer,中文常叫"快表"),存着最近用过的"虚拟页号 → 物理页号"。

```
CPU 要访问一个虚拟地址
  │
  ├─ 先看 TLB
  │    命中:直接得到物理地址,大约 1 纳秒
  │    没命中:老老实实 page walk 查四级页表,几十到上百纳秒
  │           查到之后写进 TLB,下次就能命中
  ▼
用物理地址访问内存
```

TLB 很小,一级 TLB 通常只有几十个条目,二级 TLB 也就一两千个。但它的命中率通常在 99% 左右,因为两件事:

**程序访问内存很有规律。** 刚用过的东西很快会再用(循环里的变量、栈上的局部变量),用了一个地址,很快会用它旁边的地址(遍历数组、顺序执行的代码)。厨师做一道菜,来来回回也就取那几个柜子。这叫**局部性**。

**一行记录管一整页。** TLB 里记的是"哪一页对应哪一页",一条记录就覆盖了 4KB。顺着一个数组往下读,读完 4KB 才需要换下一条记录。

有了 TLB,99% 的翻译只要 1 纳秒,多级页表的代价几乎感觉不到了。**多级页表负责省空间,TLB 负责把速度找回来**,两者缺一不可。

### 换厨房,手背就得擦干净

厨师被调去另一个厨房干活,手背上写的"7 号柜 = 352 号格"立刻就作废了:那是上一个厨房的 7 号柜,新厨房的 7 号柜对应的是完全不同的格子。不擦掉的话,他会拿错别人的东西。所以每次换厨房,手背上的字都要全部擦掉,在新厨房重新一条条攒起来。

这就是"切换进程比切换线程贵"的主要原因:进程切换要换页表,TLB 里的旧记录全部作废,接下来很长一段时间几乎每次访问内存都要重新 page walk,直到 TLB 重新攒满常用的记录。同一个进程里的线程共用一张页表,换线程不用擦手背。

后来的 CPU 想了个办法:每条记录前面写上是哪个厨房的(这个标记叫 **PCID**)。换厨房时不用全擦,只是暂时不看别的厨房的那几行;过一会儿换回原来的厨房,原来那几行还能接着用。

### 工作区太大,手背写不下

做一道家常菜,手背上几十行足够。可如果厨房接了一桌满汉全席,一顿要用到上千个柜子的东西,手背就写不下了:刚写上的很快被擦掉,下次要用又得去等管理员翻目录。计算机里这叫 **TLB 抖动**,程序的大部分时间花在了查页表上。

算一下 TLB 能覆盖多大的内存:

```
二级 TLB 按 1536 个条目算:
  4KB 一页:1536 × 4KB = 6MB
```

一个程序如果频繁访问的数据有几十 GB(比如一个大的内存缓存),6MB 的覆盖范围远远不够。

解法是**把格子做大**。经理开放一种"大格":一格相当于原来的 512 格,按一整排货架登记。手背上一行就能管一整排:

```
  2MB 一页:1536 × 2MB = 3GB    覆盖范围变成原来的 512 倍
  1GB 一页:覆盖范围更大
```

大页还顺便少了一级目录:2MB 的页查到第三级就够了,page walk 从 4 次访存变成 3 次。

但大格也有代价:

- **浪费。** 分了一整排货架,哪怕只放了一瓶酱油,这一整排也被占着。
- **凑不出整排的时候要现整理。** Linux 有一种**透明大页**(THP),由经理自动把零散的小格凑成整排给厨房用,厨房什么都不用改。问题是冷藏室用久了,空格子东一个西一个,经理为了凑出一整排连续的空货架,可能要临时把别的东西挪来挪去,这期间来取东西的厨师就得等。反映到程序上,就是偶发的、找不到原因的延迟尖峰。

所以 Redis 这类对延迟很敏感的软件,官方文档都建议关闭透明大页,或者改成只有程序明确申请时才用(`madvise` 模式);确实需要大页的程序,更愿意事先手动预留好一批。

## 对照表每行后面的备注栏

对照表的每一行,除了写"对应哪个格子",后面还有一栏备注,打着几个勾。这几个勾,撑起了后面好几个重要的机制:

| 备注 | 意思 | 用来做什么 |
|---|---|---|
| 在不在 | 这一格的东西现在在冷藏室里吗 | 不在就触发缺页,去冷库取或现分配(按需分配、换页) |
| 能不能改 | 只许看,还是可以往里放东西 | 写时复制:先标"只许看",谁要改再单独复制 |
| 厨师能不能碰 | 普通厨师能用,还是只有经理能用 | 保护经理办公室的东西 |
| 最近用过没 | 有人来取过就自动打勾 | 冷藏室满了,优先把没打勾的挪去冷库 |
| 改过没 | 放进去之后有没有动过 | 挪去冷库时,没改过的直接扔掉就行,冷库里还有原样;改过的得先存一份回去 |
| 能不能当菜谱念 | 这一格里的东西能不能当作做菜步骤来执行 | 防止有人把"毒菜谱"塞进食材格子里让厨师照着做 |

翻译成计算机里页表项(PTE)的标志位,分别是 P(Present)、R/W、U/S、A(Accessed)、D(Dirty)、NX(No Execute)。

"最近用过没"和"改过没"这两个勾,是**硬件在访问内存时自动打上的**,不用软件操心。下一篇讲换页算法时,会看到内核怎么用"最近用过没"这个勾,以几乎零成本挑出该挪去冷库的格子。

最后那个 NX 是一道重要的安全防线。攻击者利用缓冲区溢出,把一段恶意指令写进程序的栈里,再想办法让 CPU 跳过去执行。有了 NX,栈和堆所在的页都标着"不能执行",CPU 跳过去也会被直接拦下。

看到这里能感觉到:虚拟内存不只是"把编号翻译成地址",它是一整套内存管理和保护的框架。硬件提供了翻译和这几个标志位,内核在这之上实现了按需分配、写时复制、换页、内存保护,而这一切对程序都是透明的。

## 把饭馆翻译回计算机

**遍历顺序能让速度差好几倍。** 一个 4096 × 4096 的整数矩阵,在内存里是按行连续存放的。按行遍历,访问的地址一个挨一个,一页 4KB 里的数据全部用完才换下一页,TLB 一条记录用很多次;按列遍历,每读一个数就往后跳一整行(4096 × 8 字节 = 32KB),几乎每次访问都跨到了新的一页,TLB 和 CPU 缓存都频频落空。两种写法逻辑完全一样,实测速度常常差 5~10 倍。

**测量 TLB 未命中。** Linux 上有 `perf` 的话:

```bash
perf stat -e dTLB-load-misses,iTLB-load-misses ./your_program
```

`dTLB-load-misses` 很高,说明数据访问的跨度太大、太散,或者工作集远远超出了 TLB 的覆盖范围。

**查看大页设置。**

```bash
grep -i huge /proc/meminfo                          # 大页的数量和使用情况
cat /sys/kernel/mm/transparent_hugepage/enabled     # 透明大页:[always] madvise never
```

方括号括起来的是当前生效的选项。

**看一个进程用了多少大页。** `/proc/<进程号>/smaps` 里每一段地址都有一行 `AnonHugePages`,就是这一段里透明大页占了多少。

## 关联

**处理大量数据时,注意数据在内存里的排列。** Go 里遍历几百万条记录,`[]Record` 比 `[]*Record` 快得多:前者所有记录连续存放,顺着读下去 TLB 和缓存都很友好;后者存的是指针,真正的记录散落在堆的各处,每读一条都可能跳到另一页。代价是值切片拷贝起来更贵,所以适合"单条记录不大、以顺序遍历为主"的场景。结构体字段按大小排列、减少对齐填充,也是同一个道理:每条记录越小,一页里能装下的越多。

**偶发的延迟尖峰,透明大页是一个嫌疑对象。** 一个延迟敏感的服务出现找不到原因的毛刺,排查完 GC、CPU 限流之后,看一眼 `/sys/kernel/mm/transparent_hugepage/enabled`:如果是 `[always]`,可以试着改成 `madvise` 对比一下。

**页表和以太坊的 MPT 是同一种结构。** 都是把一个巨大的稀疏映射组织成多级树,用 key 的一段一段做逐级索引。区别在于 MPT 每个节点还存着子节点的哈希,可以对任何一条数据给出密码学证明。看懂了多级页表,再去看 MPT 会很熟悉。

## 总结

```
一张对照表从头列到尾
  │ 问题:256TB 地址空间,一个进程的表就要 512GB
  │ 根源:地址空间极其稀疏,绝大部分柜号根本没用
  ▼
拆成几级目录(多级页表)
  │ 没用的区段不建下级目录,小程序的表只要几十 KB
  │ x86-64 四级,每级 9 位、512 行,一张目录正好一页
  │ 新问题:查一次要翻四本目录,访存慢了好几倍
  ▼
厨师把常用的几条记在手背上(TLB)
  │ 靠局部性,几十到几千条就能命中 99%
  │ 换厨房要擦手背 → 进程切换贵的主要原因;PCID 给每行标上厨房名
  │ 工作区太大写不下 → TLB 抖动
  ▼
把格子做大(大页)
    一条记录管 2MB 甚至 1GB,还少一级目录
    代价:浪费;透明大页现凑整排会带来延迟尖峰
```

最该记住的几句话:

- **页表做成多级,是因为地址空间极其稀疏**:只为用到的部分建表。
- **多级页表省了空间,代价是一次翻译要访问好几次内存;TLB 用一小块缓存把这个代价几乎抹平。**
- **进程切换贵,主要贵在 TLB 失效**,不是保存寄存器那点工作。
- **工作集太大时 TLB 不够用,大页能把覆盖范围扩大几百倍**,但透明大页可能带来延迟尖峰。
- **页表项里的几个标志位**撑起了按需分配、写时复制、换页、内存保护。

## 动手练习

需要一台 Linux 机器,`perf` 需要安装(`apt install linux-tools-common linux-tools-$(uname -r)` 之类)。

1. **算一算你的程序的页表有多大。** `grep PageTables /proc/meminfo` 看全系统页表一共占了多少内存;`grep VmPTE /proc/<进程号>/status` 看某一个进程的页表占了多少。拿一个 RSS 几个 GB 的进程,对比它的页表大小和开始的 512GB。
2. **看看透明大页的状态。** `cat /sys/kernel/mm/transparent_hugepage/enabled`,再 `grep AnonHugePages /proc/meminfo` 看全系统有多少内存正在用透明大页。
3. **看 TLB 未命中。** 找一个现成的程序,比如 `perf stat -e dTLB-loads,dTLB-load-misses ls -R /usr > /dev/null`,看看未命中率是多少;再换一个吃内存的程序(比如对一个大文件跑 `sort`)对比。
4. **查一下自己 CPU 的 TLB 有多大。** Linux 上 `cpuid | grep -i tlb`(需要安装 `cpuid` 工具)或者 `x86info -c`,看一级、二级 TLB 各有多少条目,分别支持哪些页大小。
