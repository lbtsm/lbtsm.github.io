## Summary

"阻塞和非阻塞有什么区别?同步和异步呢?非阻塞是不是就是异步?"这组问题写后端的人几乎都绕不开,而常见的说法是把四个词搅成一锅:"阻塞就是同步,非阻塞就是异步。"这个答案是错的,错在没分清**一次 IO 到底有几段在等、每个词说的是哪一段**。

分清了这一点,五种 IO 模型、select/epoll、Reactor、Go 的 netpoll 就是一条线串下来的;线上那些怪现象——CPU 100% 却什么都没干、Go 程序线程数涨到几千、goroutine 只增不减、`kill -9` 杀不掉进程——也都能顺着它找到根因。

---

## 先搞清楚:一次 IO 到底在等什么

计算机里的"进货"就是 **IO**:收网络数据、读磁盘文件、往终端打印。CPU 算一次加法不到 1 纳秒,等一个跨机房的网络包要几十毫秒,相差几千万倍。所以 IO 的核心问题从来不是"怎么读",而是**"等的时候干什么"**。

以从网络连接上读数据为例,一次 `read` 其实分两段:

```
程序调用 read(连接, 我的缓冲区, 长度)
          │
          ▼
阶段一:等数据就绪                              ← 货在路上
   数据还在网络上传,内核等它到达网卡、
   放进这个连接的接收缓冲区(在内核内存里)
          │
          ▼
阶段二:拷贝数据                                ← 货到门口,搬进后厨
   内核把数据从自己的接收缓冲区,
   拷贝到程序给的缓冲区
          │
          ▼
read 返回,程序拿到数据
```

数据为什么非要先进内核、不直接送到程序手里?因为网卡收到一个包时,只有内核知道它属于哪条连接、哪个进程——这要查连接表、做协议校验;而程序的内存是程序自己的地盘,内核不会不请自来往里写。所以货一律先卸在饭馆门口(内核缓冲区),再由人搬进后厨(用户缓冲区)。

**阶段一慢且说不准,阶段二快且大致可预期。** 阶段一取决于对方什么时候发、网络有多堵,可能是 1 毫秒也可能是 1 小时;阶段二只是一次内存拷贝,通常是微秒级(数据量很大时也不是零成本。

后面所有的 IO 模型,区别**只在于这两个阶段里程序是干等、走开,还是让别人代劳**。记住这张两段图,整篇就不会乱。

## 讲模型前必须认识的几个词

IO 模型的讨论里反复出现这几个词:

- **文件描述符(fd)**:程序打开一个文件、建立一条连接,内核给它发一个小整数当"取货号",之后读写都报这个号。Linux 里网络连接、管道、终端、普通文件都是 fd,所以下面说"连接"的地方,很多时候换成"fd"也成立。
- **socket 缓冲区**:每条 TCP 连接在内核里有一个**接收缓冲区**和一个**发送缓冲区**。网卡收到的数据经协议栈处理后进接收缓冲区,`read` 从这里拷走;`write` 则是把数据拷进发送缓冲区就返回,真正发出去是内核的事。
- **`O_NONBLOCK`**:fd 上的一个标志位。没设它,fd 就是阻塞的;设了,就是非阻塞的。**阻塞还是非阻塞,是 fd 的属性,不是 `read` 函数的属性**——同一个 `read`,对不同 fd 行为不同。
- **`EAGAIN`**:非阻塞 fd 上"现在做不了,等会再试"的错误码,字面意思就是 try again。有的系统叫 `EWOULDBLOCK`(会阻塞),Linux 上两者数值相同。
- **阻塞态**:线程被内核挂起、移出运行队列,**不占 CPU**,等某个事件发生再被唤醒。`ps` 里显示为 `S`(可中断睡眠)或 `D`(不可中断睡眠)。

**一句话:阻塞/非阻塞是 fd 上的一个开关,决定阶段一数据没到时,线程是被挂起还是立刻拿到 `EAGAIN`。**

## 阻塞 IO:站在门口等

**阻塞 IO**:`read` 时数据没到,内核把线程挂起,CPU 让给别人;数据到了、拷贝完了再唤醒它,`read` 才返回。

```
线程:read ─────────────────────────────────────────▶ 拿到数据
       │← 阶段一:挂起等待,不占 CPU →│← 阶段二:拷贝 →│
```

> 放到饭馆里:厨师在门口坐下打盹,灶台让给别的厨师用;货到了有人叫醒他,他把货搬进后厨才回去干活。

Linux 上新建的 socket、打开的文件默认都是阻塞的。

阻塞的时候,线程是不占CPU的。这是一个很常见的误解——"阻塞 = 线程卡住 = CPU 被浪费"。实际上阻塞的线程已经被内核移出了运行队列,调度器根本不会选它,CPU 在跑别的线程。**阻塞浪费的不是 CPU,是线程本身。**

### 阻塞 IO 的问题?

**阻塞 IO 的好处是写起来简单**:代码就是一条直线,"读请求 → 处理 → 写回",不用考虑数据没到怎么办。

**问题是一个线程同一时刻只能等一个连接。** 厨师坐在 A 供应商的门口打盹,B 的货到了他也不知道。想同时服务一万个连接,就得有一万个线程,每个守一个门口。这就是著名的 **C10K 问题**(同时处理一万个连接,Concurrent 10K)。

一万个线程贵在哪?要算准:

- **栈内存**:Linux 默认给每个线程预留 8MB 栈(`ulimit -s`),一万个就是 80GB——但这是**虚拟地址**,物理内存只按真正用到的页分配,一个闲着的线程实际只占几十 KB。所以"一万线程要 80GB 内存"的说法不准确,64 位机器上虚拟地址并不缺。
- **真正的代价是调度和切换**:一万个线程轮流被唤醒、切换上下文,一次几微秒,还会冲掉 CPU 缓存和 TLB),连接越多,花在"切换"上的时间越多,花在"干活"上的越少。再加上内核为每个线程维护的数据结构、`pid_max` / `threads-max` 这些上限,线程数注定堆不到几十万。

**阻塞本身不是坏事,坏在"一个线程只能等一个连接",逼得你用线程数去堆连接数。**

## 非阻塞 IO:隔一会儿跑去门口看一眼

给 fd 设上 `O_NONBLOCK` 后,`read` 的行为变成:

```
数据已经到了  → 立刻拷贝,返回读到的字节数
数据还没到    → 立刻返回 -1,errno = EAGAIN("现在没有,等会再来")
```

注意:**非阻塞只改变了阶段一。** 数据到了之后,仍然是这次 `read` 自己把数据拷完才返回——阶段二一点没变。这一点后面区分"非阻塞"和"异步"时是关键。

### 为什么单纯的非阻塞比阻塞还差?

光有非阻塞,程序不想错过数据就只能不停地问,这叫**忙轮询**:

```
循环:
    read(连接)  → EAGAIN,没数据
    read(连接)  → EAGAIN,没数据
    read(连接)  → EAGAIN,没数据
    ……成千上万次……
    read(连接)  → 有数据了!
```

相当于厨师不坐下了,一趟趟往门口跑,跑一万趟可能只碰上一次货。问题有三层:

- **CPU 白烧。** 线程从不进入阻塞态,CPU 占用 100%,全是无用功。阻塞 IO 至少还把 CPU 让出去了。
- **每次 `read` 都是一次系统调用**,进出内核一次几十到几百纳秒,一秒问几百万次,时间全耗在路上。
- **连接一多更离谱。** 一万个连接,每一轮挨个问一万次,可能只有三个真有数据。

所以单纯的非阻塞轮询是最差的方案。它的价值在于**做零件**:下一节的多路复用离开它就跑不起来。

### 非阻塞 write:写一半就返回

阻塞 `write` 碰上发送缓冲区满,会等到腾出空间、把数据全写进去才返回;非阻塞 `write` 不等,**能写多少写多少,返回实际写入的字节数**,一点都写不进去才返回 `EAGAIN`。

```
要写 100KB,发送缓冲区只剩 30KB
  阻塞 write   → 等对端把数据收走、缓冲区腾出空间,写满 100KB 才返回
  非阻塞 write → 写进 30KB,返回 30720,剩下 70KB 你自己看着办
```

"自己看着办"的标准做法是:把没写完的部分存起来,向多路复用登记"这个连接**可写**时告诉我",等通知来了接着写。忘了处理返回值、以为 `write` 一次就写完,是非阻塞网络编程里最常见的丢数据 bug。

### 非阻塞 connect:握手还没完成

`connect` 要完成 TCP 三次握手,跨地域要几十上百毫秒。非阻塞的 `connect` 不等握手,立刻返回 -1 和 `EINPROGRESS`(进行中)。之后等这个 fd 变成**可写**,再用 `getsockopt(SO_ERROR)` 取结果——是 0 就连上了,否则就是连接失败的原因(比如 `ECONNREFUSED`)。

**"连接超时"就是这么实现的**:发起非阻塞 connect,然后只等可写事件 N 秒,等不到就算超时。阻塞的 connect 你没法自己控制等多久,只能吃内核的 SYN 重试时间(Linux 默认重试 6 次,一共两分钟出头)。

## IO 多路复用:请经理帮所有人盯着

厨师把要等的供应商列成一张单子交给经理:"这些人谁的货到了叫我。"然后他就安心去睡;经理一喊"3 号、77 号到了",他只去搬这两家。

这就是 **IO 多路复用**:程序把一批 fd 交给内核,调用一次 `select`、`poll` 或 `epoll_wait` 等着(线程挂起,不占 CPU);任何一个 fd 就绪,内核返回就绪的那几个,程序只对它们 `read`,每次都不扑空。

```
线程:epoll_wait(一万个连接) ───挂起等待───▶ 返回:3 号、77 号就绪
      read(3 号)   → 拿到数据
      read(77 号)  → 拿到数据
      回到 epoll_wait 继续等
```

关键转变:**等待的对象从"某一个连接"变成了"一批连接里的任意一个"。** 一个线程就能等一万个连接,这是 C10K 的标准答案。

### 为什么多路复用必须配合非阻塞 IO?

既然内核都说"3 号就绪了",再去读肯定有数据,fd 是不是阻塞的有什么关系呢?

关系在于:**"就绪"只是一个提示,不是保证。** 从内核报告就绪,到你真的去 `read`,中间有一段时间差,情况可能已经变了:

- 多个线程在等同一批连接,数据被另一个线程先读走了;
- 内核收到的数据校验出错,又被丢弃了;
- 你上一轮已经把数据读完了,缓冲区其实是空的。

这时如果 fd 是阻塞的,`read` 就会在一个空连接上一直等下去,而其他九千九百九十九个连接的数据到了也没人管——**一个卡住,全部停摆**。

由此得到一条铁律:**盯一批连接的那个线程,任何时候都不能被其中某一个连接卡住。** 非阻塞保证了这一点:没数据就立刻返回 `EAGAIN`,线程回到 `epoll_wait` 等下一批事件。

### 那多路复用算阻塞还是非阻塞?

要分开说:**线程阻塞在 `epoll_wait` 上,连接本身是非阻塞的。** 它并没有消灭等待,只是把"每个连接各等各的"换成了"一个线程在一个地方等所有连接"。所以说"用了 epoll 就没有任何线程阻塞"是不对的——`epoll_wait` 本身就是一个阻塞调用,只不过一次等一批。

## 信号驱动 IO 与异步 IO

### 信号驱动 IO:货到了按门铃

程序向内核登记"这个 fd 有数据时,给我发个 SIGIO 信号",然后去做别的事;收到信号,再调 `read` 去拷数据。相当于供应商到门口按铃,厨师还是得自己出去搬。

它很少用:信号处理函数里能安全做的事很少,写起来别扭;一个信号也说不清是哪个连接、来了多少数据,连接一多就乱。对 TCP 更是几乎没用——连接建立、收到数据、对方关闭、出错都会触发 SIGIO,程序分不清是哪种。它主要出现在少数 UDP 场景里。

### 异步 IO:货直接送进冰箱

前面几种做法,阶段二都是程序自己调 `read` 完成的。**异步 IO** 换了个思路:发起读请求时就把"读到哪个缓冲区"一并交给内核,调用立刻返回,程序去干别的;内核把**等待和拷贝两个阶段**都做完,再通知"数据已经在你的缓冲区里了"。

饭馆里就是:供应商有后厨钥匙,直接把货放进冰箱,然后发条消息"放好了"。厨师从头到尾没为进货停过手。

```
阻塞/非阻塞/多路复用/信号驱动:  内核说"可以读了"(就绪通知)  → 你自己去拷
异步 IO:                       内核说"已经读好了"(完成通知)→ 直接用
```

**就绪通知和完成通知的区别,就是同步和异步的分界线。**

### 五种 IO 模型放在一起

| 模型 | 阶段一:等数据 | 阶段二:拷贝 | 饭馆里 |
|---|---|---|---|
| 阻塞 IO | 挂起干等 | 自己拷,拷完才返回 | 坐门口打盹等 |
| 非阻塞 IO | 不等,没数据就返回 | 自己拷,拷完才返回 | 一趟趟跑门口看 |
| IO 多路复用 | 等在 select/poll/epoll 上(一次等一批) | 自己拷,拷完才返回 | 经理帮所有人盯着 |
| 信号驱动 IO | 不等,做别的事,等信号 | 自己拷,拷完才返回 | 到了按门铃 |
| 异步 IO | 不等 | 内核拷好再通知 | 直接送进冰箱 |

### 阻塞/非阻塞、同步/异步,到底怎么区分?

这是整篇最核心的结论,对着上面那张表看:

- **阻塞和非阻塞,说的是阶段一**:数据没到时,调用是挂起等待,还是立刻返回。
- **同步和异步,说的是阶段二**:数据的拷贝是你的线程自己做(做的时候你得等着),还是内核做完再通知你。

前四种模型的阶段二都得自己 `read`、拷的时候都要等,所以**全是同步 IO**;只有第五种是**异步 IO**。于是那个经典问题的答案就清楚了:**非阻塞不等于异步**——非阻塞 IO 数据到了还要自己拷,是"同步非阻塞"。

把两个维度交叉,就是一张 2×2 的表:

```
                 阶段一:阻塞                阶段一:非阻塞
              ┌────────────────────────┬───────────────────────────┐
  同步         │ 同步阻塞                │ 同步非阻塞                 │
 (自己拷)      │ 阻塞 IO                 │ 非阻塞 IO + 轮询           │
              │                        │ 非阻塞 IO + 多路复用(主流)   │
              ├────────────────────────┼───────────────────────────┤
  异步         │ 异步阻塞                │ 异步非阻塞                 │
 (内核拷好)    │ 提交后马上原地等结果,      │ 异步 IO(io_uring、IOCP)   │
              │ 等于白用异步,几乎没人这么写│                           │
              └────────────────────────┴───────────────────────────┘
```

还有两处常见的混淆,顺手理清:

- **Java 的 BIO / NIO / AIO**:BIO 就是阻塞 IO;NIO 是非阻塞 fd 加 `Selector`(底下是 epoll),也就是多路复用,不是异步;AIO(NIO.2 的 `AsynchronousChannel`)接口是异步的,但在 Linux 上是用 epoll 加线程池模拟的。Netty 用的是 NIO。
- **业务代码里的"异步"**:"这个接口是异步调用的""发个消息异步处理",说的是**调用方不等结果先返回**,是应用层的编程方式,和操作系统 IO 模型的"同步/异步"不是一个层面的事。讨论时先确认对方说的是哪一层。

### Linux 上的异步 IO,为什么一直不好用?

Windows 的 IOCP 很早就是成熟的异步 IO;Linux 在这方面走了很长的弯路:

- **POSIX AIO**(`aio_read` 那一套):glibc 在用户态开线程池,派线程替你做阻塞 IO,接口是异步的,底下还是在占线程。
- **Linux 原生 AIO**(`io_submit`,常配合 `libaio`):只有用 `O_DIRECT` 绕过页缓存读写文件时才真正异步,对网络基本没用,用途很窄。
- **io_uring**(Linux 5.1 起):真正好用的异步 IO。程序和内核共享两个环形队列:程序把"读什么、读到哪"写进**提交队列**,内核做完把结果写进**完成队列**。一次系统调用能提交成百上千个请求,开启内核轮询模式(SQPOLL)后甚至可以完全不进内核。文件和网络都支持。

io_uring 也不是魔法:有些操作内核没法真正异步完成时,会交给它内部的工作线程去做,并不保证"永远不阻塞任何线程"。它是近年 Linux IO 最重要的进展,数据库和高性能存储在逐步采用;但接口复杂、出过不少安全漏洞,一些环境(比如部分容器运行时的默认 seccomp 配置)会直接禁用它。所以**网络编程的主流至今仍是 epoll 加非阻塞 IO**。

## 普通文件为什么不能用 epoll

这是个不看内核想不到、但对 Go 程序影响很大的细节。

内核认为**普通文件永远是"就绪"的**:socket 的"未就绪"是数据还没从网络上来,而文件的数据就在磁盘上,"没有就绪"这个状态不存在——慢的是从磁盘读出来的那一下,那发生在 `read` 内部。

所以对普通文件调 `epoll_ctl` 会直接返回 `EPERM`,`select`、`poll` 则总是报告"可读"。结论是:**读普通文件只能阻塞**,线程会实打实地卡在磁盘读取上,多路复用帮不上忙。这正是 io_uring 想解决的问题之一,也是第 9 节里 Go 程序线程数暴涨的根源。

(管道、终端这类 fd 和 socket 一样有真正的"未就绪",可以用 epoll。)

## 线上排查:几个和 IO 模型有关的怪现象

和 TCP 的 TIME_WAIT、CLOSE_WAIT 一样,IO 模型的知识在排障时最能体现价值:

| 现象 | 多半是什么 | 怎么确认 |
|---|---|---|
| CPU 100%,但业务量很小 | 非阻塞 fd 在忙轮询 | `strace -p <pid>` 刷屏的 `read(...) = -1 EAGAIN` |
| 某连接 `Recv-Q` 一直很大 | 程序读得比数据来得慢,数据积压在内核接收缓冲区 | `ss -tn` 看 `Recv-Q` 列,正常应接近 0 |
| 某连接 `Send-Q` 一直很大 | 对端读得慢或网络堵,发送缓冲区写满 | `ss -tn` 看 `Send-Q`;非阻塞写会开始返回 `EAGAIN` |
| `kill -9` 杀不掉进程 | 线程卡在磁盘或 NFS 上,处于 `D` 状态,要等 IO 返回才能处理信号 | `ps -eLo pid,tid,stat,wchan:30,comm` 看 `STAT` 列是否为 `D` |
| Go 程序线程数涨到几百上千 | 大量 goroutine 同时做文件 IO 或 cgo,每个都占一个线程 | `/debug/pprof/goroutine?debug=2` 里大量 `[syscall]` |
| goroutine 数只涨不降 | 网络读写没设超时,对端不回也不断开,永远等下去 | goroutine dump 里大量 `[IO wait]`,且等待时间很长 |

`strace -p <进程号>` 是看"线程停在哪"的万能工具:阻塞 IO 停在 `read`,多路复用停在 `epoll_wait`,忙轮询则是满屏的 `EAGAIN`。

## 从 Go 的视角看

### 亲眼看一次 EAGAIN

用裸系统调用就能看到非阻塞 fd 的行为(Linux / macOS 都能跑):

```go
package main

import (
	"fmt"
	"syscall"
)

func main() {
	// 一对互相连通的 socket:往 fds[1] 写,从 fds[0] 读
	fds, err := syscall.Socketpair(syscall.AF_UNIX, syscall.SOCK_STREAM, 0)
	if err != nil {
		panic(err)
	}
	syscall.SetNonblock(fds[0], true) // 等价于 fcntl 加 O_NONBLOCK

	buf := make([]byte, 16)
	_, err = syscall.Read(fds[0], buf)
	fmt.Println(err == syscall.EAGAIN) // true:对面还没写,立刻返回而不是挂起

	syscall.Write(fds[1], []byte("hi"))
	n, _ := syscall.Read(fds[0], buf)
	fmt.Println(string(buf[:n])) // hi:数据到了,这次 read 自己拷完才返回
}
```

去掉 `SetNonblock` 那一行再跑,程序会卡在第一个 `Read` 上永远不动——这就是阻塞 IO。

### conn.Read 看起来是阻塞的,底下是非阻塞加 epoll

Go 的网络代码写起来是阻塞风格的一条直线:

```go
for {
	n, err := conn.Read(buf) // 看起来会阻塞
	if err != nil {
		return
	}
	handle(buf[:n])
}
```

但运行时做的事是这样的:

```
net.Dial / Accept 拿到 fd
  → 设成非阻塞,登记到运行时内部的 epoll(Linux)/ kqueue(macOS)

conn.Read
  → internal/poll.FD.Read 调 syscall.Read
      有数据   → 直接返回
      EAGAIN   → 把当前 goroutine 挂起(gopark),线程去跑别的 goroutine
  → 运行时调度循环和 sysmon 定期调 netpoll(底下就是 epoll_wait)
  → fd 就绪 → 把等它的 goroutine 放回运行队列 → 重新 Read,这次有数据
```

**写的是阻塞式代码,跑起来是"一个线程盯一批连接"的多路复用。** goroutine 挂起不占线程,所以一个 Go 服务挂着十万个空闲长连接也没问题。

### 网络 IO 和文件 IO 的并发要区别对待

普通文件不能用 epoll,所以 `os.ReadFile` 这类调用会让线程真的卡在系统调用里。运行时的应对是:sysmon 发现某个线程在系统调用里待太久,就把它手上的调度权(P)交给另一个线程,必要时新建线程顶上。同时读一千个文件,线程数就可能涨到几百上千;超过默认上限 10000 个(`debug.SetMaxThreads`),程序会直接崩溃退出。

所以:**网络 IO 的并发通常不用限,文件 IO 和 cgo 调用(比如 C 写的密码学库)要用固定大小的 worker 池限制并发。** 在 pprof 的 goroutine dump 里,`[IO wait]` 是在等网络、不占线程;`[syscall]` 才是真占着线程。

### 每一次网络 IO 都要有截止时间

阻塞式写法有个副作用:对端不回数据也不断开时,`conn.Read` 会永远等下去。goroutine 不占 CPU、不报错,就这样一个个积累起来——**没有超时的 IO 是 goroutine 泄漏的头号来源**。

```go
conn.SetReadDeadline(time.Now().Add(5 * time.Second))
n, err := conn.Read(buf)
if errors.Is(err, os.ErrDeadlineExceeded) {
	// 超时:决定是重试、换节点还是标记失败,不能只把 error 往上一抛了事
}
```

HTTP 客户端用 `http.Client{Timeout: ...}` 或带超时的 `context`;自己写的 TCP 协议用 `SetReadDeadline` / `SetWriteDeadline`。Go 的 deadline 就是在 netpoll 里挂了个定时器,到点把等待的 goroutine 唤醒并返回超时错误,成本很低,没有理由不设。

## 关联

- **区块链节点和 RPC 调用**:中继、监听服务要同时盯着多条链的 RPC 节点,每条链一个读循环。公共 RPC 节点慢、断连、TLS 握手卡住都是家常便饭,任何一次没设超时的调用都可能让整个读循环停住。每次调用设截止时间,超时后明确这件事的状态(待重试还是失败),是这类服务稳定运行的前提。
- **"盯一批的循环里不能有阻塞操作"不只适用于 epoll**:从 channel 消费事件的 worker、轮询多条链的调度循环,只要在循环里直接调一个没有超时的外部接口,一个慢请求就能让整个消费者停住。这和 5.1 节"一个卡住,全部停摆"是同一个道理。
- **P2P 网络**:节点之间维持成百上千条长连接同步区块、广播交易,libp2p 这类库底下就是多路复用加非阻塞 IO;Go 实现的节点(geth)靠 netpoll 让每个对等连接一个 goroutine 而不爆线程。
- **数据库与存储**:区块链节点的状态数据库(LevelDB、Pebble)大量读写本地文件,这部分走不了 epoll,是线程数和磁盘 IO 争用的高发区;io_uring 正是这类场景在逐步采用的方向。

## 总结

```
IO:要等外部数据,不知道等多久
  │ 一次读分两步:等数据就绪(慢、说不准)→ 从内核拷贝到程序(快)
  ▼
阻塞 IO:挂起干等(不占 CPU,但占线程)
  │ 好处:代码是一条直线
  │ 问题:一个线程只能等一个连接,一万连接一万线程(C10K)
  ▼
非阻塞 IO:没数据立刻返回 EAGAIN
  │ 问题:光这样用只会忙轮询,烧 CPU、系统调用多
  │ 坑:write 可能只写一部分,connect 返回 EINPROGRESS
  │ 价值:多路复用的零件
  ▼
IO 多路复用:一批连接交给内核,谁就绪了告诉我
  │ 一个线程等一批,只读就绪的;必须配非阻塞,"就绪"只是提示
  ▼
信号驱动:就绪时发 SIGIO(很少用)
  ▼
异步 IO:内核等待、拷贝都做完再通知(Linux 上直到 io_uring 才好用)
```

最该记住的几句话:

- **一次读分两个阶段:等数据就绪,再从内核拷贝到程序。** 第一阶段慢且说不准,第二阶段快。
- **阻塞和非阻塞说的是第一阶段**:没数据时挂起还是立刻返回。**同步和异步说的是第二阶段**:拷贝自己做,还是内核做完再通知。非阻塞不等于异步,前四种模型全是同步 IO。
- **阻塞 IO 的问题不在阻塞本身,而在一个线程只能等一个连接。** 阻塞的线程不占 CPU。
- **IO 多路复用让一个线程等一批连接,是 C10K 的标准答案;连接必须非阻塞,因为"就绪"只是提示。**
- **普通文件没有"未就绪",不能用 epoll,读文件只能阻塞。** 这决定了 Go 里文件 IO 要限并发、网络 IO 不用。
- **Go 的 `conn.Read` 写起来是阻塞的,跑起来是非阻塞加 epoll;代价是你必须自己给每次 IO 设超时。**

## 练习

以下需要一台 Linux 机器(第 1 题 macOS 也行)。

1. **跑一遍 9.1 的代码**,再删掉 `SetNonblock` 那行重跑,对比"立刻返回 EAGAIN"和"永远卡住"。
2. **看阻塞的线程停在哪。** 终端一 `nc -l 9000`(等连接),终端二 `strace -p $(pgrep -n nc)`,可见它停在 `accept` 或 `poll` 这类调用上;终端三 `nc localhost 9000` 连上去敲几个字回车,观察 strace 里出现的 `read`。
3. **看接收缓冲区堆了多少数据。** 在跑着服务的机器上 `ss -tn`,看 `Recv-Q`、`Send-Q`。绝大部分应为 0;某连接 `Recv-Q` 一直不为 0,说明程序来不及读。
4. **看成熟程序用哪种方式等。** 对 nginx、redis 执行 `strace -f -p <进程号> -e trace=epoll_wait,read,write`,它们大部分时间停在 `epoll_wait`,有事件才出现一串 `read`、`write`。
5. **看线程的睡眠状态。** `ps -eLo pid,tid,stat,wchan:30,comm | head -50`,`STAT` 列 `S` 是等事件,`D` 是卡在磁盘这类不可中断等待上;`WCHAN` 列是它睡在哪个内核函数里。
6. **看 Go 程序的线程数。** 写个程序开 500 个 goroutine 同时读大文件,另开 500 个 goroutine 各自挂一个空闲 TCP 连接,分别用 `ls /proc/<pid>/task | wc -l` 看线程数,对比两种 IO 的差别。
