## Summary

"Reactor 是什么?"最常听到的回答是"Reactor 就是 epoll"。顺着这个说法还会听到几句:"Go 没用 Reactor,它是一个连接一个 goroutine""回调就是异步""Redis 是单线程的,所以多核机器上它很慢"。这几句都不对,错在**把三个层次的东西混在了一起**:epoll 是操作系统提供的机制,Reactor 是围绕这个机制的一种程序分工方式,回调和 goroutine 是写业务代码的两种风格。epoll 只回答"哪些连接就绪了",至于就绪之后谁去读、谁去算、谁去写,是 Reactor 要回答的;而 Go 恰恰在运行时里藏了一个 Reactor,只是你看不见回调。

把这三层分开,下面这些线上现象就都能顺着找到原因:Redis 里一条 `KEYS *` 让所有客户端的延迟一起飙升;一台 32 核的机器上 Redis 只把一个核打满,其他核闲着;Netty 服务里有人在 handler 里查了一次数据库,整组连接都卡住;Go 服务挂着十万个长连接,线程数却只有十几个。

饭馆的故事接着讲。前面讲 IO 多路复用时,大厅装好了呼叫器,客人一按铃,面板上就亮起桌号,一个人就能照看上千桌。可面板只会亮灯,不会点菜、不会做菜、不会上菜——**亮灯之后这家店怎么分工**,就是本文要讲的。

## 先搞清楚:epoll 是呼叫器,Reactor 是围着它的分工

先看不用 Reactor 的朴素写法。每个连接配一个线程,线程里是一条直线:

```
线程 N:accept 得到连接 → read(没数据就挂起)→ 处理 → write → 再 read ……
```

饭馆里就是每桌配一个服务员,站在桌边等客人开口。讲五种 IO 模型时说过它的问题:一个线程同一时刻只能等一个连接,一万个连接就要一万个线程,大部分时间在切换上下文。

有了呼叫器(epoll)以后,换一种分工:**不再让人守着某一桌,而是由一个人盯着面板,哪桌亮灯就派人过去处理那一桌这一次的事,处理完马上回来看面板。** 写成程序就是:

```
程序启动时,向框架登记:"这个连接可读时,请调用我的 onRead 函数"
然后把控制权交给一个循环:

循环:
    就绪的 fd = epoll_wait(一个都没有就挂起等)
    对每个就绪的 fd:
        查登记表,找到它对应的处理函数
        调用这个函数(读一次、处理、写回,然后返回)
```

这就是 **Reactor 模式**。名字里的 react 是"做出反应":循环本身不知道业务是什么,它只对发生的事件做出反应,把事件派发给登记好的处理函数。Douglas Schmidt 1995 年把它总结成文,今天 Redis、Nginx、Netty、Node.js、Memcached 的骨架都是这一套。

注意这里控制权的方向反过来了。朴素写法是**你的代码主动去等**("我要读这个连接,读不到我就等");Reactor 是**你登记好,框架来调你**("这个连接能读了,来,处理一下")。这叫**控制反转**,也常被叫作"好莱坞原则":Don't call us, we'll call you。

三个层次放在一起看:

```
┌──────────────────────────────────────────────────────────────┐
│ 业务代码风格:回调(Node.js、Netty handler)                  │
│              或顺序代码(Go 的 goroutine-per-connection)    │
├──────────────────────────────────────────────────────────────┤
│ 程序分工:Reactor —— 事件循环 + 登记表 + 派发                 │
│          (单线程 / 单 Reactor 多线程 / 主从,见下文)         │
├──────────────────────────────────────────────────────────────┤
│ 操作系统机制:epoll / kqueue / IOCP —— 告诉你哪些 fd 就绪了   │
└──────────────────────────────────────────────────────────────┘
```

**epoll 是 Reactor 的零件,Reactor 是一种分工,回调和 goroutine 是在这种分工上写业务的两种方式。** 后面所有内容都在这张三层图里。

## 讲 Reactor 前必须认识的几个词

- **事件**:某个 fd 上"发生了值得处理的事",最常见的是**可读**(有数据了、有新连接了、对端关闭了)和**可写**(发送缓冲区腾出了空间)。定时器到期也常被当成一种事件。
- **事件分发器(同步事件分离器)**:能"一次等一批 fd、返回其中就绪的那几个"的东西,在 Linux 上就是 `epoll_wait`,macOS 上是 `kevent`。论文里叫 Synchronous Event Demultiplexer,"同步"指的是调用它的线程会在这里等着。
- **事件循环(Event Loop)**:一个不停转的循环,每一圈调一次事件分发器,拿到就绪事件后逐个派发。论文里这个角色叫 Reactor,Netty 里叫 `EventLoop`,Redis 里是 `aeMain`。
- **handler(事件处理器)**:你写的、登记在某个 fd 上的处理逻辑:可读时做什么,可写时做什么。它可以是一个函数,也可以是一个对象(Netty 的 `ChannelHandler`)。
- **回调**:"先把函数交给别人,等时机到了由别人来调用"的这种用法。handler 就是以回调的形式交给事件循环的。**回调只说明谁来调用,不说明调用时会不会等**——回调里照样可以写阻塞调用,而那正是 Reactor 最怕的事。所以"回调就是异步"这个说法不成立。
- **就绪通知 / 完成通知**:讲五种 IO 模型时划过的分界线。就绪通知是"这个连接可以读了,你自己去读";完成通知是"数据已经读好,放在你给的缓冲区里了"。
- **Proactor**:基于完成通知的对应模式。程序先提交"帮我读、读到这里",等内核做完再派发结果。Windows 的 IOCP、Linux 的 io_uring 走这条路,下文讲 Reactor 和 Proactor 的区别时细说。

角色和饭馆的对照:

| Reactor 里的角色 | 计算机里 | 饭馆里 |
|---|---|---|
| 句柄(Handle) | 一个 fd:监听端口、连接、定时器 | 一张桌子 |
| 事件分发器 | `epoll_wait` | 呼叫器面板 |
| 事件循环 | 一个不停转的线程 | 盯着面板派活的领班 |
| handler | 你写的处理函数 | 某桌亮灯后要做的事:点菜、上菜、结账 |

**一句话:Reactor = 一个事件分发器 + 一张"fd → handler"登记表 + 一个把两者连起来的循环。**

## 事件循环里为什么不能有阻塞调用

上面那段循环里,handler 是**事件循环线程自己调用的**。handler 执行的这段时间里,没有人去调 `epoll_wait`,别的连接就算早就就绪了,也只能排队。

饭馆里就是:领班亲自去 3 号桌点菜,3 号桌的客人翻了十分钟菜单还没想好,领班就在桌边站了十分钟——这十分钟里面板上亮了几十盏灯,没人理。

所以 Reactor 有一条铁律:**handler 必须很快返回,事件循环里不能有任何阻塞调用。** 哪怕只卡 1 秒,这 1 秒里这个循环负责的所有连接都停摆。

什么算"阻塞调用",比想象的多:

- **同步访问外部服务**:查一次数据库、调一次 HTTP 接口、`getaddrinfo` 做 DNS 解析。连接本身可以是非阻塞的,但你在 handler 里用了一个同步客户端,照样卡。
- **读写普通文件**:讲阻塞与非阻塞 IO 时说过,普通文件不能用 epoll,读冷数据可能要几毫秒到几十毫秒。写日志碰上磁盘抖动也一样。
- **长时间计算**:没有任何 IO,但一次排序几百万条、一次复杂正则、一次大 JSON 序列化,CPU 被占满一样等于阻塞。**"没有 sleep、没有 IO"不能证明 handler 足够短。**
- **等锁**:handler 里抢一把被别的线程长时间持有的锁。

讲阻塞与非阻塞 IO 时有一条要求:"盯一批连接的线程不能被其中一个连接卡住",那里靠的是把 fd 设成非阻塞;这里是同一条纪律推广到 handler 的全部代码:**非阻塞 fd 只保证读写本身不卡,保证不了你在 handler 里做的其他事情不卡。** 后面各种多线程变体,本质上都是在对付"有些处理就是很慢"这件事。

## 单 Reactor 单线程:为什么 Redis 够用,它怕什么

最简单的形态是一个线程包揽一切:

```
一个线程:
  epoll_wait → 监听 fd 就绪:accept 新连接,登记 onRead
             → 连接 fd 就绪:read 请求 → 解析 → 执行 → write 回复
  → 回到 epoll_wait
```

饭馆里就是夫妻店:老板一个人看面板、点菜、炒菜、上菜。

### 只用一个核,凭什么够快

Redis 的命令执行一直是这个模型,它的事件循环在 `ae.c` 里,只有几百行,结构和上面的伪代码几乎一样:

```
aeMain:                        ← 主循环,一直转
    aeProcessEvents:
        aeApiPoll              ← Linux 上就是 epoll_wait,超时设成最近一个定时任务的到期时间
        对每个就绪的 fd:
            可读 → 调用登记的读回调(读取客户端命令并执行)
            可写 → 调用登记的写回调(把回复写回去)
        processTimeEvents      ← 处理到期的定时任务(过期 key 清理等)
```

`aeApiPoll` 在不同系统上有不同实现文件(`ae_epoll.c`、`ae_kqueue.c`、`ae_select.c`),和 IO 多路复用在各平台上的机制一一对应。

一个线程敢扛全部流量,是因为三件事同时成立:

- **数据全在内存里**,一次 `GET` / `SET` 只是查一次哈希表,微秒级。handler 天然很短。
- **不用加锁**。所有数据结构只有一个线程碰,互斥锁带来的竞争和锁开销全都没有,数据结构可以写得很简单。
- **没有线程间切换**。上下文切换的那笔成本全省了,CPU 缓存也一直是热的。

瓶颈通常先出在网络收发上(系统调用、协议解析、内存拷贝),而不是执行命令——这一点讲 Redis 6 的多线程 IO 时还会用到。

### 它怕的是"一个慢操作卡住所有人"

单线程的另一面是"事件循环里不能有阻塞调用"这条铁律被放到了最大:**任何一条慢命令执行的那几秒,所有客户端一起干等。** 这是架构决定的硬约束,常见的几种:

- **`KEYS *`**:遍历整个 key 空间,几千万个 key 能卡几秒。要遍历用 `SCAN`,每次只取一小批,中间把循环让给别人。
- **大 key**:一个几百万元素的 Hash 上执行 `HGETALL`、`SMEMBERS`,或者直接 `DEL` 一个大 key(释放几百万个元素的内存也要时间)。删大 key 用 `UNLINK`,它把内存释放交给后台线程。
- **长 Lua 脚本**:脚本执行期间是原子的,也就意味着它执行多久,所有人就等多久。
- **持久化的 `fork`**:做 RDB 快照或 AOF 重写时要 `fork` 子进程。写时复制不用复制内存本身,但页表还得复制,几十 GB 内存的实例可能卡几十到几百毫秒,`INFO stats` 里的 `latest_fork_usec` 记着上一次 fork 花了多少微秒。

单线程还有一个问题:**多核用不上**。一台 32 核的机器上,Redis 进程把一个核打满,其余 31 个核看着。生产上的做法是一台机器起多个 Redis 实例,或者用 Redis Cluster 按 key 分片——**横向切成多个单线程,而不是把一个实例改成多线程**,这样"单线程不用加锁"的好处保住了。

## Redis 6 的多线程 IO 改了什么

前面说过,Redis 的瓶颈常在网络收发:每个请求要 `read` 一次、解析协议、`write` 一次,连接多、流量大时这些系统调用和拷贝把主线程的时间吃掉一大半。Redis 6.0 引入了 **I/O 线程**,只把这一部分拆出去:

```
                 主线程(唯一的事件循环)
                       │
         ┌─────────────┼─────────────┐
         ▼             ▼             ▼
     io 线程 1      io 线程 2      主线程自己也分一份
     read+解析       read+解析      read+解析          ← 可选(io-threads-do-reads)
         └─────────────┼─────────────┘
                       ▼
             主线程逐条执行命令(仍然是单线程)
                       │
         ┌─────────────┼─────────────┐
         ▼             ▼             ▼
     io 线程 1      io 线程 2      主线程
     write 回复     write 回复      write 回复
```

要点有三个:

- **执行命令的仍然只有主线程。** 数据结构依旧只有一个线程碰,不用加锁,前面那些慢命令禁令一条都没变。
- 6.x 里 `io-threads` 默认是 1(就是不开);打开后**默认只把写回复交给 io 线程**,读请求和协议解析要另外设 `io-threads-do-reads yes`。官方配置文件里的建议是:至少 4 核再开、留出一个空闲核,4 核机器用 2~3 个 io 线程,8 核用 6 个,超过 8 个基本没有收益;而且只有在 Redis 确实吃满 CPU 时才值得开。
- Redis 8.0 换了一套新的 I/O 线程实现,`io-threads-do-reads` 不再起作用,开了 `io-threads` 就是读写都走 io 线程。

这个改法很克制:**只把"慢在系统调用和拷贝"的部分并行化,"慢在业务"的部分保持单线程。** 它也说明了一件事——"Redis 是单线程的"这句话要说完整:执行命令是单线程的,网络收发从 6.0 起可以多线程,后台还有做 `UNLINK` 释放内存、刷 AOF 的线程。

## 单 Reactor 多线程:把什么交给线程池

如果业务处理本身就重(要查库、要算),夫妻店撑不住了。下一步是:**事件循环只负责 IO,业务处理交给一个工作线程池。**

```
Reactor 线程:epoll_wait → accept / read → 解析出完整请求
     │ 把请求作为任务放进队列
     ▼
工作线程池:线程 1 / 线程 2 / 线程 3 各自取任务,做业务处理(可以阻塞)
     │ 处理完把结果交回
     ▼
Reactor 线程:write 回复
```

饭馆里:服务员只管看面板、点菜、上菜,菜交给后厨一群厨师去做。

**交给线程池的是"业务",IO 留在循环里。** 读写 fd 本来就是非阻塞的、很快;慢的是读到请求之后的那部分。所以分工是:循环负责"收到完整请求"和"把回复写出去",线程池负责中间那段可能很慢的计算或下游调用。

结果为什么要交回 Reactor 线程去写,而不是工作线程直接 `write`?

- **同一个连接不能被两个线程同时写。** 一个连接上先后来了两个请求,分给两个工作线程,如果它们各自直接写,两个回复的字节可能交错,协议就坏了。
- **非阻塞写可能只写一半**,剩下的要登记可写事件、等通知再写,这个状态由 Reactor 统一管理最简单。
- **连接可能已经关了**。工作线程处理了 3 秒,这期间客户端断开,fd 号甚至被新连接复用;结果交回循环,由循环判断这个连接还在不在,才不会把回复写给别人。

这种做法的代价:

- **线程间交接有成本**:任务队列要加锁或用无锁队列,结果交回要唤醒 Reactor 线程(常用 `eventfd` 或管道往 epoll 里塞一个事件),这就是信号量与条件变量里那个经典的生产者消费者问题。
- **队列必须有界**。下游变慢时,无界队列会把请求无限堆在内存里,最后 OOM。队列满了就要停止读新请求(不再登记可读),让 TCP 接收缓冲区填满、让客户端感受到压力——这叫**背压**。
- **Reactor 线程还是只有一个**。几千个连接没问题,到十万连接、高吞吐时,光收发就能把这一个线程压满。

## 主从 Reactor:为什么要把 accept 和读写分开

一个 Reactor 线程扛不住收发,就把连接分区,每个区一个事件循环:

```
MainReactor(只盯监听 fd,只做 accept)
     │ 新连接按轮询分给某个 SubReactor,之后这个连接一辈子归它管
     ▼
SubReactor 1     SubReactor 2     SubReactor 3      ← 各有自己的 epoll 和事件循环
(连接 1,4,7…)   (连接 2,5,8…)   (连接 3,6,9…)       负责本组连接的读写
     │
     ▼
工作线程池(可选,业务重时才加)
```

饭馆里:门口一个迎宾只负责领位,把客人领到某个区;每个区有自己的服务员和面板,客人从此只找这个区的服务员。

### 为什么要分开

- **accept 和读写的节奏不一样。** 建连接是突发的(服务重启后客户端一起重连,一秒几万个),读写是持续的。混在一个循环里,建连高峰会拖慢已有连接的收发;读写忙的时候,新连接又迟迟得不到 `accept`,堆在内核的全连接队列里,队列满了就开始丢 SYN。拆开以后两边互不干扰。
- **连接固定归属一个循环,就不用加锁。** 一个连接的所有读写、它的解析状态、待发送的缓冲区,都只在一个线程里被碰,和单线程 Reactor 一样简单。多个 SubReactor 之间互不共享连接,自然也就不竞争。
- **能用满多核。** SubReactor 的数量一般设成和 CPU 核数相当:它们都是一直在跑的线程,多于核数只会增加切换。不过这不是固定公式,还要看业务池占多少 CPU、机器上还跑着什么。

代价是**分配不一定均匀**。连接按轮询分下去,如果某几个连接特别忙(一个长连接上压着大量流量),它所在的 SubReactor 就会被打满,其他的闲着——平均分配的是连接数,不是负载。

### 真实系统里的样子

| 系统 | 怎么做的 |
|---|---|
| Netty(Java) | `bossGroup` 是 MainReactor,`workerGroup` 是一组 SubReactor;每个 `Channel` 注册后固定绑定一个 `EventLoop`;`EventLoopGroup` 不指定线程数时默认是核数的 2 倍;慢的 handler 可以挂到单独的 `EventExecutorGroup` 上,相当于加了工作线程池 |
| Memcached | 主线程 accept,把新连接通过管道通知交给某个工作线程,每个工作线程有自己的事件循环(基于 libevent) |
| Nginx | 一个 master 加多个 worker **进程**(`worker_processes auto` 即核数个),每个 worker 一个事件循环;没有专门的 MainReactor,各 worker 自己 accept |
| Node.js | 主体是单 Reactor 单线程(libuv);文件 IO、DNS 解析这些没法用 epoll 的操作交给 libuv 的线程池(默认 4 个线程) |

### 大家一起 accept:惊群和 SO_REUSEPORT

Nginx 这种多个 worker 一起盯同一个监听 fd 的做法,有个经典问题叫**惊群**:新连接到来,所有在等的 worker 都被唤醒,只有一个能 `accept` 成功,其余的白醒一次又睡回去,浪费上下文切换。解法经历了三代:

- **轮流**:Nginx 早期用一把锁(`accept_mutex`),同一时间只让一个 worker 把监听 fd 放进自己的 epoll。
- **只唤醒一个**:Linux 4.5 给 epoll 加了 `EPOLLEXCLUSIVE`,一个新连接只唤醒一个等待者。
- **各自一个监听 socket**:Linux 3.9 起的 `SO_REUSEPORT` 允许多个 socket 绑定同一个端口,内核按连接的四元组哈希,直接把新连接分到其中一个 socket 上,根本不用抢。Nginx 在 `listen` 指令后加 `reuseport` 就是这种。

nginx 1.11.3 起 `accept_mutex` 默认关闭,官方文档的说法是:系统支持 `EPOLLEXCLUSIVE` 或用了 `reuseport` 时就不需要它。

`SO_REUSEPORT` 的思路值得记住:**不是让大家抢得更有序,而是让内核直接分配,不用抢。** 把竞争变成分配,在系统设计里常能把问题一下子简化。

## Reactor 和 Proactor 差在哪,为什么 Linux 上主流是 Reactor

前面所有的事件都是"可以读了",读还得 handler 自己动手。如果事件直接告诉你"数据已经读好、放在你的缓冲区里了",就是 **Proactor**。区别正是五种 IO 模型里就绪通知和完成通知的区别:

```
Reactor(就绪通知):
   事件循环:"3 号连接可以读了"
   → handler 自己调 read,把数据从内核拷到自己的缓冲区
   → 处理

Proactor(完成通知):
   程序先提交:"帮我读 3 号连接,读到这块缓冲区里"
   → 内核完成等待和拷贝
   → 事件循环:"3 号连接的读已完成,读了 512 字节"
   → handler 直接处理缓冲区里的数据
```

饭馆里:Reactor 是面板亮灯,服务员过去点菜;Proactor 是客人在手机上点好、钱付好,服务员收到的直接是一张做好的单子。

两者的区分标准是**通知的语义**,不是线程数、不是函数叫不叫 callback、也不是代码里有没有 `async` 关键字。

Proactor 看起来更省事,但它有自己的麻烦:

- **缓冲区在操作完成前归内核用。** 提交读请求时就得把缓冲区交出去,完成之前不能复用、不能释放。一万个连接各提交一个 64KB 的读,就是 640MB 先被占着——哪怕大部分连接半天才来一个字节。Reactor 是数据到了才分配缓冲区去读,空闲连接几乎不占内存。
- **取消很难写对。**"取消"请求和"操作完成"可能同时发生,要按具体接口确认什么时候内核才真正不再碰这块缓冲区。

Linux 上长期以 Reactor 为主,根本原因是:很长时间里没有好用的异步 IO,原生 AIO 基本只对 `O_DIRECT` 文件有效,对网络没用。而 Windows 的 IOCP 天生就是完成通知,是天然的 Proactor。所以 Boost.Asio 这类跨平台库对外统一提供 Proactor 接口,在 Linux 上内部用 epoll 加"就绪后自己读"来模拟。

io_uring(Linux 5.1 起)出现后,Linux 终于能做真正的 Proactor,文件和网络都支持。但它接口复杂、有些环境出于安全考虑直接禁用,网络服务的主流至今仍是 epoll 加 Reactor。

## 回调地狱是怎么来的

"事件循环里不能有阻塞调用"这条铁律给写业务的人带来很大负担。一个请求要"查库存 → 算优惠 → 写回复",每一步都可能慢,都不能在事件循环里原地等,只能把"接下来做什么"作为回调交出去,等下一步完成后由循环来调:

```
收到请求(连接, 数据):
    异步查库存(数据, 查完之后执行:
        异步算优惠(库存, 算完之后执行:
            写回复(连接, 结果, 写完之后执行:
                ……
            )
        )
    )
```

这就是**回调地狱**。根源不在于回调这种写法本身,而在于:**一段本来顺序执行的逻辑,被"不能原地等"切成了很多段,每一段都必须在等待点之前返回,把剩下的部分交给循环。** 局部变量活不过一次回调,只能放进闭包或手动塞进一个"上下文"对象——这其实是在手写一个**状态机**,记录"这个请求进行到第几步、手上有哪些中间结果"。随之而来的是:错误处理每层都要写,漏一层请求就悄悄挂住;超时和取消要贯穿所有层;出了问题看调用栈,只能看到"事件循环 → 某个回调",看不出请求是从哪一步走过来的。

后来的改良是把状态机交给语言去生成:JavaScript 先有 Promise 把嵌套拉平,再有 `async/await`,编译器把一个 `async` 函数在每个 `await` 处切开、自动生成状态机。代码看起来又是顺序的了,但**底下仍然是同一个单线程 Reactor**——`await` 之间如果做了一次长计算,事件循环照样被卡住。

Go 走得更彻底:它不在编译期切函数,而是给每个连接一个有独立栈的 goroutine,等待时把整个 goroutine 挂起,底下仍是 runtime 里的 netpoll 在用 epoll 做 Reactor。

## 线上排查:几个和 Reactor 有关的现象

Reactor 的知识在排障时最直接的用处,是把"所有请求一起变慢"和"某个事件循环被卡住"联系起来:

| 现象 | 多半是什么 | 怎么确认 |
|---|---|---|
| Redis 所有客户端的延迟一起出现尖刺 | 有一条慢命令占住了事件循环(`KEYS`、大 key 的 `HGETALL`/`DEL`、长 Lua) | `redis-cli SLOWLOG GET 10` 看慢命令;`redis-cli --latency` 持续测延迟 |
| Redis 延迟周期性抖一下 | 持久化 `fork` 复制页表 | `redis-cli INFO stats \| grep latest_fork_usec`;对照 RDB/AOF 重写的时间点 |
| 怀疑有大 key 但不知道是哪个 | 单个 key 元素过多 | `redis-cli --bigkeys`(用 SCAN 实现,可在线跑,但会有一些负载);`redis-cli MEMORY USAGE <key>` |
| 机器 32 核,某进程只把一个核打满,其余空闲 | 单 Reactor 单线程到顶了,或者主从 Reactor 里连接分配不均,热点连接压在一个循环上 | `top -H -p <pid>` 看每个线程的 CPU;`pidstat -t -p <pid> 1` |
| Netty 服务里一组连接同时卡住,其他连接正常 | 某个 `EventLoop` 线程在 handler 里做了阻塞调用(同步 JDBC、HTTP) | `jstack <pid> \| grep -A 20 nioEventLoopGroup`,看栈是不是停在 `socketRead`、JDBC 之类的调用上 |
| 请求排队、延迟涨,CPU 却不高 | 工作线程池全部在等慢下游,任务在队列里堆积 | 看线程池队列长度指标;Go 程序看 `/debug/pprof/goroutine?debug=1` 里是否大量 goroutine 停在同一个下游调用或 `chan send` 上 |
| 连接建不上、客户端超时,服务进程却活着 | accept 跟不上,全连接队列满了 | `ss -ltn` 看监听 socket 的 `Recv-Q`(当前排队数)是否接近 `Send-Q`(队列上限);`nstat -az TcpExtListenOverflows` 是否在涨 |
| Go 服务线程数涨到几百上千 | 大量 goroutine 在做文件 IO 或 cgo,每个占一个线程,netpoll 帮不上 | `ls /proc/<pid>/task \| wc -l`;goroutine dump 里大量 `[syscall]` |

规律是:**单个 Reactor 线程的 CPU 是 100% 而整体 CPU 很低,或者一组连接同时卡住,先去看那个事件循环在干什么。**`top -H` 找到打满的线程,再用对应语言的栈工具(`jstack`、Go 的 pprof、`gdb`/`perf top -t <tid>`)看它卡在哪。

## 关联

- **Go 写网络服务"又好写又快"的完整解释。** 把进程与线程、协程与用户态调度、阻塞与非阻塞 IO、IO 多路复用和本文的 Reactor 连起来:非阻塞 fd 加 epoll 组成 Reactor,是性能的底座;goroutine 挂起成本低、自带栈,让"一个连接一段顺序代码"可行。geth 这类 Go 写的区块链节点给每个对等连接一个 goroutine 同步区块、广播交易,靠的就是这一套。
- **Redis 的单线程禁忌要牢记。** 用 Redis 做缓存、分布式锁、nonce 计数器、交易去重时:遍历用 `SCAN` 不用 `KEYS`;大 key 拆分,删除用 `UNLINK`;Lua 脚本保持短小。一条运维同学随手敲的慢命令,能让所有依赖 Redis 的服务一起超时。
- **"循环里不能有不可控的等待"可以迁移到你自己的代码。** 跨链中继、链上事件监听服务通常有一个按区块高度顺序处理事件的循环。循环里直接同步调一个公共 RPC 节点又没设超时,一个慢节点就能让整条链的处理停住。这和互斥锁里"持有锁时不做 IO"是一类纪律:**任何独占的、串行的执行上下文里,都不能有不可控的等待。**
- **把竞争变成分配。** 多个实例抢同一把分布式锁来处理同一类任务,往往不如按 key(比如链 ID、账户地址)哈希,把任务固定分给某个实例——和主从 Reactor 里"连接固定归属一个 SubReactor"、`SO_REUSEPORT` 是同一个思路,还顺带保证了同一个 key 的处理顺序。

## 总结

```
epoll 只告诉你哪些连接就绪了;就绪之后怎么分工?
  │
  │ Reactor:登记 fd→handler,事件循环 epoll_wait 后派发(控制反转)
  │ 铁律:handler 在循环线程里执行,不能有任何阻塞调用
  ▼
单 Reactor 单线程 —— Redis(命令执行)、Node.js 主线程
  │ 不用加锁、没有切换;但一条慢命令卡住所有人,多核用不上
  │ Redis 6:io 线程只并行收发,命令执行仍是单线程
  ▼
单 Reactor 多线程 —— 业务交给有界线程池,结果交回循环去写
  │ 能用多核、慢业务不卡循环;但有交接成本,一个循环收发全部连接仍会压垮
  ▼
主从 Reactor —— Netty、Memcached、Nginx(多进程变体)
  │ accept 和读写分开;连接固定归属一个 SubReactor,不用加锁
  │ 惊群 → accept_mutex / EPOLLEXCLUSIVE / SO_REUSEPORT
  ▼
Proactor —— 完成通知(IOCP、io_uring);缓冲区要提前交出,取消难写
  ▼
回调地狱:顺序逻辑被"不能原地等"切碎 → Promise / async-await 生成状态机
  ▼
Go:netpoll 是藏在运行时里的 Reactor
    等待时挂起 goroutine(栈替你保存状态),findRunnable / sysmon 查 epoll 后唤醒
    只藏得住网络等待;文件 IO、cgo、长计算照样占线程
```

最该记住的几句话:

- **epoll 是机制,Reactor 是分工,回调和 goroutine 是写法。**"Reactor 就是 epoll""Go 没用 Reactor"都是把层次搞混了。
- **Reactor = 事件分发器 + fd→handler 登记表 + 事件循环。** handler 在循环线程里执行,所以**事件循环里不能有任何阻塞调用**,长计算也算。
- **单线程 Reactor 不用加锁、没有切换,但一个慢操作卡住所有人**,所以 Redis 禁止慢命令;Redis 6 的多线程只并行了收发,执行命令仍是单线程。
- **单 Reactor 多线程把业务交给线程池、把 IO 留在循环里;主从 Reactor 把 accept 和读写分开,连接固定归属一个循环。**
- **Reactor 是"可以读了"时通知,Proactor 是"已经读完了"时通知**;Linux 上长期没有好用的异步 IO,所以主流是 Reactor。
- **Go 用 goroutine 的栈代替了回调**:网络等待时只挂起这一个 goroutine,所以能用顺序代码写出事件驱动的性能。
