## Summary

关于文件,大多数人脑子里有三个默认的想法:**文件名就是文件**;**`rm` 了,空间就回来了**;**`write` 返回成功,数据就在磁盘上了**。三个都不对。文件名只是目录里的一行登记,文件本体是另一样东西;`rm` 删掉的是这行登记,只要还有进程开着这个文件,空间一个字节都不会少;`write` 成功只说明数据交给了内核,还躺在内存里,这时断电照样丢。

这三个错误理解,对应着线上最常见的一批怪现象:删了 50GB 日志 `df` 纹丝不动;`df` 显示还有 60GB 却报 `No space left on device`;`df` 和 `du` 算出来差几十 GB;几十 GB 的目录 `mv` 一下瞬间完成,换个分区却要半小时;日志轮转之后程序还在往旧文件里写;机器断电重启,配置文件变成了 0 字节。把文件系统的分层搞清楚,这些现象都能一眼看出根因。

还是那家饭馆:厨师(程序)取货存货都要找经理(内核),而货存在远处的仓库(磁盘)里。仓库里的货成千上万,经理凭记性找不到,得有一套登记制度——这套制度就是**文件系统**。

## 先搞清楚:一个文件分成哪几层

把仓库的登记制度拆开看,有三样东西:

- **货架上的格子**:货物本身放在这里,对应磁盘上的**数据块**。
- **货物档案卡**:每批货一张卡,写着这是什么货、归谁、多重、放在哪几个格子。卡上有编号,但**没有货名**。对应 **inode**。
- **门口的名录本**:一页页写着"番茄酱 → 档案 131074 号"。对应**目录**。

厨师来取货时,经理查名录、找档案、去格子里拿货,然后给厨师一张**取货单**,上面写着"你正在取 131074 号,已经取到第几箱"。之后厨师再来,报取货单号就行,不用再查名录。这张取货单就是**文件描述符**背后的东西。

落到 Linux 上,一个"文件"其实横跨两边、一共五层:

```
进程这边(内存里,进程退出就没了)            磁盘这边(持久的)

进程 A 的 fd 表                               目录 /var/log 的内容
┌────┬────────┐                               ┌─────────────┬────────┐
│ 0  │ stdin  │                               │ app.log     │ 131074 │──┐
│ 1  │ stdout │                               │ app.log.1   │ 131080 │  │
│ 3  │ ───────┼──┐                            └─────────────┴────────┘  │
└────┴────────┘  │                                                      ▼
                 ▼                                        inode 131074
          打开文件(struct file)                        ┌──────────────────────────┐
          ┌─────────────────────┐                     │ 类型 普通文件 权限 0644   │
          │ 偏移量 f_pos = 4096  │                     │ 属主 1000  大小 6KB       │
          │ 打开方式 O_WRONLY|   │  ──────────────────▶│ 链接数 1  三个时间戳      │
          │          O_APPEND   │                     │ 数据在:块 8801~8802       │──▶ 数据块
          │ 引用计数 1           │                     │ (没有文件名)              │
          └─────────────────────┘                     └──────────────────────────┘
```

从左到右:**fd 是进程私有的一个小整数** → 指向内核里的一个**打开文件**对象,偏移量和打开方式记在这里 → 打开文件指向 **inode**,文件的身份和元数据在这里 → inode 记着内容在哪些**数据块**里。而**目录项**是从另一头进来的:它只负责把"名字"翻译成 inode 号,翻译完就没它的事了。

这张图有两个结论,整篇都在反复用:

- **名字和文件是分开存放的。** 名字在目录里,文件的信息在 inode 里。改名、删名、多起一个名字,动的都只是目录,文件本身不动。
- **进程拿着 fd 访问文件,走的是"打开文件 → inode"这条路,不再经过名字。** 文件打开之后,名字被删、被改、被换成别的文件,都不影响这个进程手里的 fd。

## 讲文件系统前必须认识的几个词

下面这些词会反复出现,先用大白话过一遍:

- **块(block)**:文件系统分配空间的最小单位,常见 4KB。一个 1 字节的文件也要占一整块(极小的文件某些文件系统能塞进 inode 里,是例外)。
- **超级块(superblock)**:整个文件系统的"总台账",记着块大小、总块数、inode 总数、还剩多少空闲。它坏了整个文件系统就打不开,所以 ext4 在磁盘各处存了多份副本。
- **inode(索引节点)**:每个文件一个,记元数据和数据块位置,有一个在本文件系统内唯一的编号。磁盘上有一份,被访问时内核在内存里建一个 `struct inode`,除了磁盘上的字段,还多了引用计数、页缓存(`i_mapping`,页缓存与零拷贝的主角就挂在这里)等运行时信息。
- **目录项(dentry)**:目录里的一行"名字 → inode 号"。内核把查过的目录项缓存在内存里,叫 **dentry cache**,所以同一路径第二次打开不用再一层层读磁盘。
- **fd 表**:每个进程一张,下标就是 fd,内容是指向"打开文件"的指针。内核里是 `task_struct → files_struct → fdtable`。
- **打开文件(open file description)**:每调用一次 `open` 内核就新建一个,内核里叫 `struct file`,记着**当前偏移量**、打开方式(只读、追加、非阻塞……)、指向哪个 inode,以及有几个 fd 指着它。
- **链接计数(`i_nlink`)**:有几个目录项指向这个 inode。`ls -l` 第二列就是它。和它容易混的是**引用计数**:内存里有多少地方正在用这个 inode(被打开、被映射)。**两个都归零,文件才真正被删。**
- **日志(journal)**:文件系统在磁盘上留的一块"施工记录区",改元数据之前先把要改什么写在这里,断电后靠它恢复。后面讲日志文件系统时细讲。
- **挂载点**:一个文件系统接到目录树上的位置。inode 号只在一个文件系统内有意义,所以硬链接、`rename` 都不能跨挂载点。

**一句话:目录把名字翻译成 inode,inode 记着文件的一切(除了名字),fd 是进程手里指向"一次打开"的号牌。**

## 文件名存在哪?inode 里有什么、没有什么

### inode 里有什么

`stat` 看到的几乎就是 inode 的全部内容:

```
$ stat menu.txt
  File: menu.txt
  Size: 6144        Blocks: 16         IO Block: 4096   regular file
Device: 8,1   Inode: 131074      Links: 1
Access: (0644/-rw-r--r--)  Uid: ( 1000/  chef)   Gid: ( 1000/  chef)
Access: 2026-11-17 09:12:03      ← atime:最近一次读
Modify: 2026-11-16 22:40:11      ← mtime:内容最近一次改
Change: 2026-11-16 22:40:11      ← ctime:inode 本身最近一次改(chmod、改链接数也算)
 Birth: 2026-11-01 10:00:00      ← 创建时间,ext4 有,要内核和 stat 都支持 statx 才显示
```

类型、权限、属主、大小、链接数、几个时间戳、数据块位置——都在。**没有的是文件名**,也没有"它在哪个目录"。所以 inode 天然可以有多个名字(硬链接),也可以一个名字都没有(被删了但还开着)。

ctime 常被误认为"创建时间",其实是 change time:`chmod`、`chown`、加一个硬链接都会更新它,改内容也会顺带更新。

### inode 怎么记录数据块的位置

ext4 默认 inode 256 字节,其中记录数据位置的 `i_block` 只有 60 字节。60 字节记不下一个大文件的所有块号,于是有两代方案。

ext2/ext3 用**多级索引**:60 字节是 15 个块号指针。

```
第 1~12 个   直接写块号                         12 × 4KB = 48KB 以内,一步找到
第 13 个     → 一级索引块 → 数据块               再大一些,多读一块
第 14 个     → 索引 → 索引 → 数据块              更大,多读两块
第 15 个     → 索引 → 索引 → 索引 → 数据块       最大可到 TB 级
```

多数文件很小,直接指针一步到位,少数大文件才多读几层。**让最常见的情况走最快的路**,多级页表也是这个思路。

ext4、XFS 改用 **extent(区段)**:不再一个个记块号,而是记"从 8801 号块开始连续 300 块"。大文件通常连续存放,一条记录顶几百个块号。ext4 一个 extent 最多描述 32768 个块(4KB 块下是 128MB),`i_block` 里能直接放 4 条 extent,再多就长成一棵 extent 树。

同样这 60 字节,软链接还有一个妙用:目标路径短于 60 字节时直接存在 `i_block` 里,不占数据块(所谓"快速符号链接")。

### 文件名存在目录里

目录本身也是一个文件,有自己的 inode,它的"内容"就是一张名字表:

```
目录 /home/chef(inode 131072)的内容
┌──────────────┬───────────┐
│ 名字         │ inode 号  │
├──────────────┼───────────┤
│ .            │ 131072    │ ← 自己
│ ..           │ 2         │ ← 上一级
│ menu.txt     │ 131074    │
│ recipes      │ 131080    │ ← 子目录
└──────────────┴───────────┘
```

ext4 的目录小的时候就是线性表,条目多了用哈希树(htree)索引,几十万个文件的目录里按名字查找也不慢——但 `ls` 一个这样的目录照样要读完所有条目,该慢还是慢。

打开 `/home/chef/menu.txt` 时,内核从根目录(ext4 上 inode 号固定是 2)开始:在根目录里找 `home` → 拿到它的 inode → 读出 home 目录内容找 `chef` → 再找 `menu.txt` → 拿到 131074 号 inode。每一层都要检查执行权限(目录的 `x` 位就是"允许穿过")。查过的每一层都留在 dentry cache 里,下次直接命中。

### 由此能解释的几个现象

- **同一文件系统内 `mv` 几十 GB 也是瞬间完成**:它调用 `rename`,只是源目录删一行、目标目录加一行,数据块一块不动。
- **跨分区 `mv` 很慢**:`rename` 跨文件系统会直接失败,返回 `EXDEV`(终端里显示为 `Invalid cross-device link`),`mv` 命令收到这个错误后自己改成"复制一份再删原文件"。所以跨分区的 `mv` 不是原子的,中途中断会留下半份。
- **改名不影响正在用它的进程**:进程拿的是 fd,和名字无关。

### inode 总数是格式化时定死的

磁盘上的大致布局(ext4 实际上分成很多个"块组",每组都是这个结构):

```
┌──────────┬──────────────┬──────────────┬──────────┬───────────────────┐
│ 超级块   │ 数据块位图   │ inode 位图   │ inode 表 │ 数据块            │
└──────────┴──────────────┴──────────────┴──────────┴───────────────────┘
  总台账     哪些块用了     哪些 inode 用了  所有 inode    文件内容
```

**ext4 的 inode 表在格式化时就分配好了**,默认每 16KB 空间配一个 inode(`/etc/mke2fs.conf` 里的 `inode_ratio = 16384`)。100GB 的盘大约 650 万个 inode,文件平均大于 16KB 时绰绰有余,平均几百字节时 inode 会先于空间用完——后面"df 说有空间却报 No space left on device"的故障就是这么来的。

## 硬链接和软链接有什么区别,为什么目录不能硬链接

### 两种链接的本质

**硬链接**是给同一个 inode 在目录里多登记一个名字,`ln a.txt b.txt` 之后两个名字指向同一个 inode,链接数变成 2。两个名字完全平等,没有"原件"和"副本"之分,改哪个内容都一样,删掉一个另一个照常能用。

**软链接**(符号链接)是一个独立的文件,有自己的 inode,内容就是一段路径字符串。访问它时内核读出这段路径,再按路径去找——找不到就是"悬空链接"。

| | 硬链接(`ln`) | 软链接(`ln -s`) |
|---|---|---|
| 本质 | 目录里多一个名字,指向同一个 inode | 一个内容是路径的独立文件 |
| 自己的 inode | 没有,共用 | 有 |
| 原名字被删后 | 照常能用 | 悬空,访问报 `No such file or directory` |
| 跨文件系统 | 不能(`EXDEV`) | 能,存的只是字符串 |
| 指向目录 | 不能(`EPERM`) | 能 |
| 权限 | 就是 inode 的权限 | 链接自身永远 `0777`,不参与权限检查,看的是目标 |

软链接还有两个细节容易踩:

- **相对路径相对的是链接所在目录**,不是你执行命令时所在的目录。`/opt/app/current -> releases/v2` 永远指 `/opt/app/releases/v2`。
- **`rm` 软链接只删链接本身**,不会跟过去删目标(`symlink(7)` 明确写了 `rm`、`unlink` 不跟随)。但 `rm -r current/`(末尾带斜杠)就是另一回事了,它会进入目标目录,操作前要看清。

`stat` 会跟随软链接看目标,`lstat` 看链接自己;`ls -l` 用的是后者,所以能显示 `s.txt -> a.txt`。路径解析中最多跟随 40 层软链接,超过就报 `ELOOP`,防止 `a -> b -> a` 这种环让内核死转。

### 为什么目录不能硬链接

`link(2)` 对目录直接返回 `EPERM`。原因有三层:

- **会成环。** 如果 `/a/b/link` 硬链接到 `/a`,目录树就变成了图,`find`、`du`、备份工具遍历时会无限转圈。软链接也能成环,但软链接能被识别出来(它有自己的类型),工具默认不跟随就安全;硬链接和原名字完全平等,根本分不出哪条是"回头路"。
- **`..` 会有歧义。** 一个目录如果同时挂在两个父目录下,它的 `..` 该指谁?
- **回收没法判断。** 成环之后,一圈目录互相引用,链接数永远不为 0,从根上已经走不到它们了却删不掉。

目录自己其实是有硬链接的,只不过全由文件系统代管:每个目录的 `.` 指向自己,每个子目录的 `..` 指向它。所以**一个目录的链接数 = 2 + 子目录个数**(父目录里那一行,加自己的 `.`,加每个子目录的 `..`),`ls -ld` 一看便知。

### 硬链接在运维里的用处

硬链接常被当成冷门知识,其实身边不少工具靠它:

- **数据库的 checkpoint**:RocksDB、Pebble 做 checkpoint 时,对不再修改的 SST 文件直接建硬链接,瞬间得到一份一致快照,不额外占空间。两个目录 `du` 各自都很大,加起来却不翻倍。
- **增量备份**:`rsync --link-dest`、Time Machine 一类工具,没变化的文件就硬链接到上一份备份。
- 迁移这类目录时 `rsync` 要带 `-H`,否则硬链接会被展开成多份完整拷贝,空间翻倍。

单个 inode 的硬链接数有上限(`link(2)`:ext4 不开 `dir_index` 时是 65000),超了报 `EMLINK`。

## fork 之后父子进程共享文件偏移吗

共享。理由要落在开头那张分层图上:**偏移量不在 fd 里,也不在 inode 里,在"打开文件"对象上。** 谁和谁共享偏移,只看它们指向的是不是同一个打开文件:

```
fork 或 dup:复制的是 fd 表里的指针        两次独立 open:各建一个打开文件

父进程 fd 3 ─┐                           进程 A fd 3 ──▶ 打开文件 #1(偏移 100)─┐
             ├──▶ 打开文件(偏移 100)──▶ inode                                    ├──▶ inode
子进程 fd 3 ─┘                           进程 B fd 3 ──▶ 打开文件 #2(偏移 0)  ─┘

  一个读走 10 字节,另一个的偏移也跟着到 110     各读各的,互不影响
```

- `fork` 时子进程复制父进程的 fd 表,两份表里的指针指向同一个 `struct file`,引用计数加 1,所以偏移量、打开方式都是共享的。`dup`、`dup2` 同理,shell 里的 `2>&1` 就是一次 `dup2`。
- 两个进程(或同一进程两次)各自 `open` 同一个路径,得到两个打开文件,偏移量各管各的;它们指向同一个 inode,所以写进去的内容彼此可见。

这带来两个实际问题:

**多个进程写同一个日志文件,要用 `O_APPEND`。** 不带它,两个进程各自维护偏移量,A 写到第 100 字节,B 不知道,也从第 100 字节写,互相覆盖。带了 `O_APPEND`,每次 `write` 前内核把偏移量移到文件末尾,"移到末尾"和"写入"是一步完成的(`open(2)` 的原话是 a single atomic step),多个进程追加不会互相盖掉。(NFS 上这个保证不成立。)

**fd 会被子进程继承。** `fork` + `exec` 启动子进程时,父进程开着的 fd 默认全部被带过去。父进程打开的日志、socket、甚至密钥文件,子进程都能读写;父进程以为关掉了,其实子进程还开着,文件删了空间也不释放。解决办法是打开时带 `O_CLOEXEC`,`exec` 时自动关掉。Go 的 `os.Open` 默认都带这个标志。

**日志轮转后程序还往旧文件写**,也是同一张图:轮转工具把 `app.log` 改名成 `app.log.1`、新建一个 `app.log`,但程序手里的 fd 指的是原来那个 inode,名字变了不影响它,数据继续写进现在叫 `app.log.1` 的那个文件。所以轮转后必须让程序**重新打开**路径,后面讲删除正在写的日志时细讲。

## 删除了正在被写的大日志,为什么磁盘空间没释放

### 内核里发生了什么

`rm app.log` 调用的是 `unlink`。它做的只是:在目录里删掉 `app.log` 这一行,把 inode 的链接数减 1。

```
删除前:  目录 app.log ──▶ inode(链接数 1)◀── 进程 fd 3(引用计数 ≥1)
删除后:  目录里没这行了    inode(链接数 0)◀── 进程 fd 3 照样能读写,文件还在长
关闭后:  链接数 0 且没人引用 → 释放 inode 和全部数据块,df 这时才变
```

链接数到 0 只是"没有名字了",内核还要看内存里有没有人在用这个 inode。最后一个 fd 关闭时,`struct file` 的引用计数归零 → 释放它对 dentry 和 inode 的引用 → inode 引用计数也归零 → 发现链接数是 0,这才真正回收 inode 和数据块。

ext4 还为这种"没名字但开着"的文件准备了**孤儿链表**:链接数降到 0 时把 inode 记进去,如果这时断电,下次挂载时扫一遍孤儿链表,把它们的空间回收掉,不会永久泄漏。

所以 **`rm` 删的是名字,空间要等最后一个使用者关掉才释放。** 一个持续写日志的进程不重启,那 50GB 就一直占着,而且还在长。

### 怎么找到它

```bash
# 列出所有链接数小于 1(已删除)但还开着的文件
$ sudo lsof +L1
COMMAND   PID  USER  FD   TYPE  DEVICE  SIZE/OFF     NLINK  NODE    NAME
app      4127  app    3w  REG   8,1     53687091200  0      131099  /var/log/app.log (deleted)

# 没装 lsof 时,直接看 /proc:fd 指向的路径后面会带 (deleted)
$ sudo ls -l /proc/4127/fd | grep deleted
l-wx------ 1 app app 64 Nov 17 10:02 3 -> /var/log/app.log (deleted)

# 不知道是哪个进程时,扫全部进程
$ sudo find /proc/[0-9]*/fd -lname '*(deleted)' -printf '%p -> %l\n' 2>/dev/null
```

`lsof` 输出里 `FD` 列的 `3w` 是"fd 3,写方式打开",`SIZE/OFF` 是文件大小,`NLINK 0` 说明名字已经没了。注意容器里的进程从宿主机上也能看到,但路径是容器内的路径。

`/proc/<pid>/fd/N` 不是普通的软链接,内核叫它"魔法链接":沿着它打开或 `stat`,拿到的直接是那个已经没有名字的 inode,而不是按显示出来的路径重新查找。下面的截断能起作用,靠的就是这一点。

### 怎么释放

| 办法 | 做法 | 代价 |
|---|---|---|
| 让程序重开日志 | 发程序约定的信号(nginx 是 `USR1`,很多服务是 `HUP`)或调用它的管理接口 | 最干净;前提是程序支持,**不支持的程序收到 `HUP` 默认会退出** |
| 截断 | `: > /proc/4127/fd/3` 或 `truncate -s 0 /proc/4127/fd/3` | 不重启立刻释放;日志内容丢了 |
| 重启程序 | 正常重启 | 最确定;有服务中断 |

截断还有一个小坑:如果程序打开日志时**没带 `O_APPEND`**,它手里的偏移量还停在 50GB,下一次写会写到 50GB 处,文件变成前面全是"空洞"的稀疏文件——`ls -l` 显示又是 50GB,`du` 却只有几 KB,实际没占空间,但足以吓人一跳。带了 `O_APPEND` 就没这个问题。

根上的办法是**轮转时别直接删正在写的文件**。`logrotate` 有两种模式:

- `create` + `postrotate` 里通知程序重开:改名 → 建新文件 → 发信号,程序关掉旧 fd 打开新路径。干净,但程序要支持。
- `copytruncate`:先把内容复制一份,再把原文件截断成 0。程序无感知,代价是复制和截断之间写进来的日志会丢(`logrotate` 手册自己也这么写),而且复制大文件本身要花 IO。

## df 说有空间,为什么报 No space left on device

`No space left on device` 对应的错误码是 `ENOSPC`,但"空间"不只指数据块。最常见的原因是 **inode 用完了**:

```bash
$ df -h /data
Filesystem   Size  Used  Avail  Use%  Mounted on
/dev/sdb1    100G   40G    60G   40%  /data          # 还有 60G

$ touch /data/newfile
touch: cannot touch '/data/newfile': No space left on device

$ df -i /data
Filesystem   Inodes  IUsed  IFree  IUse%  Mounted on
/dev/sdb1      6.5M   6.5M      0   100%  /data      # inode 用完了
```

每个文件再小也要占一个 inode,前面讲 inode 时说过 ext4 的 inode 总数格式化时就定了。几百万个几百字节的小文件(缓存碎片、session 文件、邮件队列、按条存的小 JSON)会让 inode 先于空间耗尽。找文件最多的目录:

```bash
# 统计 /data 下每个一级目录里有多少个条目(-xdev 不跨到别的文件系统)
for d in /data/*/; do echo "$(find "$d" -xdev | wc -l) $d"; done | sort -n | tail
```

删掉这些小文件就能恢复。长期的解决:海量小数据放进数据库或嵌入式 KV,挤在少数大文件里;非要存成文件,格式化时用 `mkfs.ext4 -i 4096` 之类调小每 inode 对应的字节数。XFS 按需分配 inode(上限受 `imaxpct` 约束),很少碰到这个问题。

inode 之外,"有空却写不进去"还有几种情况,区别要看具体错误:

- **保留块**:ext4 默认留 5% 给 root(`tune2fs -l` 里的 `Reserved block count`),普通用户看到 `Avail` 为 0 时 root 还能写。所以 `df` 里 `Size ≠ Used + Avail`。
- **磁盘配额**:用户或项目超了配额,报的是 `Disk quota exceeded`(`EDQUOT`),不是 `ENOSPC`。
- **文件系统变成只读**:ext4 遇到磁盘错误时,按挂载选项 `errors=remount-ro` 会把自己改成只读,之后所有写都报 `Read-only file system`(`EROFS`)。这时该看的是 `dmesg` 和磁盘健康,不是清空间。
- **写进了另一个文件系统**:容器的可写层、`/tmp` 是 tmpfs、目录其实是另一块盘的挂载点。`df <具体路径>` 会告诉你这个路径实际在哪个文件系统上,别只看 `df /`。

## df 和 du 为什么对不上

两个命令算法根本不同:**`du` 从目录出发,沿着名字一个个加文件大小;`df` 直接问文件系统的超级块还剩多少。** 凡是"占着空间但从目录走不到"的东西,都会让 `df` 比 `du` 大:

| 原因 | 现象 | 确认 |
|---|---|---|
| 已删除但仍被打开的文件 | `df` 大于 `du` | `lsof +L1` |
| 挂载点下面压着旧文件 | 往某目录写了一堆东西后又在它上面挂了一块盘,旧文件被"盖住" | `mount --bind / /mnt/rootfs` 后 `du /mnt/rootfs/<该目录>` |
| 保留块、日志区、inode 表等元数据 | `df` 的 `Used` 天生比所有文件之和大一些 | `tune2fs -l`、`dumpe2fs -h` |
| 快照(Btrfs、ZFS、LVM) | 删了文件空间不回来,旧快照还引用着这些块 | 列快照、看快照占用 |

反过来,也有让 `du` 和 `ls -l` 对不上的:

- **稀疏文件**:虚拟机镜像、数据库预分配文件,`ls -l` 显示的是逻辑大小,`du` 显示的是实际占用的块。`du --apparent-size` 可以让 `du` 按逻辑大小算。
- **硬链接**:`du` 在同一次统计里遇到同一个 inode 只算一次;对两个目录分别 `du`,每次都会算上。

排查 `df` 和 `du` 差距的顺序:**先 `lsof +L1`,再看挂载点有没有盖住东西,最后才考虑元数据和快照。** 第一项占了绝大多数情况。

## write 成功、fsync、rename、断电持久,分别保证什么

这是文件系统里最容易混的一组概念。把一次写入从程序到磁盘的路径画出来:

```
程序 write(fd, data)
   │  数据拷进页缓存(内存),页面标成"脏页",write 返回成功
   ▼                                      ← 进程崩溃:数据还在,内核会写回
页缓存(饭馆冰箱里的"待入库区")             ← 断电:没了
   │  内核回写线程几秒到 30 秒内写回;或者程序调 fsync 立刻写
   ▼
磁盘控制器的写缓存(盘自己的内存)          ← 断电:可能没了(取决于盘有无掉电保护)
   │  fsync 会发"刷缓存"命令,等盘确认
   ▼
持久介质(盘片 / 闪存)                      ← 断电:还在
```

对照这张图,四个操作各管一件事:

| 操作 | 保证什么 | 不保证什么 |
|---|---|---|
| `write` 返回成功 | 数据进了内核;其他进程立刻能读到;本进程崩溃也不丢 | 断电不丢;而且可能**只写了一部分**,要看返回的字节数 |
| `fsync(fd)` | 这个文件的数据和 inode 元数据写到了持久介质,包括刷掉盘的写缓存 | 目录里指向它的那一行已经落盘 |
| `rename(tmp, path)` | 原子可见:任何时刻打开 `path`,要么是旧文件要么是新文件,不会扑空也不会看到半截 | 断电后这个改名还在 |
| `fsync(目录 fd)` | 目录内容(新建、删除、改名的条目)落盘 | — |

几个容易漏的细节:

- **`close` 不等于 `fsync`**,关闭文件不会触发落盘。但写完不检查 `close` 的返回值也不对,NFS 这类文件系统会在 `close` 时才报写错误。
- **`fsync` 对新建的文件只管文件本身。** `fsync(2)` 原文:调用 fsync 并不保证包含该文件的目录项也已到达磁盘,需要对目录的 fd 也调一次 fsync。新建文件后断电,可能出现"数据块写好了,但目录里查不到这个名字"。
- **`fdatasync`** 比 `fsync` 省一点:不影响后续读取的元数据(比如 mtime)可以不刷,但文件大小变了还是要刷。数据库写 WAL 常用它。
- **`fsync` 失败之后别重试了事。** 2018 年 PostgreSQL 发现,Linux 上 fsync 报 IO 错误后,出错的脏页可能已经被标成"干净"并丢弃,再调一次 fsync 会返回成功,但数据早没了。PostgreSQL 此后的做法是 fsync 失败直接崩溃,从 WAL 恢复。**fsync 报错就当这批数据已经丢了处理。**
- **macOS 上的 `fsync` 不刷盘缓存。** 苹果的 `fsync(2)` 只保证数据交给了磁盘,盘的写缓存不管;要真正落到介质得用 `fcntl(fd, F_FULLFSYNC)`。Go 标准库在 macOS 上的 `File.Sync` 已经替你改用了 `F_FULLFSYNC`(源码 `internal/poll/fd_fsync_darwin.go`),所以在 Mac 上跑 Go 程序的 `Sync` 会明显比 Linux 慢。

**`fsync` 的代价**是一次通常几毫秒(SSD 带掉电保护时可以到几十微秒,机械盘十毫秒级),比写页缓存慢几个数量级。数据库和消息队列不会每条记录都 fsync,而是攒一批一起 fsync(组提交),拿一小段"可能丢失"的窗口换吞吐。关键是**确认给上游的时机必须在 fsync 之后**,先回"成功"再刷盘,就等于承诺了做不到的事。

### 怎样安全地原子替换一个配置文件

最常见的错误写法是直接覆盖:`echo "..." > config.toml`,或 Go 里的 `os.WriteFile`。它的步骤是"打开时截断成 0 → 写入新内容",于是:

- 截断和写完之间,另一个进程来读,读到的是空文件或半截内容;
- 写到一半程序崩溃或断电,文件就是半截的,旧版本也已经没了。

ext4 早期(2009 年前后)还有一个著名事故:因为延迟分配,"截断 + 写 + 不 fsync"在断电后大批量地留下 **0 字节文件**,桌面配置全丢。ext4 后来加了 `auto_da_alloc` 选项,识别"rename 替换"和"截断替换"这两种模式并提前分配块来兜底,但这只是对不规范程序的补救,不是保证。

正确的做法是**写临时文件,再 rename 过去**:

```
① 在目标同一个目录里新建临时文件,完整写入新内容
② fsync 临时文件            → 新内容和新 inode 落盘
③ rename(临时文件, 目标)    → 目标名字一步从旧 inode 指到新 inode
④ fsync 所在目录            → 这次改名落盘
```

每一步之间崩溃会怎样:

| 崩溃时刻 | 重启后目标文件 | 残留 |
|---|---|---|
| ① 写到一半 | 完整旧版 | 半截临时文件,清掉即可 |
| ② 之后、③ 之前 | 完整旧版 | 完整临时文件 |
| ③ 之后、④ 之前 | 旧版或新版之一(改名可能没落盘),不会是半截 | — |
| ④ 之后 | 完整新版 | — |

几个要点:

- **临时文件必须和目标在同一个文件系统**,所以放同一个目录,不要放 `/tmp`。否则 `rename` 报 `EXDEV`,如果再"贴心地"退化成复制,原子性就没了。
- **跳过第 ② 步是最常见的错**:rename 可能先于数据落盘,断电后目标指向一个还没写完数据的 inode——又是那个 0 字节文件。
- 新文件的权限、属主是新 inode 的,不会继承旧文件;要在 rename 之前设好。
- 已经打开旧文件的进程继续读旧内容(它拿着旧 inode),这不违反原子性;想让它们切换到新配置,得靠重新加载机制。
- 想要"目标已存在就别覆盖",用 `renameat2` 的 `RENAME_NOREPLACE`;想原子地交换两个文件,用 `RENAME_EXCHANGE`。

这个"写新的、再一步换指针"的思路,部署时切换版本目录也能用:`ln -s releases/v2 current.tmp && mv -T current.tmp current`。`mv -T` 走的就是 `rename`,`current` 这个软链接一步换到新版本,不存在"先删旧链接、还没建新链接"的空窗。

## TOCTOU:先检查再使用的竞争

还有一类问题出在"名字"和"文件"之间的空隙。程序先 `stat` 检查文件存在、属于谁、不是软链接,然后再 `open` 它——两次调用之间,文件可能被删除、被替换成指向 `/etc/shadow` 的软链接。这叫 **TOCTOU**(time of check to time of use,检查与使用之间的竞争),是经典的安全漏洞模式。

原则是:**能直接去做、做不成再处理错误的,就别先检查再做。** 想"不存在才创建",用 `O_CREAT|O_EXCL` 一步完成;想"别跟随软链接",用 `O_NOFOLLOW`;要检查属性,先 `open` 再对 fd 做 `fstat`,检查和使用的就是同一个 inode。限制程序只在某个目录里操作,Go 里用 `os.Root`。

## 日志文件系统(ext4 journal)防的是什么

### 改到一半断电

往文件末尾追加一个块,文件系统要改三处:

```
① 数据块位图:把 8803 号块标成已用
② inode:添一条"数据在 8803",大小改大
③ 数据块 8803:写入内容
```

三处在磁盘的不同位置,不可能一次写完。只完成 ① 就断电,8803 标成已用却没人指向,空间永久泄漏;只完成 ②,inode 指向的块里是别人的旧数据,读出来是垃圾甚至是别的文件的内容。早年靠开机时 `fsck` 扫描全盘修复这类不一致,盘一大要几个小时。

### 先写日志再动手

日志文件系统的做法是:改正式位置之前,先把"要改哪几处、改成什么"连同一个**提交标记**写进日志区;日志写完,再去改正式位置(这一步叫 checkpoint);改完,这段日志就可以作废。

崩溃重启后只看日志尾部:有提交标记的记录,按记录重做一遍(重做是幂等的,做几次结果都一样);没有提交标记的,说明正式数据还没动,直接丢弃。**不管断在哪一刻,文件系统的结构都能恢复成一致的,而且只需要读日志最后一小段**,不用扫全盘。ext4 默认每 5 秒提交一次日志(挂载选项 `commit=5`)。

这和数据库的 WAL(预写日志,讲数据库事务时会讲到)是同一个思想:先记录意图,再执行。

ext4 用 `data=` 选项决定日志里记多少:

| 档位 | 日志里记什么 | 特点 |
|---|---|---|
| `journal` | 元数据和数据本身 | 最安全,数据写两遍,最慢 |
| `ordered`(默认) | 只记元数据,但保证数据块先写完再提交元数据 | 不会出现"inode 指向一块垃圾",速度和安全兼顾 |
| `writeback` | 只记元数据,不管先后 | 最快,崩溃后文件里可能出现旧的垃圾数据 |

### 日志不防什么

**journal 保护的是文件系统自己的结构一致,不是你的数据不丢。** 它保证断电后不会出现"块被两个文件同时占用""inode 指向不存在的块"这类结构损坏,`fsck` 不用跑几小时;但你 `write` 了还没 `fsync` 的数据,该丢照样丢,写了一半的配置文件还是半截的。应用层的数据安全,仍然要靠前面讲的 fsync 和原子替换。

它也不防磁盘本身坏了、不防误删——那是备份和 RAID 的事。

### 另一条路:写时复制

Btrfs、ZFS 走的是另一条路:从不原地修改。新数据和新元数据都写到空闲位置,最后把最上层的一个指针从旧版本换到新版本,这一步一次完成。崩溃在换指针之前是完好的旧版本,之后是完好的新版本。这叫**写时复制**(COW)。旧版本不回收就是一份**快照**,这也是前面 df 和 du 对不上时"快照占着空间"的来由。

fork 的内存写时复制、前面讲的原子替换配置文件、Git 的提交、以太坊的状态树,都是同一个思路:**不改旧的,写新的,再一步切过去。**

## 线上排查:几个和文件系统有关的怪现象

| 现象 | 多半是什么 | 怎么确认 |
|---|---|---|
| 删了大日志,`df` 没变 | 文件还被进程开着 | `lsof +L1`;`ls -l /proc/<pid>/fd \| grep deleted`;释放用重开日志或 `truncate -s 0 /proc/<pid>/fd/<N>` |
| `df -h` 有空间却报 `No space left on device` | inode 耗尽 | `df -i <路径>`,`IUse%` 为 100% |
| `df` 比 `du` 大很多 | 已删未关的文件,或挂载点盖住了旧文件 | 先 `lsof +L1`,再 `mount --bind / /mnt/rootfs` 看被盖住的目录 |
| `ls -l` 显示 50GB,`du` 只有几 KB | 稀疏文件(比如截断后无 `O_APPEND` 的进程继续写) | `du -h --apparent-size` 对比 `du -h` |
| 报 `Too many open files` | 进程 fd 用到上限(`EMFILE`),多半是泄漏 | `cat /proc/<pid>/limits \| grep 'open files'` 看上限;`ls /proc/<pid>/fd \| wc -l` 看已用,隔几分钟再看是否只涨不降;`ulimit -n` 看当前 shell 的限制 |
| 报 `Too many open files in system` | 整机 fd 用尽(`ENFILE`) | `cat /proc/sys/fs/file-nr`(已分配 / 空闲 / 上限) |
| 日志轮转后新文件是空的,旧的 `.1` 还在长 | 程序没重开日志,fd 还指着旧 inode | `ls -l /proc/<pid>/fd` 看到指向 `app.log.1` |
| 程序偶尔读到空的或半截的配置 | 写方直接覆盖(`O_TRUNC`),没用临时文件 + rename | `strace -f -e trace=openat,rename,renameat2 -p <写方 pid>`,看到对目标的 `O_TRUNC` |
| 断电重启后某文件变成 0 字节 | 写完没 fsync 就 rename 或直接覆盖 | 检查写入代码里有没有 fsync;`mount` 看 `data=`、`auto_da_alloc` |
| 突然所有写入报 `Read-only file system` | 磁盘出错,ext4 自动只读保护 | `dmesg -T \| grep -i -E 'ext4\|I/O error'`;`mount \| grep '(ro,'` |
| `mv` 或 `rename` 报 `Invalid cross-device link` | 源和目标不在一个文件系统 | `df <源目录> <目标目录>` 看是否同一设备 |

## 关联

- **节点数据目录**:区块链节点的状态库(LevelDB、Pebble)是大量中等大小的 SST 文件,通常 inode 不是瓶颈,但空间增长快。数据目录最好放独立的盘或分区,监控同时盯 `df -h` 和 `df -i`,不然写满时连同系统日志一起写不进去,排查都困难。节点自己的 checkpoint、快照常用硬链接(见前面硬链接在运维里的用处),迁移数据目录用 `rsync -aH`;同一个盘里挪目录用 `mv`,瞬间完成。
- **日志清理**:节点、中继程序的日志是磁盘满的头号元凶。**清理时别 `rm` 正在写的日志**,用程序自带的轮转、`logrotate` 加重开信号,或者实在不行 `truncate`。批量巡检多台机器时,把 `lsof +L1` 加进磁盘检查项,能一眼发现"删了没释放"的空间。
- **keystore 和配置文件**:私钥的 keystore 文件、节点配置、程序记录的"已处理到哪个区块高度"之类的进度文件,写一半或断电变成 0 字节都会出事故——轻则节点起不来,重则重复处理或私钥文件损坏。一律用前面讲的原子替换写法;进度文件尤其要注意:**先确认 fsync 成功,再认为这个高度已经处理完。** 密钥文件还要注意权限在 rename 前就设成 `0600`,不要先以宽松权限写出来再改。
- **崩溃恢复的思路是共通的**:文件系统的 journal、数据库的 WAL、链上节点的区块回放,都是"先记下要做什么,崩溃后照着记录重做"。理解了文件系统这一层,看节点"异常退出后要回放多少数据""为什么数据目录里有个 LOCK 文件"就有了参照。

## 总结

```
一个文件 = 五层
  │ fd(进程私有小整数)→ 打开文件(偏移量、打开方式)→ inode(元数据 + 数据位置,没有名字)→ 数据块
  │ 目录项从另一头进来:名字 → inode 号
  ▼
名字和文件分离带来的现象
  ├─ 硬链接 = 同一 inode 多个名字;软链接 = 内容是路径的独立文件
  ├─ 目录不能硬链接:会成环、.. 有歧义、无法回收
  ├─ 同文件系统 mv / rename 只改目录项,瞬间且原子;跨文件系统 EXDEV
  ├─ fork / dup 共享打开文件,所以共享偏移;独立 open 各管各的
  └─ rm 只删名字:链接数和引用数都归零才释放(lsof +L1)
  ▼
"有空间"的几种口径
  ├─ No space 但 df 有空 → inode 耗尽(df -i),或保留块、配额、只读、路径在别的盘
  └─ df ≠ du → 已删未关、挂载点盖住、元数据、快照、稀疏文件
  ▼
写入的几级保证
  │ write 成功 → 进了页缓存   fsync → 落盘(macOS 要 F_FULLFSYNC)
  │ rename → 原子可见         fsync 目录 → 改名落盘
  │ 原子替换 = 同目录临时文件 → fsync → rename → fsync 目录
  ▼
崩溃一致性
  ├─ 日志式(ext4、XFS):先写日志再改,保护的是文件系统结构,不是你的数据
  └─ 写时复制(Btrfs、ZFS):写新的再换指针,顺带得到快照
```

最该记住的几句话:

- **文件名不属于文件。** 名字在目录里,文件的一切在 inode 里,进程手里的 fd 指向的是一次"打开",不经过名字。
- **`rm` 删的是名字。** 链接数归零、而且没有进程再打开着,空间才释放;删了没释放,先查 `lsof +L1`。
- **偏移量在"打开文件"上**:fork、dup 共享,独立 open 不共享;多进程追加同一文件用 `O_APPEND`。
- **`write` 成功 ≠ 落盘,`rename` 原子 ≠ 持久。** 原子替换文件的标准四步:同目录临时文件、fsync、rename、fsync 目录。
- **journal 保护文件系统不坏,不保护你没 fsync 的数据。**
