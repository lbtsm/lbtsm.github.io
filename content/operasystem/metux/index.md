## Summary 

在厨房里的那块白板写着"还剩 5 个鸡蛋",如果两个厨师同时看到 5,各拿一个,都改成 4,实际剩 3。这个该怎么办呢？对应计算机里面,这种情况就是两个线程同时对共享计数器做"读、改、写"。

---

## 临界区和互斥

这个问题出现的原因错在三步中间被别的线程插了进来。
**访问共享数据、必须一口气做完、中途不能被插入的一段代码**叫**临界区**,比如"读出计数器、加一、写回去"这三条指令。**互斥**指同一时刻最多一个线程在临界区里,实现它的工具是**互斥锁**(mutex,mutual exclusion 的缩写)。

一把正确的锁要同时满足:

1. **互斥**:同一时刻最多一个线程在临界区里。这是根本。
2. **空闲时能进(progress)**:临界区里没人时,想进的线程必须能马上进。
3. **有限等待(bounded waiting)**:想进的线程迟早能进去,不能每次都被后来的抢先。

此外还有实际要求:**要快**。

## 用普通变量做锁:失败

最朴素的锁是一个布尔变量:

```
锁住():
    while 锁 == 真: 等
    锁 = 真
```

```
线程 A:读到 锁 == 假
线程 B:读到 锁 == 假         ← A 读完了,还没来得及设置
线程 A:锁 = 真,进入临界区
线程 B:锁 = 真,也进入临界区

两个线程同时在临界区里
```

"检查"和"设置"是两步,中间可以被插进来。这是个绕不出去的圈:**用来保护临界区的锁,"检查再设置"本身也是一个临界区**,再加一个变量保护它,又需要第三个,没完没了。

只靠普通读写的巧妙算法也有,比如 Peterson 算法,但它只能处理两个线程,在现代 CPU 上会被指令重排打乱,还得配合内存屏障指令才能用,实际没人这么写锁。

---

## 原子指令:一步完成"检查"和"设置"

出路是**让"检查"和"设置"成为一个不可分割的动作**,由硬件保证执行期间别的核心不能碰这块内存,这类指令叫**原子指令**。两个核心同时执行,一定有先有后,先执行的看到"空闲",后执行的看到"已占用"。

最简单的一种叫 **Test-and-Set**(测试并设置):写入新值,同时返回写入**之前**的旧值。

```
TestAndSet(位置, 新值):         ┐
    旧值 = 位置上的值            │ 硬件保证这三步一次做完,
    位置上的值 = 新值            │ 中间不可能被别的核心插进来
    返回 旧值                   ┘

锁住():
    while TestAndSet(锁, 真) == 真:    ← 原来就是"有人",接着等
        等
    ← 原来是"空闲",现在已经被我设成"有人"了,我拿到锁了
```

更通用的一种叫 **CAS**(Compare-And-Swap,比较并交换):

```
CAS(位置, 预期值, 新值):          ┐
    if 位置上的值 == 预期值:      │
        位置上的值 = 新值         │ 硬件保证一次做完
        return 成功             │
    return 失败                 ┘
```

有了 CAS,计数器甚至可以不用锁:两个线程同时执行"如果还是 5,就改成 4",只有一个成功;失败的重新读(现在是 4),再 CAS 成 3。

```
线程 A:CAS(计数器, 5, 4) → 成功
线程 B:CAS(计数器, 5, 4) → 失败,已经不是 5 了
线程 B:重新读,是 4;CAS(计数器, 4, 3) → 成功

减了 2 次,从 5 变成 3,对了
```

这种"不加锁直接改,被别人改过就重来"的做法叫**乐观并发**,适合冲突少的时候,冲突一多反复重来反而更慢;先加锁再改叫**悲观锁**,适合冲突多的时候。

这对思路在数据库里叫悲观锁和乐观锁(带版本号的更新),在版本控制里叫"先锁定文件再改"和"各自改完再合并"。

**硬件实现。** x86 上的 `LOCK CMPXCHG` 就是 CAS,`XCHG` 可以当 Test-and-Set 用。现代 CPU 执行时会锁住这块内存所在的缓存行,靠缓存一致性协议保证其他核心期间无法修改。所以原子操作仍比普通读写慢,多核激烈争抢同一变量时更慢,因为缓存行要在核心之间来回传递。

## 拿不到锁时:自旋还是阻塞

锁被占着时,线程该干什么?好比只有一口油锅,甲在用,乙可以站在锅边盯着,也可以先去休息等人叫。

### 自旋与阻塞

**自旋锁**:拿不到锁的线程循环重试、一直占着 CPU,锁一释放马上接手,但等待期间 CPU 白白空转。

**阻塞**:拿不到锁的线程让操作系统把自己挂起、让出 CPU,锁释放时再被唤醒。不浪费 CPU,但一睡一醒是两次上下文切换,一次几微秒到几十微秒。

### 选哪个,看临界区多长

依据是:**持锁线程还要用多久,和一次睡眠唤醒相比哪个长?**

```
一次线程睡眠再唤醒 ≈ 几微秒到几十微秒

临界区很短,比如 100 纳秒  → 自旋 100 纳秒就能拿到,远比睡一觉划算
临界区很长,比如 10 毫秒   → 自旋 10 毫秒等于白烧 10 毫秒 CPU,不如睡
```

自旋还有个前提:**多核。** 单核上,自旋的线程占着唯一的 CPU,被调度走的持锁者没机会运行去释放锁,只能空转到时间片用完。所以**自旋只在多核且临界区很短时才有意义**,内核里保护一小段数据时最常用。

### 混合策略:先自旋,再阻塞

实际的锁大多两者结合:

```
① 先自旋一小会儿,重试几次
       ↓ 还没拿到
② 进入等待队列,阻塞睡眠
```

它赌的是**大多数时候临界区都很短**:自旋一会儿就拿到,省下睡眠唤醒;碰上长的也只多转一小会儿。Linux 的锁、Java 的 `synchronized`、Go 的 `sync.Mutex` 用的都是这个思路。

## futex:没有竞争就不进内核

绝大多数加锁时锁是空的,每次都做系统调用没有必要。Linux 的 **futex**(Fast ß Mutex,快速用户态互斥锁)的设计是:

```
加锁:
  ① 在用户态用一条 CAS 指令抢锁
       成功(没人抢) → 直接返回,不进内核
       失败(有人抢) → 调用 futex 系统调用,让内核把自己挂起

解锁:
  ① 在用户态用原子指令释放
  ② 只有锁上标记着"有人在等",才调用 futex 系统调用唤醒一个
```

**没有竞争时,加锁只是一条原子指令,十几到几十纳秒,不进内核;** 有竞争才付出系统调用和线程切换的代价。

一个 futex 就是用户态的一个整数,加上内核里关联的等待队列。两个核心操作是 `FUTEX_WAIT`(如果这个整数还是某个值,就把我挂到它的等待队列上睡觉)和 `FUTEX_WAKE`(唤醒它上面的若干个等待者)。`FUTEX_WAIT` 的检查值和睡下在内核里原子完成,避免了"刚检查完锁、还没睡下,锁就被释放了,结果睡下去再没人叫醒"的问题。

## 锁的粒度

**持锁做慢事。** 在临界区里读写磁盘、发网络请求,所有线程都在等。原则:**持锁时只做必须做的那一点点事,慢的事放到锁外面做。**

**一把锁管得太宽。** 不相干的数据共用一把锁,本可并行的操作被迫排队。解法是**拆细**:数据分成 16 片,每片一把锁,按编号算出属于哪片只锁那片,这叫**分片锁**。

**伪共享。** 拆细后,不相干的锁仍可能互相拖慢。CPU 读写内存以**缓存行**为单位,通常一行 64 字节(`getconf LEVEL1_DCACHE_LINESIZE` 可以查)。两个被不同核心频繁修改的变量挤在同一缓存行里,一个核心改锁 A,另一个核心缓存里的整行就失效,即使它只关心锁 B。逻辑上没有竞争,硬件上却在争抢同一缓存行,这叫**伪共享**。解法是在结构体里加填充字节,让它们落在不同缓存行。

**读写锁。** 有些数据随时被读、很少被改,比如配置。多个线程同时读没问题,只有写需要独占,这就是**读写锁**:

- **读锁**可以多个线程同时持有。
- **写锁**独占:有人在写,谁都不能读写;有人在读,写者要等读完。

实现上维护一个读者计数和一个写者标志。读者源源不断时,写者可能永远等不到"没人在读",所以常见做法是**写者优先**:有写者在等时,新来的读者也被挡住。维护读者计数比普通锁多做一些事,每次读只要一瞬间时反而更慢。**只有读远多于写、而且每次读都要花一点时间时,读写锁才划算。**

## 公平与吞吐

锁释放时,等待队列里有一个睡着的线程,恰好又有个新线程来加锁,锁给谁?

- **给新来的**:它正在 CPU 上,马上能用;唤醒睡着的线程要等调度,锁这段时间空着。吞吐更高。
- **给等待的**:它先来。总让新来的插队,它可能永远轮不到,这叫**饥饿**。

公平锁严格按到达顺序授予,吞吐较低;非公平锁允许插队,吞吐高但可能饥饿。很多锁兼顾两者:平时允许插队,一旦有线程等得太久,就切换成严格排队,锁只交给等得最久的那个,排队的都处理完再切回去。Go 的 `sync.Mutex` 就是这么做的,"太久"的标准是 1 毫秒。

## 关联

以下以 Go 1.26 为准。

`sync.Mutex` 加锁先在用户态用 CAS 抢;抢不到时,满足条件才自旋:多核、`GOMAXPROCS` 大于 1、还有别的 P 在运行、本地队列为空,最多自旋 4 轮,每轮执行 30 次 CPU 的 `PAUSE` 指令;再不行就让 goroutine 睡眠,由 runtime 负责唤醒。它有正常模式和饥饿模式:正常模式允许新来的 goroutine 插队,一旦有 goroutine 等了超过 1 毫秒,就切到饥饿模式,锁直接交给队首。从 Go 1.24 起实现搬到了 `internal/sync/mutex.go`,注释里写清了两种模式的取舍。

**三条使用规则。** 零值就能用,不需要初始化;不可重入,同一个 goroutine 连续 `Lock` 两次会把自己锁死;不能复制,带锁的结构体要用指针传递,`go vet` 会检查。

**持锁时绝不做 IO。** "持锁做慢事"。持锁调 RPC、查数据库,一个慢下游就能让所有请求在这把锁上排队。慢操作挪到锁外;多个请求同时查同一个 key,可以用 `singleflight` 合并成一次。

**读写锁要实测。** `sync.RWMutex` 是写者优先的,有写者在等时新的 `RLock` 会阻塞。临界区极短时可能比 `Mutex` 还慢,先用 `Mutex`,压测证明锁是瓶颈再换。

**原子操作和 CAS。** `sync/atomic` 提供 `atomic.Int64`、`atomic.Pointer[T]` 等类型,`Add`、`CompareAndSwap` 就是原子指令。简单计数器用它比用锁快得多。

**能不共享就不共享。** Go 的说法是"不要用共享内存来通信,要用通信来共享内存":每个 goroutine 写自己的结果槽位,或通过 channel 交出数据,从根上没有临界区。

**排查锁竞争。** 开发和测试时用 `go test -race` 找数据竞争;线上用 `runtime.SetMutexProfileFraction` 打开 mutex profile,`go tool pprof .../debug/pprof/mutex` 能看出哪把锁上等待的总时间最长。

## 总结

```
共享计数器的值对不上
  │ 找出不能被打断的一段:读 → 改 → 写 = 临界区
  ▼
用普通布尔变量做锁
  │ 失败:"检查"和"设置"是两步,两个线程能同时拿到
  │ 怪圈:保护临界区的手段,本身又是一个临界区
  ▼
原子指令(Test-and-Set、CAS)
  │ 硬件保证"检查"和"设置"一步完成
  │ 衍生:不加锁直接 CAS 改数据 = 乐观并发
  ▼
拿不到锁时干什么
  │ 自旋 → 适合临界区很短、且多核
  │ 阻塞 → 适合临界区很长
  │ 先自旋一会儿再阻塞 = 混合策略
  ▼
多数时候没有竞争,不必进内核 = futex
  │ 快路径在用户态,有竞争才进内核
  ▼
锁该管多大
  │ 持锁做 IO → 慢事放锁外
  │ 一把锁管太宽 → 拆细 = 分片锁
  │ 两个变量挤在同一缓存行 = 伪共享
  │ 读多写少 = 读写锁
  ▼
锁给新来的还是等着的 = 吞吐与公平的权衡,等太久就切换成严格排队
```

最该记住的几句话:

- **临界区是必须一口气做完的一段操作,互斥锁保证同一时刻只有一个人在里面。**
- **锁不能靠普通的读写来实现,必须靠硬件提供的原子指令**,因为"检查"和"设置"必须是一步。
- **拿不到锁时,短的等待用自旋,长的等待用阻塞,实际的锁先自旋再阻塞。**
- **没有竞争时,好的锁根本不进内核**,只是一条原子指令。
- **持锁时只做最少的事**,慢操作放到锁外;锁太粗就拆细。

## 动手练习

1. **看一眼缓存行有多大。** Linux 上执行 `getconf LEVEL1_DCACHE_LINESIZE`,macOS 上执行 `sysctl hw.cachelinesize`,一般是 64 或 128。这就是伪共享的单位。
2. **看锁竞争有没有进内核。** 在 Linux 上找一个多线程程序(比如 `sort --parallel=4` 排序一个大文件),用 `strace -f -c -e trace=futex <命令>` 运行,结尾的统计表会显示 `futex` 系统调用的次数。只有竞争时才有 futex 调用,次数远少于加锁次数,这就是的快路径。
3. **看一个进程被迫睡了多少次。** `grep ctxt_switches /proc/<进程号>/status` 会显示两个数:`voluntary_ctxt_switches` 是自己主动让出 CPU 的次数(等锁、等 IO 都算),`nonvoluntary_ctxt_switches` 是时间片用完被换下的次数。锁竞争严重的程序,前者涨得很快。
4. **复现并修好计数器问题。** 写一个两个 goroutine 各对同一个计数器加 10 万次的程序,用 `go run -race` 看报错;再分别用 `sync.Mutex` 和 `atomic.Int64` 修好,确认 `-race` 不再报错,结果都是 20 万。
