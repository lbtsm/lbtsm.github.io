## Summary

当我们饭馆的生意越来越好时。午市一开,订单一张接一张地涌进厨房:有点一碗阳春面的,有点一桌全羊宴的,有点了一份凉拌黄瓜就急着赶回去上班的,还有一位常来的老顾客,点完就盯着厨房看。

可灶台就那么几口,同一时刻只能做那么几道菜。**下一道先做谁的?**

这个问题看着简单,决定的却是客人的体验:同样一个中午,同样的厨师和灶台,排单方式不同,有的饭馆客人平均十分钟上菜,有的饭馆平均也是十分钟,但总有几桌等了一个小时、拍桌子走人。

计算机里,"下一个让哪个线程用 CPU"这件事叫**调度**,做这个决定的是内核里的**调度器**,也就是饭馆的经理。这一篇跟着经理,把排单的办法一个个试一遍。为了讲清楚,先假设厨房里只有一口灶,也就是只有一个 CPU 核心。

---

## 经理到底想要什么

经理排单,心里其实同时惦记着好几件事:

- **一个中午总共出多少道菜**,越多越好。计算机里叫**吞吐量**。
- **每桌从点单到全部上齐要多久**,越短越好。叫**周转时间**。
- **每桌从点单到吃上第一口要多久**,越短越好。叫**响应时间**。客人等第一道菜等得最焦躁。
- **别让哪桌一直被晾着**,叫**公平性**。
- **灶台别闲着**,叫 **CPU 利用率**。

麻烦在于这几件事互相打架,最典型的是"出菜总量"和"吃上第一口"之间:

```
想多出菜 → 厨师少换锅(换锅要洗锅、换料,耽误工夫)→ 一道菜一口气做完
                                                    → 后面的桌等得久,第一口来得晚

想让每桌都快点吃上 → 多换锅,每桌轮流做一点
                                                    → 换锅次数多,总出菜量下降
```

---

## 先来先做:一桌全羊宴堵死整个厨房

最朴素的办法是按点单顺序,做完一桌再做下一桌。这叫**先来先服务**(FCFS)。

听起来最公平,直到某天中午,第一张单子是一桌全羊宴,要做 100 分钟;紧跟着两张单子,各是一碗阳春面,各要 1 分钟。

```
按点单顺序:全羊宴(100) → 面 A(1) → 面 B(1)
  三桌分别在第 100、101、102 分钟吃完
  平均要等 (100 + 101 + 102) / 3 ≈ 101 分钟

把两碗面挪到前面:面 A(1) → 面 B(1) → 全羊宴(100)
  三桌分别在第 1、2、102 分钟吃完
  平均要等 (1 + 2 + 102) / 3 = 35 分钟
```

只是换了个顺序,平均等待时间就缩短到三分之一。全羊宴那桌只多等了 2 分钟,两碗面的客人却省了 100 分钟。

这种"一个大任务堵在前面,后面所有小任务一起被拖慢"的现象,叫**护航效应**。就像超市里一个人推着满满一车货在结账,后面只拿一瓶水的人只能干等。

## 短的先做:理论上最好,实际上做不到

既然大单堵路,那就**每次先做最快能做完的那张**,这叫**短作业优先**(SJF)。凉菜先上、面条先上,大菜往后排。可以证明,在所有排法里,它的平均周转时间最短。

它还有一个改进版:做大菜做到一半,又来了一张更短的单子,就先停下来把短的做掉,这叫**最短剩余时间优先**(SRTF)。

但这个办法在饭馆里能用,在计算机里却用不了,问题有两个。

**第一,经理不知道每张单子要做多久。** 饭馆的菜单是固定的,做一碗面几分钟,经理心里有数。计算机里的情况更像是:每位客人都带着自己写的菜谱来,让厨房照着做,菜谱有多长、中间要等几次炖锅,经理事先根本看不到。一个程序要跑多久,操作系统没法提前知道。

**第二,大单可能永远做不上。** 只要短单源源不断地来,全羊宴就一直往后排,永远轮不到。一个任务因为一直排不上而永远得不到 CPU,这叫**饥饿**。

所以短作业优先在实际中只能当一个"理想上限":后面的办法都在想,怎样在不知道时长、也不饿死任何人的前提下,尽量接近它。

## 每桌轮流炒一会:谁都能很快吃上第一口

换个思路:不再求"一张单子一口气做完",而是**每张单子轮流做一小会儿**。规定每次最多做 2 分钟,到点不管做完没有,都换下一张,没做完的排回队尾。

```
每次 2 分钟,三张单子 A、B、C:
A B C A B C A B C ……
```

这叫**时间片轮转**(RR),那"一小会儿"叫**时间片**。

它解决的是响应时间:不管前面排了多少单,最多等一圈就能轮到。点凉拌黄瓜赶着上班的客人,不会再被全羊宴堵上一个半小时。

代价有两个。

**一是换锅本身要花时间。** 每次换单子,厨师要把手上这道菜的进度记好、把锅洗了、把下一道菜的料摆上来。时间片定得太短,比如每道菜只炒 10 秒就换,大半时间都花在换锅上了。时间片定得太长,比如每次 30 分钟,又退回成了先来先做。计算机里,一次切换的直接成本是一到几微秒,时间片一般在几毫秒到几十毫秒,让切换开销只占很小的比例。

**二是"全部上齐"反而变晚了。** 每张单子都被拆成很多段,和别人的穿插着做,每一桌的最后一道菜都要等到很晚才出锅。时间片轮转用平均周转时间换来了响应时间。对于有人在等着看结果的场景(桌面程序、网页服务),这笔交易很划算;对于只关心"一批活多久干完"的后台批处理,就不划算。

## VIP 优先:老顾客满意了,散客饿死了

常来的老顾客跟经理抱怨:"我每周来三次,能不能先给我做?"经理一想有道理,给单子分了等级:VIP 的单子永远先做,普通单子在 VIP 单子都做完之后再做。这叫**优先级调度**。

周末 VIP 特别多,一张接一张,普通客人的单子从中午压到下午三点还没开始做。

这又是饥饿。解决办法也很直接:**普通单子等得越久,就给它的等级往上提一点**,等到一定程度,就算是散客也能排到 VIP 前面去。这叫**老化**(aging)。

---

## 看客人的表现来分级:多级反馈队列

到这里,经理面临一个两难:短的先做效果最好,但不知道谁短;按等级排要提前给每张单子定级,可经理也不知道该给谁定什么级。

一位老经理想出了办法:**不知道将来,就看过去。** 他发现订单大体分两种:

- 有的单子每次一上灶,做不了一会儿就要等:等炖锅、等烤箱、等客人确认口味。这种单子每次占灶的时间很短,而且客人往往正盯着,很在意响应速度。
- 有的单子一上灶就不停地炒,每次都把分给它的时间用满,比如一大锅需要连续翻炒的炒饭。这种单子在意的是"总共多久能做完",早一分钟晚一分钟开始,区别不大。

于是他在厨房里挂了好几排订单架,做法是:

```
等级
 高  ┌────────────────┐  每次最多做 1 分钟   ← 新单子一律从这里开始
     │   第 1 排       │
     └───────┬────────┘
             │ 把 1 分钟用满了还没完 → 降到下一排
 中  ┌───────▼────────┐  每次最多做 2 分钟
     │   第 2 排       │
     └───────┬────────┘
             │ 又用满了 → 再降
 低  ┌───────▼────────┐  每次最多做 4 分钟
     │   第 3 排       │
     └────────────────┘

规矩:
 ① 永远先做高等级那排的单子
 ② 一张单子把分给它的时间用满了,就降一级
 ③ 没用完就主动去等别的了,就留在原级
 ④ 每隔一段时间,把所有单子都提回第 1 排
```

这叫**多级反馈队列**(MLFQ)。它的妙处在于,经理不用事先知道任何东西,单子自己的表现就把它分到了合适的位置:

- 经常要等、每次占灶时间短的单子,一直留在高等级,来了就能很快上灶,响应很快。
- 一上灶就不停炒的单子,慢慢沉到低等级。低等级每次能做的时间更长,换锅次数少,反而做得更有效率。

新单子从最高级开始,如果它其实很短,一两次就做完了,效果就接近"短的先做";如果它很长,很快就会沉下去,不会挡住别人。

第 ④ 条规矩有两个作用。一是防饿死,低等级的单子总有被提上来的时候。二是防钻空子:曾经有客人摸清了规矩,每次在分给他的时间快用完时,故意说一句"等一下,我确认下口味",这样就永远不算"用满",一直赖在最高级。定期重置让这招失效;更好的做法是改成按"在这一级累计用了多少时间"来降级,不管中间停了几次,累计用满就降,钻空子就彻底没用了。

计算机里,"要等的单子"就是频繁等键盘输入、等网络数据的交互式程序,"一上灶就不停炒的单子"就是编译、视频转码这类纯计算的程序。Windows、macOS 和早期的 Unix 调度器,都用过多级反馈队列的思路。

## 记账本:Linux 的完全公平调度器

Linux 的经理用的是另一套思路,更简单,也更优雅。从 2.6.23 版本(2007 年)开始用了十几年,叫**完全公平调度器**(CFS)。

### 谁吃亏最多,就先给谁

经理不再分几排订单架,而是拿出一个记账本,**给每张单子记一笔"已经占用灶台多少分钟"**。排单的规矩只有一条:

**每次都选账上记得最少的那张单子来做。**

一张单子上了灶,它的账就开始往上涨;涨到超过别人了,它就不再是最少的,自然会被换下来,让账面最少的那张上。这个账在 Linux 里叫 `vruntime`(虚拟运行时间)。

就像给几个孩子分蛋糕,不是排队一人一块,而是**谁碗里最少就给谁添一勺**,添着添着,大家碗里就差不多一样多了。

这套规矩自带几个好效果:

- **经常要等的单子天然占便宜。** 一张单子去等炖锅了,这段时间不占灶,账就不涨;等它回来,账面比一直在炒的单子少得多,马上就能上灶。交互式程序的响应因此很好,不用专门去识别它们。
- **不需要固定的时间片,也不需要分好几排。** 只需要一个按账面排好序的订单架。

新来的单子从多少记起,有个讲究:如果从 0 记起,它的账面比谁都少,会一直霸着灶台,直到追上大家。所以新单子是按当前账面最少的那张来起记的,既能很快轮到,又不会一下子霸占很久。

### VIP 的账记得慢

那 VIP 怎么体现?规矩不变,还是选账面最少的,只是**VIP 的账涨得慢**:同样在灶上做了 1 分钟,普通单子记 1 分钟,VIP 可能只记 0.8 分钟。账涨得慢,就更常是最少的那个,也就更常被选中。

Linux 里这个等级叫 **nice 值**,从 -20 到 19,数字越小越优先(越"不 nice",越不让着别人)。nice 值每差 1,分到的 CPU 份额大约差 10%;差 5,大约差 3 倍。所有任务遵守同一条规则,优先级只体现在"账涨得快还是慢"上。

### 订单架用红黑树

"每次选账面最少的",需要一个能快速做三件事的订单架:找出最小的、放进一张新单子、抽出任意一张单子(一张单子去等炖锅时,要把它从架子上拿下来)。

CFS 用的是**红黑树**,一种自动保持平衡的二叉搜索树,按账面从小到大排好。账面最少的就是树最左边的那个节点,内核还专门把它缓存起来,取最小几乎不花时间;插入和删除都是 O(log n)。

### EEVDF:不光看谁吃亏,还看谁急

CFS 有一个照顾不到的地方:它只管"公平",不管"急不急"。点了一碗面、只要一小会儿灶台的客人,和点了一大锅炒饭的客人,在账面相同的时候是一样对待的,可前者其实只要插进来一下就能走。

从 Linux 6.6(2023 年)开始,内核用 **EEVDF** 替代了 CFS。它保留了记账本,但多看一样东西:

- 先看账:**少拿了自己应得那份的单子,才有资格上灶**,这一步保证公平,和 CFS 是一个意思。
- 在有资格的单子里,**给每张单子算一个"这一口最晚该在什么时候做完"的截止时间,选截止时间最早的。** 只要一小口灶台时间的单子,截止时间自然靠前,能更快插进来。

结果是,延迟敏感的短任务能更快地被照顾到,而整体仍然公平。思路和 CFS 一脉相承,理解了记账本,EEVDF 也就理解了。

### 几类不同待遇的单子

Linux 的经理手上其实不止一套规矩,而是把单子分成几类,按类别的先后来排:

| 类别 | 用途 | 饭馆里 |
|---|---|---|
| `SCHED_DEADLINE` | 有明确截止时间的实时任务 | 必须在某个时刻准时上桌的婚宴主菜 |
| `SCHED_FIFO` / `SCHED_RR` | 实时任务,优先级 1~99 | 急救:来了就插到所有普通单子前面 |
| `SCHED_OTHER`(普通) | 你写的程序默认在这里,用 CFS/EEVDF | 普通单子,按记账本排 |
| `SCHED_BATCH` | 批处理,不在乎响应 | 明天才要的预订单 |
| `SCHED_IDLE` | 只在完全没事时才做 | 厨房闲下来才做的员工餐 |

实时类别要格外小心:一个 `SCHED_FIFO` 的任务如果陷入死循环,它会一直压着同一个核上的所有普通任务。Linux 默认会给普通任务留一点保底的 CPU 时间,不至于让系统彻底失去响应,但普通任务会慢到几乎不可用。除非在做真正的实时系统,不要随便用这几个类别。

## 多口灶以后的新问题

前面一直假设只有一口灶。饭馆扩建成八口灶以后,经理除了决定"做哪张单",还要决定"在哪口灶上做"。

**每口灶一个订单架。** 如果八口灶共用一个订单架,八个厨师每次取单都要挤到同一个架子前,排队取单的时间反而成了瓶颈。所以每口灶旁边放一个自己的订单架,厨师只从自己的架子上取。经理定期巡视,哪口灶的架子堆满了、哪口灶的空了,就把单子挪一挪,这叫**负载均衡**。

**单子别在灶台之间搬来搬去。** 一道菜在 3 号灶上做了一半,锅是热的,料都摆在 3 号灶旁边。这时候把它挪到 5 号灶,锅得重新烧热,料得重新搬过去。所以经理会尽量让一张单子留在原来那口灶上,除非忙闲差得太多。计算机里,"热锅和摆好的料"就是 CPU 核心自己的缓存:一个线程在某个核上跑了一会儿,它常用的数据就在这个核的缓存里,换到别的核,缓存要重新装。这叫**缓存亲和性**。延迟要求特别高的程序,会干脆把关键线程钉在固定的核上(`taskset -c 0,1 ./程序` 就是只允许它在 0、1 号核上跑)。

**厨房分了区,冰箱也分了远近。** 大饭馆的后厨分成东西两个区,各有一组灶台和一台冰箱。东区的厨师从东区冰箱拿料几步就到,去西区冰箱拿就要穿过整个后厨。大型服务器也是这样:多颗 CPU 各自连着一部分内存,访问自己那部分快,访问别人那部分要慢一些。这叫 **NUMA**(非统一内存访问)。经理会尽量让一张单子和它要用的料待在同一个区。`numactl --hardware` 可以看到机器分了几个区。

## 包灶的外包团队:容器的 CPU 限额

饭馆生意大了,开始把一部分灶台按时间包给外包团队用。合同是这么写的:**每 100 分钟里,这个团队最多用 200 "灶·分钟"**,也就是平均相当于一直占着 2 口灶。

有一天,某个外包团队来了 64 个厨师。按合同,他们平均只能用 2 口灶,但一开工,64 个人同时冲上 64 口灶,干了 3 分钟多,200 灶·分钟的额度就用光了。按合同规定,额度用光后整个团队**全部停工,一直等到这 100 分钟结束**,下一个周期才能再开工。这 90 多分钟里,他们手上没做完的菜全都晾着,客人干等。

```
时间 →  [64 人同时干,3 分钟用完额度][────── 全队停工,等下个周期 ──────][下个周期]
        0                         3                                     100
```

从外面看,这个团队一个周期总共只用了 200 灶·分钟,平均 2 口灶,一点都不多;但他们的客人却时不时要多等很久。

这就是容器里最常见、也最让人摸不着头脑的性能问题。Kubernetes 给容器设的 `cpu limit: 2`,底层就是 Linux cgroup 的 CPU 配额: 每 100 毫秒的周期里,容器内所有线程加起来最多用 200 毫秒的 CPU 时间,相当于 2 个核跑满。线程一多,这点配额可能 25 毫秒就花光了。配额一旦用完,容器里所有线程都被冻结到下个周期开始。症状是:**CPU 平均使用率看着才一半,P99 延迟却时不时冒出几十毫秒的尖刺。**

查它只要看一个文件:

```bash
cat /sys/fs/cgroup/cpu.stat
# nr_throttled     被叫停了多少次
# throttled_usec   总共被冻结了多少微秒
# 这两个数一直在涨,就是被限流了
```

64 个厨师同时冲上去,正是程序"以为自己有很多核"造成的。

## 把饭馆翻译回计算机

**调度器什么时候出手。** 经理不是一直站在厨房里盯着的。内核调度器在这几种时候做决定:当前线程主动去等了(读磁盘、等网络、等锁、sleep),这叫**自愿切换**;时钟中断到来,发现当前线程用完了它该用的时间,或者有一个更该运行的线程醒了,把当前线程换下,这叫**非自愿切换**,也就是抢占。

**这两种切换能分别看到。**

```bash
vmstat 1                  # cs 列:整台机器每秒的切换次数
pidstat -w -p <进程号> 1   # cswch/s:自愿切换  nvcswch/s:非自愿切换
```

它们说明的问题完全不同。自愿切换多,说明程序经常在等,对网络服务来说通常是正常的,远超预期时可能是锁争抢严重。非自愿切换多,说明可运行的线程比 CPU 核多,大家在抢灶台。如果非自愿切换很高、CPU 却没用满,通常是线程开得太多了,减少并发反而更快。

**调整优先级和调度类别。**

```bash
nice -n 10 ./批处理任务           # 以较低优先级启动
renice -n 5 -p <进程号>            # 调整运行中进程的 nice 值
chrt -p <进程号>                   # 查看一个进程的调度类别和实时优先级
taskset -pc 2 <进程号>             # 把运行中的进程绑到 2 号核
```

**内核调度器的位置。** CFS 和 EEVDF 的代码在内核源码的 `kernel/sched/fair.c`(名字里的 fair 就是"公平")。每个 CPU 核有一个运行队列 `struct rq`,普通任务挂在其中按虚拟运行时间排序的红黑树上。

## 工作方向的关联

**Go 程序里有两层调度。** 上一篇的领班(Go 运行时)把 goroutine 排到线程上,这一篇的经理(内核)把线程排到 CPU 核上。`GOMAXPROCS` 管的是第一层;第二层你基本管不了,容器的 CPU 限额就作用在这一层。两层都可能是瓶颈:第一层开得再多,第二层只给 2 个核也没用。

**P99 延迟有尖刺而 CPU 不高,先查 `cpu.stat`。** 这是第 9 节的场景。Go 1.26 会按容器的 CPU 限额自动设置 `GOMAXPROCS`(前提是 `go.mod` 版本足够新),避免"64 个厨师冲上去"。但程序瞬时并发很高时,即使 `GOMAXPROCS` 设对了,也可能在短时间内把配额用完,这时要么调大限额,要么把并发压平。

**worker 池的大小按任务类型定。** 等网络的任务可以远多于核数;纯计算的任务接近核数就够了。用 `pidstat -w` 看非自愿切换,是判断"是不是开多了"的好办法。

**排单的思路可以搬到业务里。** 处理任务队列时,一个耗时很长的任务堵住一批短任务,就是之前讲的护航效应;按历史耗时把快的和慢的分到不同队列,是多级反馈队列的思路。多租户共享资源(比如给不同客户分配接口配额)时,记下每个租户已经用了多少、每次优先给用得最少的,再让高级别租户的账涨得慢一点,就是就是记账本。

## 总结

```
午市订单涌进来,只有一口灶,先做谁?
  │
  ├─ 先来先做(FCFS):一桌全羊宴堵死后面的面条 = 护航效应
  ├─ 短的先做(SJF):平均最快,但不知道谁短,大单会饿死
  ├─ 每桌轮流炒一会(RR):第一口来得快,但换锅有成本,全部上齐变晚
  ├─ VIP 优先:散客饿死 → 等久了就提级(老化)
  ├─ 看表现分级(MLFQ):常等的留在高级,一直炒的沉下去,定期全部提回
  └─ 记账本(CFS → EEVDF):谁占灶最少先给谁;VIP 的账涨得慢;
                            EEVDF 再看谁急,只要一小口的先插进来
  ▼
扩建成多口灶
  │ 每口灶一个订单架 + 定期挪单(负载均衡)
  │ 别让菜在灶台间搬来搬去(缓存亲和性);厨房分区,冰箱分远近(NUMA)
  ▼
外包团队包灶(容器 CPU 限额)
    一下子冲上去用光额度,全队停工到下个周期 → 平均不高,延迟尖刺
```

最该记住的几句话:

- **调度的核心矛盾在吞吐和响应之间**:少切换出活多,多切换响应快。
- **短作业优先理论最好但做不到**,因为不知道任务要跑多久;多级反馈队列用"看过去的表现"来逼近它。
- **Linux 的 CFS 只有一条规矩:选占用 CPU 最少的那个**;优先级只是让账涨得快慢不同。EEVDF 在公平之外又照顾了延迟。
- **任何按优先级排的办法都要防饥饿。**
- **容器的 CPU 限额是按周期给的额度,用光了整个容器冻结**,所以会出现"CPU 不高、延迟有尖刺"。
